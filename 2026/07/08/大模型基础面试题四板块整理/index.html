LLM 运行机制相关面试题

1. Token 是什么？为什么中文、英文、代码消耗的 Token 不一样？

Token 是大模型处理文本的最小计量单位，可以理解为模型眼中的“文本切片”。 它不一定等于一个字、一个词或一个字符，而是由模型使用的分词器根据训练语料和编码规则切分出来的片段。

在工程上，Token 主要用于三件事：

  • 计量上下文长度，例如一个模型支持 128K tokens 上下文。
  • 计算调用成本，通常输入 Token 和输出 Token 分别计费。
  • 控制生成长度，例如限制最多输出 2048 tokens。

中文、英文和代码消耗 Token 不一样，核心原因是它们在分词器中的切分方式不同：

  • 英文通常会按常见词根、单词、子词切分。例如 development 可能被切成一个或几个 Token，常见英文单词通常比较省 Token。
  • 中文没有天然空格分词，很多中文字符可能会被单独切分，或者几个常见字组成一个 Token。因此中文并不一定比英文省 Token，具体取决于分词器。
  • 代码包含大量符号、缩进、变量名、括号、换行和不常见标识符，很多片段可能被拆得更细，所以同样字符数下，代码往往更耗 Token。

面试中可以这样总结：

Token 不是字符，也不是单词，而是模型分词器切出来的文本单元。不同语言和内容形态的统计规律不同，所以中文、英文、代码的 Token 消耗不同。做 AI 应用时，Token 会直接影响成本、延迟和上下文容量。

2. 上下文窗口是什么？上下文窗口越大，效果一定越好吗？

上下文窗口指模型一次请求中能够“看到”的最大 Token 数量，包括系统提示词、用户输入、历史对话、工具结果、RAG 检索内容和模型输出。

例如一个模型支持 128K tokens 上下文，并不代表输入可以完整占满 128K，因为还要给输出预留 Token。假设最多上下文是 128K，如果输入已经占了 126K，那模型可生成的空间就很少。

上下文窗口变大有明显好处：

  • 可以处理更长文档、更多历史对话和更复杂任务。
  • 可以减少过早截断上下文导致的信息丢失。
  • 在代码审查、合同分析、长文档问答等场景中更方便。

但上下文窗口越大，效果不一定越好，原因包括：

  • 注意力稀释：信息太多时，模型不一定能稳定关注关键内容。
  • 噪声增加：无关内容越多，越容易干扰推理。
  • 成本更高：输入 Token 越多，调用成本通常越高。
  • 延迟更高：长上下文会增加推理时间。
  • 可靠性不线性提升：模型虽然“能看到”，但不代表一定“用得好”。

生产环境中，更推荐“有效上下文”而不是“最大上下文”。也就是说，只放和当前任务最相关、最可信、最结构化的信息。

面试中可以这样回答：

上下文窗口是模型一次推理能处理的最大 Token 范围。窗口大能提升长任务处理能力，但不等于效果一定更好。工程上要控制上下文质量，避免把大量无关内容直接塞给模型。

3. 什么是 Lost in the Middle 问题？长上下文场景下怎么缓解？

Lost in the Middle 指的是在长上下文中，模型对开头和结尾的信息更敏感，而容易忽略中间位置的关键信息。

例如把一份很长的资料塞进上下文，关键证据刚好位于中间，模型可能明明“看到了”这段内容，却在回答时没有正确使用它。这说明长上下文不是简单的“放进去就能记住”。

常见原因包括：

  • Transformer 注意力机制在长序列中对信息位置存在偏好。
  • 上下文越长，相关信息和噪声混在一起，检索和利用难度变高。
  • 生成答案时，模型更容易依赖靠近指令或靠近输出位置的信息。

长上下文场景下可以这样缓解：

  • 把最重要的信息放在开头或靠近问题的位置，不要把关键证据埋在中间。
  • 对长文档先做分块、摘要和结构化提取，再让模型基于压缩后的内容回答。
  • 使用 RAG 检索相关片段，只把高相关内容放入上下文。
  • 对证据排序，把最相关、最权威、最新的证据排在前面。
  • 重复强调关键约束，例如在系统提示词和用户问题附近都写明回答依据。
  • 使用引用和编号，让模型按证据编号回答，降低遗漏概率。
  • 分阶段推理，先找证据，再基于证据回答，而不是一次性生成最终答案。

面试中可以这样总结：

Lost in the Middle 是长上下文中的信息利用问题，不是单纯的上下文长度问题。缓解思路是减少噪声、调整关键信息位置、用 RAG 精准召回、对证据结构化，并把任务拆成“找证据”和“生成答案”两个阶段。

4. Temperature、Top-P、Top-K 分别控制什么？生产环境怎么设置更稳？

这三个参数都和模型生成的随机性有关，但控制方式不同。

Temperature 控制概率分布的平滑程度。

  • Temperature 越低，模型越倾向选择高概率词，输出更稳定、更保守。
  • Temperature 越高，低概率词也更可能被选中，输出更发散、更有创意。
  • 常见范围是 0 到 2，但生产中通常不会设置太高。

Top-P 又叫 nucleus sampling，控制从累计概率达到 P 的候选 Token 集合中采样。

  • top_p = 0.9 表示只从累计概率前 90% 的候选 Token 中采样。
  • Top-P 会动态调整候选集合大小。
  • 它适合控制生成多样性，同时避免特别低概率的离谱输出。

Top-K 控制每一步只从概率最高的 K 个候选 Token 中采样。

  • top_k = 40 表示每一步最多只考虑概率最高的 40 个 Token。
  • Top-K 是固定候选数量，不像 Top-P 那样按累计概率动态变化。
  • 部分 API 不暴露 Top-K，更多暴露 Temperature 和 Top-P。

生产环境更稳的设置建议：

  • 事实问答、RAG、客服、代码生成：低 Temperature，例如 0 到 0.3。
  • 分类、抽取、结构化输出：尽量低 Temperature，并配合 JSON Schema 或函数调用。
  • 创意写作、营销文案、头脑风暴：可以适当提高，例如 0.7 到 1.0。
  • 不要同时大幅调整多个采样参数，否则不容易判断效果变化来自哪里。
  • 优先固定参数并做评测，不要凭感觉调参。

面试中可以这样回答：

Temperature 控制随机性强弱，Top-P 控制候选 Token 的累计概率范围，Top-K 控制候选 Token 的数量。生产环境如果追求稳定，一般使用较低 Temperature，配合结构化输出约束、评测集和重试机制。

5. 为什么 Temperature 设置为 0，模型输出仍然可能不完全一致？

Temperature 设置为 0 通常表示尽量选择最高概率 Token，让输出更接近确定性，但它不保证绝对一致。

原因主要有几类：

  • 底层推理并非完全确定：GPU 并行计算、浮点数精度、算子实现和并发调度可能带来极小差异。
  • 概率接近时容易发生选择差异：当多个候选 Token 的概率非常接近时，微小数值差异可能改变最终选择。
  • 服务端实现可能变化：模型版本、系统提示词、路由策略、安全策略或推理框架升级都可能影响结果。
  • 上下文并不完全相同：哪怕多一个空格、换行、历史消息或工具结果，输出也可能不同。
  • 部分接口的 temperature = 0 不是数学意义上的完全贪心解码，不同厂商实现可能略有差别。

如果生产环境需要尽量稳定，可以使用这些方法：

  • 固定模型版本，不使用自动升级别名。
  • 固定 Prompt 模板、参数和上下文拼接顺序。
  • 使用结构化输出约束，例如 JSON Schema。
  • 对关键任务增加后处理校验。
  • 对非确定性结果做幂等设计和缓存。
  • 使用评测集监控输出漂移。

面试中可以这样总结：

Temperature 为 0 只能降低随机性，不能保证完全确定性。大模型推理涉及浮点计算、并行执行、服务端版本和上下文细节，都会导致轻微差异。工程上要通过版本固定、结构化约束、缓存和评测来提升稳定性。

6. 大模型为什么会产生幻觉？常见缓解方案有哪些？

幻觉是指模型生成了看似合理但事实错误、无依据或与上下文不一致的内容。

大模型产生幻觉的根本原因是：它本质上是在根据上下文预测下一个 Token，而不是像数据库一样检索事实。它擅长生成符合语言规律的内容，但不天然保证事实正确。

常见原因包括：

  • 训练数据中存在错误、过时或相互矛盾的信息。
  • 模型没有访问实时知识或私有知识，但仍然尝试补全答案。
  • Prompt 要求过于开放，没有要求引用依据或承认不知道。
  • 上下文证据不足，模型只能根据模式猜测。
  • 问题本身包含错误前提，模型可能顺着错误前提回答。
  • 生成目标偏向流畅性，模型会优先生成自然、完整的回答。

常见缓解方案包括：

  • RAG：从知识库、数据库、文档系统中检索证据，让模型基于证据回答。
  • 工具调用：对计算、查询、搜索、订单状态等任务调用外部工具，而不是让模型猜。
  • 强约束 Prompt：要求“只基于给定资料回答，资料不足则说明无法判断”。
  • 引用来源：要求答案引用文档片段、链接、ID 或数据库字段。
  • 结构化输出：用 JSON Schema、函数调用或枚举值约束输出空间。
  • 后处理校验：对数字、日期、代码、SQL、权限等结果做程序化验证。
  • 多阶段流程：先检索证据，再判断证据是否足够，最后生成答案。
  • 人工审核：高风险场景必须引入人工确认。
  • 评测和监控：建立幻觉率、引用准确率、拒答率等指标。

面试中可以这样回答：

幻觉来自大模型的生成式本质，它生成的是高概率文本，不是事实查询结果。缓解幻觉不能只靠 Prompt，而要结合 RAG、工具调用、结构化约束、证据引用、后处理校验和评测监控。

7. Token 预算怎么估算？输入、输出、历史消息、RAG 证据如何取舍？

Token 预算就是在模型上下文窗口和成本限制内，合理分配输入、输出、历史消息和外部证据的 Token。

一个完整请求通常包括：

  • 系统提示词。
  • 开发者或业务规则提示词。
  • 用户当前问题。
  • 历史对话。
  • RAG 检索证据。
  • 工具调用结果。
  • 预留输出 Token。

估算 Token 预算时，可以先用这个公式：

例如模型上下文窗口是 32K tokens，可以粗略分配：

  • 系统提示词和业务规则：1K - 3K
  • 当前用户问题：1K - 2K
  • 历史对话摘要：2K - 6K
  • RAG 证据：10K - 18K
  • 工具结果：1K - 4K
  • 预留输出：2K - 4K

具体取舍原则如下：

  • 当前用户问题优先级最高，不能被压缩到丢失意图。
  • 系统规则必须保留，尤其是安全、权限、格式、业务边界。
  • 历史消息不应原样无限追加，应该做摘要、裁剪或只保留与当前任务相关的部分。
  • RAG 证据宁可少而准，不要多而杂，相关性和可信度比数量更重要。
  • 输出 Token 必须预留，否则模型可能回答不完整。
  • 工具结果要结构化压缩，例如只保留关键字段，不要直接塞完整 JSON 日志。
  • 长文档任务要分阶段处理，不要把所有材料一次性塞入。

常见工程策略：

  • 使用 tokenizer 在请求前精确计算 Token。
  • 对历史对话做滚动摘要。
  • 对 RAG 结果按相关性、权限、时间和来源质量排序。
  • 对文档 chunk 做去重和压缩。
  • 为不同任务配置不同预算模板。
  • 如果超预算，按“低相关证据、旧历史、冗余工具结果”的顺序裁剪。

面试中可以这样总结：

Token 预算本质是在上下文窗口、成本、延迟和答案质量之间做权衡。当前问题、系统规则和输出空间优先保留；历史消息要摘要化；RAG 证据要少而准；工具结果要结构化压缩。

8. 长上下文窗口会不会取代 RAG？二者分别适合什么场景？

长上下文窗口不会完全取代 RAG，它们解决的问题不同，更常见的是组合使用。

长上下文窗口的优势是简单直接，可以把大量材料一次性放进模型，让模型在一个请求中综合分析。它适合这些场景：

  • 单份或少量长文档分析。
  • 合同、论文、代码文件的整体审阅。
  • 用户明确提供材料，并希望模型在材料内部做总结、对比、抽取。
  • 信息规模不大，但单次任务需要完整上下文。
  • 对实时更新和权限过滤要求不复杂的场景。

RAG 的优势是从大规模外部知识库中动态检索相关内容，再把少量高相关证据提供给模型。它适合这些场景：

  • 企业知识库问答。
  • 海量文档检索。
  • 内容经常更新的业务知识。
  • 需要权限控制、多租户隔离的系统。
  • 需要引用来源和可追溯答案的场景。
  • 需要控制成本和延迟的生产应用。

长上下文不能完全替代 RAG，主要原因是：

  • 企业知识库可能远大于任何上下文窗口。
  • 把所有内容都塞进上下文成本高、延迟高。
  • 长上下文中仍然有 Lost in the Middle 问题。
  • RAG 可以做权限过滤、实时更新、来源追踪和召回排序。
  • RAG 可以把“找信息”和“生成答案”解耦，系统可控性更好。

比较合理的架构是：

  • 用 RAG 从大规模知识库中召回最相关材料。
  • 用长上下文承载更多高质量证据、历史和工具结果。
  • 用重排序、摘要和引用机制提升证据利用率。
  • 对关键场景增加校验和人工审核。

面试中可以这样回答：

长上下文提升了模型一次性处理材料的能力，但不会取代 RAG。长上下文适合处理用户已提供的有限长材料，RAG 适合从大规模、动态、需要权限控制和来源追踪的知识库中取证。生产系统通常是 RAG 加长上下文，而不是二选一。

API 调用工程相关面试题

1. 大模型 API 调用的完整链路是什么？

大模型 API 调用不是简单地发一个 HTTP 请求拿结果，而是一条完整的生产调用链路。 在真实业务里，模型通常要被当作一个慢、贵、不完全稳定、输出不可完全控的外部依赖来治理。

一个相对完整的调用链路可以分为这些阶段：

其中比较关键的工程点包括：

  • 请求校验：校验用户权限、输入长度、敏感参数、业务状态，避免非法请求直接进入模型。
  • Prompt 组装：把系统提示词、业务规则、用户问题、历史上下文和外部证据按固定模板拼接。
  • 上下文治理：对历史消息做摘要，对 RAG 证据做筛选，避免超过 Token 上限。
  • 模型路由：根据任务类型、成本、延迟、质量要求选择不同模型。
  • 限流与熔断：防止单租户、单用户或异常流量打爆模型服务。
  • 超时与重试：对可恢复错误做有限重试，对不可恢复错误快速失败。
  • 结构化解析：如果输出要进入业务系统，必须做 JSON Schema、枚举、类型和业务规则校验。
  • 观测与审计：记录调用日志、Token 消耗、延迟、错误码、模型版本和用户反馈。

面试中可以这样总结：

大模型 API 调用链路包括请求校验、Prompt 组装、上下文注入、Token 预算、模型路由、限流、超时、重试、流式返回、结构化解析、结果校验、日志和评测。生产系统不能把模型 API 当成普通 HTTP 接口直接裸调。

2. Streaming 为什么能改善用户体验？它能减少总耗时和 Token 成本吗？

Streaming 的核心价值是改善首字延迟和交互感，而不是必然减少总耗时或 Token 成本。

普通非流式调用通常是模型生成完整答案后，服务端一次性返回给前端。用户需要等待整个生成过程完成，页面才有内容展示。如果答案较长，用户会明显感觉“卡住了”。

流式输出则是模型边生成边返回，前端边接收边展示。它带来的体验改善主要有：

  • 首字时间更短：用户更快看到第一个 Token 或第一段内容。
  • 等待感降低：即使完整答案还没生成完，用户也能看到系统正在工作。
  • 可中途停止：用户发现方向不对时可以点击停止，减少无效生成。
  • 更适合长回答：写作、代码生成、总结报告等长输出任务体验明显更好。
  • 便于做渐进式 UI：例如边生成边展示引用、步骤、工具调用状态。

但 Streaming 不一定减少总耗时：

  • 模型完整生成同样数量 Token 所需的计算量基本没有减少。
  • 网络传输从“一次返回”变成“多次小块返回”，甚至可能有额外开销。
  • 如果后端还要做完整后处理，最终完成时间未必更短。

Streaming 也不直接减少 Token 成本：

  • 成本通常按输入 Token 和输出 Token 计费。
  • 如果最终生成的内容一样，Token 成本基本一样。
  • 只有在用户中途停止、系统提前截断或减少无效输出时，才可能间接降低成本。

面试中可以这样回答：

Streaming 改善的是用户感知延迟，尤其是首字延迟，而不是必然降低模型总推理时间。它本身不减少 Token 单价或计算量，但可以通过中途停止、减少无效生成来间接节省成本。

3. SSE、WebSocket、HTTP Chunked 在流式输出场景下怎么选？

这三种方式都能实现流式输出，但适用场景不同。

SSE，也就是 Server-Sent Events，适合服务端向浏览器单向推送文本事件。

优点：

  • 浏览器原生支持 EventSource。
  • 基于 HTTP，接入成本低。
  • 自动重连机制比较方便。
  • 很适合大模型文本流式输出，因为大多数场景是服务端持续向前端推 Token。

缺点：

  • 主要是单向通信，客户端如果要发消息通常需要额外 HTTP 请求。
  • 不适合高频双向互动。
  • 某些代理、网关或服务端框架需要额外配置缓冲策略。

WebSocket 适合双向、低延迟、持续连接的交互场景。

优点：

  • 支持客户端和服务端双向通信。
  • 适合实时语音、多人协作、Agent 运行状态同步、复杂交互式会话。
  • 可以在同一连接里发送控制指令，例如暂停、继续、取消、确认工具调用。

缺点：

  • 连接管理更复杂。
  • 对负载均衡、心跳、断线重连、鉴权和扩缩容要求更高。
  • 对简单文本生成来说可能偏重。

HTTP Chunked 是 HTTP 层的分块传输机制，适合服务端逐块返回响应体。

优点：

  • 协议层简单，很多后端框架可以直接支持。
  • 不一定要求浏览器使用 SSE 格式。
  • 适合后端服务之间的流式转发。

缺点：

  • 浏览器端处理体验通常不如 SSE 标准化。
  • 缺少 SSE 那样的事件语义和自动重连约定。
  • 中间代理可能缓冲响应，导致“看起来不流式”。

选择建议：

  • 普通 ChatGPT 类文本流式输出：优先 SSE。
  • 需要双向控制、实时音视频、复杂 Agent 交互：选择 WebSocket。
  • 后端到后端转发、简单分块下载、内部服务流式传输：可以使用 HTTP Chunked。
  • 企业生产环境：无论选哪种，都要验证网关、Nginx、CDN、负载均衡是否会缓冲流式响应。

面试中可以这样总结：

大模型文本流式输出多数是服务端到客户端的单向推送，所以 SSE 通常最合适；如果需要双向实时控制，用 WebSocket；如果只是 HTTP 层分块传输或后端转发，可以用 HTTP Chunked。选型时还要关注代理缓冲、断线重连和连接治理。

4. 哪些大模型 API 错误可以重试？哪些错误不能重试？

判断是否重试的核心原则是：错误是否可能是临时性的，以及重试是否会造成副作用。

通常可以重试的错误包括：

  • 网络超时：连接超时、读超时、临时网络抖动。
  • 服务端 5xx 错误：例如 500、502、503、504。
  • 限流错误：例如 429，但要按服务端返回的 Retry-After 或退避策略重试。
  • 连接被中断：流式输出过程中连接断开，但要结合幂等和已输出内容处理。
  • 供应商临时不可用：可以重试同模型，也可以 fallback 到备用模型。

通常不应该重试的错误包括：

  • 鉴权失败：例如 API Key 错误、签名错误、权限不足。
  • 请求参数错误：例如模型名不存在、字段格式错误、JSON 非法。
  • 上下文超限：输入 Token 超过模型窗口，重试不会自动变好，必须裁剪上下文。
  • 内容安全拦截：请求或输出触发安全策略，直接重试通常没有意义。
  • 余额不足或配额耗尽：需要充值、扩容或切换租户预算，而不是盲目重试。
  • 业务校验失败：例如用户无权限、订单状态不允许操作。

重试策略建议：

  • 使用指数退避，例如 100ms -> 300ms -> 1s -> 3s。
  • 增加随机抖动，避免大量请求同时重试造成雪崩。
  • 设置最大重试次数和总超时时间。
  • 对流式请求要特别处理已经返回给用户的部分内容。
  • 重试前必须确认请求幂等，尤其是涉及工具调用、扣费、落库时。
  • 多次失败后进入降级，例如切换备用模型、返回简化答案或提示稍后重试。

面试中可以这样回答：

网络抖动、5xx、429、临时不可用这类瞬时错误可以有限重试；鉴权失败、参数错误、上下文超限、安全拦截、余额不足这类确定性错误不应盲目重试。重试必须配合超时、退避、抖动、幂等和降级。

5. 为什么大模型调用必须做幂等？

大模型调用必须做幂等，是因为模型调用慢、容易超时、可能重试，而且经常和业务副作用绑定。

幂等指同一个请求执行一次和执行多次，最终业务结果应该一致，不应该重复产生副作用。

如果没有幂等，大模型调用中的重试和断线恢复可能造成严重问题：

  • 重复扣费：用户点击一次生成，后端超时重试，可能产生多次模型调用费用。
  • 重复落库：同一条 AI 回复被保存多次。
  • 重复发消息：客服、邮件、短信场景可能重复通知用户。
  • 重复执行工具：Function Calling 场景下可能重复退款、重复下单、重复创建工单。
  • 状态错乱：第一次请求其实已经成功，但客户端以为失败后再次提交。

大模型场景比普通 API 更需要幂等，原因是：

  • 模型延迟高，请求更容易超时。
  • 流式输出可能中途断开，服务端和客户端对状态认知不一致。
  • 输出不完全确定，重试后内容可能不一样。
  • Agent 或工具调用链路中，一个请求可能包含多个中间步骤和外部副作用。

常见幂等设计包括：

  • 请求幂等键：客户端或服务端生成 request_id、idempotency_key。
  • 结果缓存：同一个幂等键重复请求时返回已有结果或当前执行状态。
  • 状态机控制：请求状态从 pending、running、succeeded、failed 明确流转。
  • 工具调用去重：对外部工具执行记录 tool_call_id，避免重复执行。
  • 数据库唯一约束：对订单、退款、消息发送等关键副作用加唯一键。
  • 重试只重试安全阶段：如果已经进入不可重复的业务执行阶段，要先查状态再决定。

面试中可以这样总结：

大模型调用必须幂等，因为超时、重试、流式断开和工具调用都可能导致同一请求被执行多次。没有幂等会造成重复扣费、重复落库、重复发消息甚至重复退款。生产里要用幂等键、状态机、结果缓存、唯一约束和工具调用去重来治理。

6. 大模型限流为什么不能只按 QPS 做？

大模型限流不能只按 QPS 做，因为每个请求的资源消耗差异非常大。

普通 HTTP API 的单次请求成本通常比较接近，所以 QPS 是一个重要指标。但大模型调用不同，一个请求可能只有几十 Token，也可能有几十万 Token；可能输出一句话，也可能生成一篇长报告。只看 QPS 会严重低估真实负载。

大模型限流至少要考虑这些维度：

  • QPS：每秒请求数，控制入口流量。
  • RPM：每分钟请求数，很多模型供应商按分钟限额。
  • TPM：每分钟 Token 数，包括输入和输出 Token。
  • 并发数：长生成会占用连接和推理资源，低 QPS 也可能高并发。
  • 输入 Token 数：长上下文请求更贵、更慢。
  • 最大输出 Token 数：用户设置很大的输出上限，会放大成本和延迟。
  • 租户配额：不同客户、团队、应用有不同预算。
  • 模型维度：不同模型价格、吞吐和限额不同。
  • 工具调用和 RAG 成本：一次用户请求可能触发检索、重排、多个模型调用和外部工具。

生产中的限流策略通常包括：

  • 按用户、租户、应用、模型分别限流。
  • 同时限制 QPS、RPM、TPM、并发数和预算。
  • 对超长输入或超大输出上限单独限流。
  • 对低优先级任务排队或降级。
  • 对异常调用设置熔断。
  • 做成本预估，超过预算时提前拒绝或要求用户确认。

面试中可以这样回答：

大模型请求的资源消耗和 Token 数强相关，同样一个 QPS 可能对应完全不同的成本和延迟。所以限流不能只看 QPS，还要看 RPM、TPM、并发数、输入长度、输出上限、模型类型、租户预算和工具链路消耗。

7. 模型网关通常要承担哪些能力？

模型网关是业务系统和底层模型供应商之间的统一接入层，核心目标是屏蔽模型差异、提升稳定性、控制成本并增强可观测性。

如果没有模型网关，业务代码会直接耦合不同模型厂商的 API 格式、错误码、参数、鉴权和流式协议。一旦要切模型、做 fallback、统计成本或统一限流，会非常困难。

模型网关通常承担这些能力：

  • 统一 API 协议：对业务侧提供统一的 Chat、Embedding、Rerank、Vision、Audio 等接口。
  • 模型路由：根据任务类型、租户、成本、质量和延迟选择模型。
  • Fallback 降级：主模型失败时切换备用模型，或返回降级结果。
  • 限流与配额：按用户、租户、应用、模型做 QPS、TPM、并发和预算控制。
  • Token 预算管理：估算输入输出 Token，提前拦截超限请求。
  • Prompt 模板管理：统一管理系统提示词、版本、变量和灰度。
  • 重试、超时、熔断：治理模型调用的不稳定性。
  • 流式协议适配：对接不同厂商的流式返回格式，统一输出给前端。
  • 结构化输出适配：统一 JSON Schema、Function Calling、工具调用格式。
  • 安全治理：做敏感词、隐私数据脱敏、内容安全、越权检查。
  • 日志与 Trace：记录完整调用链、模型版本、Token、延迟、错误和中间步骤。
  • 成本归因：按用户、团队、应用、功能模块统计费用。
  • 评测与灰度：支持模型 A/B 测试、Prompt 版本对比和线上采样评估。
  • 缓存：对可缓存的确定性结果做语义缓存或请求缓存。

面试中可以这样总结：

模型网关负责把大模型从“一个 API”治理成“一个可生产使用的能力层”。它通常承担统一协议、模型路由、fallback、限流、Token 预算、Prompt 管理、重试熔断、流式适配、安全治理、日志观测、成本归因和评测灰度。

8. AI 应用的调用日志里至少要记录哪些字段？

AI 应用调用日志的目标不是只排查接口错误，还要支持质量分析、成本归因、安全审计和评测回放。

至少应该记录这些字段：

  • 请求标识：request_id、trace_id、session_id、message_id。
  • 用户与租户信息：用户 ID、租户 ID、应用 ID、渠道、权限角色。
  • 模型信息：模型供应商、模型名称、模型版本、网关路由结果。
  • Prompt 信息：Prompt 模板 ID、模板版本、系统提示词版本、参数变量。
  • 输入摘要：用户问题、上下文摘要、RAG 文档 ID、工具结果摘要。
  • Token 消耗：输入 Token、输出 Token、总 Token、缓存命中 Token。
  • 成本信息：本次调用费用、计费模型、所属业务模块。
  • 延迟指标：请求开始时间、首 Token 时间、总耗时、模型耗时、检索耗时、工具耗时。
  • 调用参数：Temperature、Top-P、最大输出 Token、是否流式。
  • 返回状态：成功或失败、错误码、错误类型、重试次数、fallback 信息。
  • 输出摘要：模型回答、结构化解析结果、引用来源、是否被安全过滤。
  • 工具调用记录：工具名称、参数摘要、执行状态、耗时、错误信息、幂等键。
  • RAG 记录：query、召回文档 ID、chunk ID、score、rerank 结果。
  • 安全与合规字段：脱敏状态、内容安全结果、是否命中敏感策略。
  • 用户反馈：点赞、点踩、人工标注、投诉、是否解决问题。

需要注意的是，日志不能无脑记录所有原文：

  • 用户输入和模型输出可能包含隐私、商业秘密或敏感数据。
  • 应对敏感字段做脱敏、加密或访问控制。
  • 高风险业务要有审计日志，但普通开发人员不应随意查看完整内容。
  • 日志保留周期要符合公司安全和合规要求。

面试中可以这样回答：

AI 调用日志至少要能回答四个问题：谁在什么时候调用了哪个模型，输入输出和上下文是什么，消耗了多少 Token 和成本，结果是否成功以及质量如何。所以要记录请求 ID、用户租户、模型版本、Prompt 版本、Token、成本、延迟、错误、重试、RAG 证据、工具调用、安全结果和用户反馈。同时要注意隐私脱敏和权限控制。

结构化输出与工具调用相关面试题

1. 为什么只写“请返回 JSON”不可靠？

只在 Prompt 里写“请返回 JSON”不可靠，因为这只是自然语言约束，不是强约束。 大模型仍然是在生成文本，而不是在执行 JSON 序列化函数。

常见不可靠表现包括：

  • 输出前后夹杂解释性文本，例如“下面是 JSON：”。
  • JSON 语法错误，例如少逗号、少引号、多尾逗号。
  • 字段名不稳定，例如一会儿叫 user_name，一会儿叫 username。
  • 字段类型不稳定，例如本应是数组，结果返回字符串。
  • 必填字段缺失，或者多出业务不接受的字段。
  • 枚举值不受控，例如状态本应是 pending、success、failed，结果返回 done。
  • 模型拒答、安全拦截、上下文截断时，返回内容可能根本不是目标 JSON。

在生产环境中，这会带来三个问题：

  • 解析不稳定：后端 JSON.parse 可能失败。
  • 业务不稳定：即使 JSON 能解析，也不一定符合业务字段要求。
  • 安全不稳定：模型可能输出多余字段、伪造参数或绕过业务限制。

更稳的做法是：

  • 使用 JSON Mode 保证输出是合法 JSON。
  • 使用 Structured Outputs 或 JSON Schema 约束字段结构。
  • 对模型输出做服务端校验，不信任模型原始输出。
  • 校验失败后进入重试、修复、降级或人工处理流程。

面试中可以这样总结：

“请返回 JSON”只是 Prompt 约束，不能保证语法、字段、类型和业务语义都正确。生产环境要用 JSON Mode、Structured Outputs、JSON Schema、服务端校验和失败兜底来保证稳定性。

2. JSON Mode 和 Structured Outputs 有什么区别？

JSON Mode 解决的是“是不是合法 JSON”的问题，Structured Outputs 解决的是“是不是符合指定 Schema”的问题。

JSON Mode 的特点：

  • 保证模型输出尽量是合法 JSON。
  • 适合只需要可解析 JSON，但字段结构不复杂的场景。
  • 不保证字段名、字段类型、必填项、枚举值符合业务要求。
  • 即使开启 JSON Mode，仍然需要在 Prompt 中明确要求输出 JSON。
  • 仍然要处理输出不完整、被截断、拒答等边界情况。

Structured Outputs 的特点：

  • 基于 JSON Schema 约束输出结构。
  • 不仅要求 JSON 合法，还要求字段符合 Schema。
  • 可以约束对象、数组、类型、必填字段、枚举值、嵌套结构等。
  • 更适合结构化抽取、表单生成、分类结果、业务参数生成等场景。
  • 通常比单纯 JSON Mode 更适合生产系统。

面试中可以这样回答：

JSON Mode 只保证输出能被当作 JSON 解析，Structured Outputs 则进一步保证输出符合 JSON Schema。生产中只要有稳定字段、类型、枚举或必填项要求，就优先使用 Structured Outputs，而不是只依赖 JSON Mode。

3. JSON Schema 在大模型应用里解决什么问题？

JSON Schema 在大模型应用里解决的是“模型输出和业务系统之间的契约问题”。

大模型擅长生成自然语言，但业务系统需要稳定、可校验、可落库、可调用的结构化数据。JSON Schema 就是把输出格式从“口头约定”变成“机器可校验的契约”。

它主要解决这些问题：

  • 字段稳定性：规定必须返回哪些字段，字段名是什么。
  • 类型稳定性：规定字段是字符串、数字、布尔值、数组还是对象。
  • 枚举约束：规定状态、分类、意图只能取指定值。
  • 嵌套结构约束：规定复杂对象、数组元素的结构。
  • 缺省和必填控制：区分哪些字段必须有，哪些字段可选。
  • 禁止多余字段：避免模型输出业务系统不认识的字段。
  • 自动校验：后端可以用标准 JSON Schema 校验器做程序化验证。
  • 跨团队协作：前端、后端、模型服务可以围绕同一份 Schema 开发。

常见应用场景包括：

  • 简历信息抽取。
  • 发票、合同、病历等文档结构化。
  • 意图识别和槽位抽取。
  • 工单分类和优先级判断。
  • 生成可执行工具参数。
  • 生成前端 UI 所需的数据结构。

需要注意的是，JSON Schema 解决的是结构约束，不等于事实正确：

  • Schema 可以保证 price 是数字，但不能保证价格一定真实。
  • Schema 可以保证 city 是字符串，但不能保证城市一定存在。
  • Schema 可以保证 action 在枚举里，但不能保证这个动作一定安全。

面试中可以这样总结：

JSON Schema 是大模型输出和业务系统之间的结构化契约，它把“希望模型这样输出”变成“系统可以校验的格式规则”。它能提升字段、类型、枚举和嵌套结构的稳定性，但事实正确性和业务安全仍然需要额外校验。

4. Function Calling 的完整链路是什么？

Function Calling 是让模型在需要外部数据或能力时，生成一个工具调用请求，由应用执行工具，再把工具结果交回模型生成最终回答。

完整链路通常是：

举例：用户问“我上一个订单到哪了？”

  • 模型不应该凭空回答订单状态。
  • 应用提供 get_order_status(order_id) 工具。
  • 模型识别需要查订单，生成工具调用参数。
  • 后端校验用户是否有权限查询该订单。
  • 后端调用订单系统拿到物流状态。
  • 模型再把结果组织成自然语言回复。

工程上要特别注意：

  • 模型只负责“建议调用哪个函数、传什么参数”，不应该直接拥有业务权限。
  • 应用必须校验参数，不能直接信任模型生成的参数。
  • 工具执行需要超时、重试、幂等和审计。
  • 工具结果也可能很长，需要摘要或字段裁剪。
  • 一个任务可能需要多轮工具调用，直到模型得到足够信息。

面试中可以这样回答：

Function Calling 的链路是：注册函数 Schema，模型选择函数并生成参数，应用校验后执行真实函数，再把执行结果回传给模型，模型基于结果生成最终回答。关键点是模型不直接执行业务动作，真正执行和安全校验都在应用侧。

5. Function Calling 和 MCP 有什么区别？

Function Calling 是模型调用应用侧函数的一种 API 能力；MCP 是连接大模型客户端和外部工具、资源的开放协议。

二者的区别可以从几个维度理解：

  • 抽象层级不同：Function Calling 更像一次模型 API 请求中的工具调用机制；MCP 更像工具和资源接入的协议标准。
  • 管理范围不同：Function Calling 通常由应用在请求里显式声明函数；MCP Server 可以统一暴露一组工具、资源、提示词和元数据。
  • 集成方式不同：Function Calling 常直接绑定应用代码或后端 API；MCP 通过 MCP Client 和 MCP Server 通信，适合把外部系统标准化接入给不同 Agent 或模型客户端。
  • 复用能力不同：Function Calling 往往服务于某个应用；MCP Server 可以被多个客户端复用，例如 IDE Agent、桌面 Agent、ChatGPT App 或内部 Agent 平台。
  • 能力范围不同：Function Calling 主要是工具调用；MCP 除工具外，还可以提供资源、Prompt 模板、初始化指令、工具元数据等。

可以这样类比：

二者也可以组合：

  • 模型通过工具调用机制决定要用某个能力。
  • 这个能力背后可能来自 MCP Server。
  • 应用侧仍然要做权限、审计、参数校验和安全控制。

面试中可以这样总结：

Function Calling 是模型调用函数的机制，MCP 是把外部工具和资源标准化暴露给 Agent 的协议。Function Calling 偏单次应用集成，MCP 偏工具生态和跨客户端复用；两者不是替代关系，可以一起使用。

6. MCP Tool 和普通 HTTP API 有什么关系？

MCP Tool 往往是普通 HTTP API、数据库、文件系统或内部服务之上的一层 Agent 友好封装。

普通 HTTP API 是面向程序员和业务系统的接口，通常关心 URL、方法、Header、认证、请求体和响应体。MCP Tool 是面向模型或 Agent 的工具描述，重点是让模型知道：

  • 这个工具能做什么。
  • 什么时候该用它。
  • 输入参数 Schema 是什么。
  • 输出结果结构是什么。
  • 是否有副作用。
  • 是否需要用户确认。
  • 权限、速率限制和安全边界是什么。

关系可以这样理解：

例如一个 create_refund MCP Tool 背后可能调用公司内部退款 HTTP API：

  • MCP Tool 对模型暴露的是“创建退款”这个语义化能力。
  • MCP Server 负责参数校验、鉴权、日志、幂等和调用退款 API。
  • 内部 HTTP API 仍然是最终业务执行者。

MCP Tool 相比直接把 HTTP API 给模型，有几个优势：

  • 对模型更友好，减少 URL、Header、协议细节。
  • 可以把多个底层 API 编排成一个高层工具。
  • 可以统一做权限、安全、审计和确认流程。
  • 可以标准化工具发现、调用和结果返回。
  • 可以在不同 Agent 客户端之间复用。

面试中可以这样回答：

MCP Tool 通常不是替代 HTTP API，而是把 HTTP API 等底层能力包装成模型可发现、可理解、可调用的工具接口。HTTP API 负责业务实现，MCP Tool 负责面向 Agent 的语义描述、协议适配和安全治理。

7. Agent Skill 和 Function Calling 是一回事吗？

Agent Skill 和 Function Calling 不是一回事。Skill 更偏“可复用工作流和领域知识包”，Function Calling 更偏“模型调用外部函数的执行机制”。

Agent Skill 通常包含：

  • SKILL.md 说明文件。
  • 适用场景描述。
  • 工作流程步骤。
  • Prompt 规范。
  • 示例和参考文档。
  • 可选脚本、模板、资源文件。

它解决的是“Agent 遇到某类任务时应该怎么做”的问题。例如：

  • 如何做代码评审。
  • 如何生成一份符合公司风格的 PPT。
  • 如何处理某类 GitHub PR 评论。
  • 如何按照团队规范发布版本。

Function Calling 解决的是“模型如何调用某个确定的外部函数”的问题。例如：

  • 查询订单。
  • 创建工单。
  • 调用天气 API。
  • 执行数据库检索。
  • 调用支付、退款、库存等业务接口。

两者可以配合：

  • Skill 定义完整工作流，例如“处理退款咨询”。
  • 工作流中某一步需要调用 query_order 或 create_refund。
  • 这一步可以通过 Function Calling 或 MCP Tool 执行。

面试中可以这样总结：

Skill 是可复用的任务流程、知识和资源包，告诉 Agent 怎么做一类任务；Function Calling 是模型调用外部函数的机制，帮助 Agent 获取数据或执行动作。Skill 可以编排 Function Calling，但二者不是同一个概念。

8. 结构化输出失败后怎么处理？

结构化输出失败后不能直接把错误暴露给用户，也不能盲目继续执行业务动作，而要进入可控的修复和兜底流程。

常见失败类型包括：

  • JSON 解析失败。
  • 不符合 JSON Schema。
  • 缺少必填字段。
  • 字段类型错误。
  • 枚举值非法。
  • 输出被截断。
  • 模型拒答或返回安全说明。
  • 内容虽然结构正确，但业务校验失败。

处理流程可以分层：

常见处理策略：

  • 自动修复：对轻微格式问题，可以让模型基于错误信息重新输出。
  • 有限重试：带上校验错误，要求模型只修正结构，不改变语义。
  • 降级返回：如果结构化结果不可靠，返回普通文本或提示用户补充信息。
  • 默认值兜底：对低风险可选字段使用默认值，但不能对关键字段乱填。
  • 人工审核：高风险场景，例如金融、医疗、法律、退款、发货，失败后进入人工。
  • 阻断执行：如果工具参数校验失败，绝不能继续调用真实业务 API。
  • 日志记录：记录失败原因、模型版本、Prompt 版本、原始输出和重试次数。
  • 离线评测：把失败样本加入评测集，优化 Schema、Prompt 或模型选择。

需要注意：

  • 重试次数要有限，避免成本失控。
  • 不能让模型自己决定是否绕过 Schema。
  • 不要为了通过校验而把错误数据强行补齐。
  • 业务动作必须在结构、权限和安全校验全部通过后才执行。

面试中可以这样回答：

结构化输出失败后，要按解析校验、Schema 校验、业务校验、安全校验分层处理。能修复就带错误信息有限重试，不能修复就降级或人工处理；涉及工具调用和业务副作用时，校验失败必须阻断执行。

9. 工具调用为什么必须做安全治理？

工具调用必须做安全治理，因为它把模型从“生成文本”升级成了“能够访问数据和执行动作”的系统组件。

如果没有安全治理，风险会从“答错话”扩大到“做错事”。

主要风险包括：

  • 越权访问：模型调用工具查询了用户无权访问的数据。
  • 参数伪造：模型生成了不属于当前用户的 order_id、user_id、account_id。
  • 重复执行：重试或多轮调用导致重复下单、重复扣费、重复发消息。
  • Prompt Injection：外部文档或网页中的恶意指令诱导模型调用敏感工具。
  • 数据泄露：工具结果包含隐私、密钥、内部字段，被模型输出给用户。
  • 高危动作误执行：删除数据、转账、退款、发货、发邮件等动作被错误触发。
  • 供应链风险：第三方 MCP Server 或外部工具可能改变行为或收集数据。
  • 审计缺失：无法追踪谁在何时通过模型触发了什么动作。

安全治理措施包括：

  • 最小权限：工具只暴露当前任务需要的能力。
  • 服务端鉴权：不要相信模型传来的用户 ID 和权限信息。
  • 参数校验：所有工具参数都要做类型、范围、枚举和业务规则校验。
  • 幂等控制：对有副作用的工具使用幂等键和状态机。
  • 用户确认：高风险动作必须让用户显式确认。
  • 工具分级：只读工具、低风险写工具、高风险写工具分别治理。
  • 敏感数据脱敏：工具结果返回给模型前先裁剪和脱敏。
  • Prompt Injection 防护：外部内容只当数据，不当指令；必要时隔离不可信内容。
  • 审计日志：记录工具名、参数摘要、调用人、权限、结果、耗时和审批记录。
  • Allowlist：只允许调用白名单工具和可信 MCP Server。

面试中可以这样总结：

工具调用让模型具备访问数据和执行动作的能力，所以安全边界必须从 Prompt 层下沉到服务端。必须做权限校验、参数校验、幂等、用户确认、脱敏、审计和 Prompt Injection 防护，否则模型错误可能直接变成业务事故。

10. 面试里怎么一句话概括结构化输出？

可以这样概括：

结构化输出就是用 JSON Schema、工具参数 Schema 或类似机制，把大模型的自然语言生成约束成业务系统可解析、可校验、可执行的稳定数据结构。

如果想更偏工程实践，可以这样说：

结构化输出的核心不是“让模型看起来像 JSON”，而是把模型输出变成可以被程序校验、失败可兜底、业务可消费的数据契约。

如果想更偏面试精简版，可以这样说：

结构化输出是连接大模型和传统软件系统的接口契约。

AI 应用评测相关面试题

1. 为什么不能只靠公开 benchmark 评估 AI 应用质量？

不能只靠公开 benchmark 评估 AI 应用质量，因为公开 benchmark 评估的是模型通用能力，而 AI 应用质量取决于具体业务链路。

公开 benchmark 通常适合比较模型在数学、代码、知识问答、推理、多语言等通用任务上的能力，例如模型 A 是否整体比模型 B 更强。但一个真实 AI 应用的效果，不只由基础模型决定，还受到 Prompt、RAG、工具调用、业务规则、权限控制、上下文拼接、输出格式、延迟和成本等因素影响。

公开 benchmark 的局限包括：

  • 任务不匹配：公开题目不一定覆盖你的业务问题、用户语言和真实场景。
  • 数据分布不同：线上用户问法、噪声、错别字、领域术语和上下文复杂度不同。
  • 无法评估业务规则：例如是否遵守公司政策、权限边界、产品口径。
  • 无法评估端到端链路：RAG 检索、工具调用、结构化输出、后处理都不在模型 benchmark 里。
  • 无法衡量用户体验：首字延迟、失败率、拒答率、交互轮次、可解释性也很重要。
  • 可能存在数据污染：部分公开 benchmark 可能已经出现在模型训练数据里。
  • 不能代表成本收益：一个 benchmark 分数高的模型，不一定在业务场景中性价比最好。

真实 AI 应用更应该建立自己的业务评测体系：

  • 用公开 benchmark 判断模型基础能力上限。
  • 用业务 Golden Set 判断应用在核心场景的质量。
  • 用 Trace 回放评估真实链路变化。
  • 用线上灰度评估真实用户体验和风险。
  • 用成本、延迟、稳定性、安全性等指标做综合决策。

面试中可以这样总结：

公开 benchmark 只能说明模型的通用能力，不能代表一个 AI 应用的端到端质量。AI 应用要评估的是“模型加 Prompt、RAG、工具、业务规则和用户体验”的整体效果，所以必须建立业务评测集和线上评测闭环。

2. Golden Set 应该怎么构建？冷启动阶段没有生产日志怎么办？

Golden Set 是一组高质量、可复用、带标准答案或评价标准的业务评测样本，用来稳定衡量 AI 应用质量。

构建 Golden Set 的核心不是样本越多越好，而是覆盖关键场景、边界问题和高风险问题。

一个好的 Golden Set 通常包括：

  • 真实用户问题：来自线上日志、客服工单、搜索词、销售对话等。
  • 核心业务场景：覆盖最高频、最高价值、最高风险的任务。
  • 边界样本：信息不足、歧义问题、错误前提、越权请求、超长输入。
  • 负样本：模型应该拒答、追问或说明无法判断的问题。
  • 标准答案：可以是唯一答案、参考答案、评分 Rubric 或关键点列表。
  • 证据来源：特别是 RAG 场景，要标注答案应依据哪些文档或字段。
  • 元数据：场景类型、难度、风险等级、语言、租户、产品线、期望行为。

构建流程可以是：

冷启动阶段没有生产日志，可以从这些来源构建：

  • 产品需求文档、帮助中心、FAQ、客服知识库。
  • 历史人工客服工单或销售问答。
  • 业务专家整理的高频问题和高风险问题。
  • 竞品或公开论坛中相似用户问题，但要注意合规和脱敏。
  • 基于真实文档由人工生成问题。
  • 让大模型辅助生成候选问题，再由业务专家筛选和修正。
  • 做小规模内测或灰度，收集第一批真实 Trace。

冷启动时要特别注意：

  • 不能完全依赖大模型自动生成 Golden Set，否则容易和模型偏好同源。
  • 要优先覆盖核心路径，而不是追求样本量。
  • 要把“应该拒答或追问”的样本纳入评测。
  • Golden Set 要版本化，避免每次评测样本变化导致结果不可比。

面试中可以这样回答：

Golden Set 要来自真实业务或高可信业务假设，覆盖高频、高价值、高风险和边界场景，并带有标准答案、证据或评分 Rubric。冷启动没有日志时，可以从 PRD、FAQ、客服工单、业务专家和人工构造样本开始，但要专家审核、脱敏、分层和版本化。

3. LLM-as-Judge 有哪些主要偏差？怎么缓解？

LLM-as-Judge 是用大模型作为裁判来评价模型输出质量，但它本身也会有偏差，不能无条件当作真值。

主要偏差包括：

  • 位置偏差：对先出现或后出现的答案有偏好。
  • 长度偏差：倾向给更长、更详细、看起来更完整的答案高分。
  • 表达偏差：偏好语言流畅、格式漂亮的答案，即使事实不一定更正确。
  • 自我偏好：某些 Judge 模型可能偏好和自己风格相似的答案。
  • 品牌或模型偏见：如果知道候选模型名称，可能影响判断。
  • 宽松偏差：对看似合理但缺少证据的回答给高分。
  • 事实核查不足：Judge 如果没有证据，也可能无法判断答案真假。
  • Rubric 理解偏差：评分标准写得模糊时，Judge 会按自己的理解打分。
  • 随机性偏差：同一问题多次评分可能不完全一致。

缓解方法包括：

  • 隐藏模型名称，避免品牌偏见。
  • 随机打乱答案顺序，降低位置偏差。
  • 使用明确 Rubric，把正确性、完整性、引用、格式、安全性分开评分。
  • 要求基于证据评分，特别是 RAG 场景给 Judge 提供标准证据。
  • 使用 pairwise 比较，让 Judge 比较两个答案哪个更好，而不是直接打绝对分。
  • 多 Judge 投票，使用多个模型或多次评分取一致性。
  • 校准人工标注集，定期比较 Judge 和人工的一致性。
  • 控制输出长度影响，在 Rubric 中明确“不因答案更长而加分”。
  • 记录 Judge 版本，避免 Judge 模型升级导致评测不可比。

面试中可以这样总结：

LLM-as-Judge 高效但有位置、长度、表达、自我偏好和事实核查不足等偏差。缓解方式是匿名、随机顺序、明确 Rubric、基于证据评分、多 Judge 投票、人工校准和版本固定。它适合做规模化辅助评测，但不能完全替代人工评测。

4. RAG 评测为什么必须分检索和生成两段？

RAG 评测必须分检索和生成两段，因为答案错误可能来自检索失败，也可能来自生成失败。

如果只看最终答案，很难定位问题。例如用户问一个制度条款，模型答错了，可能有两种完全不同的原因：

  • 检索阶段没有召回正确文档。
  • 检索召回了正确文档，但生成阶段没有正确使用证据。

这两类问题的修复方式完全不同：

  • 检索失败要优化切分、向量模型、关键词召回、混合检索、重排序、权限过滤。
  • 生成失败要优化 Prompt、证据排序、引用格式、上下文压缩、回答约束。

检索阶段常见指标包括：

  • Recall@K：正确文档是否出现在前 K 个结果里。
  • Precision@K：前 K 个结果中有多少是相关的。
  • MRR：第一个正确结果排在多靠前。
  • nDCG：相关文档的排序质量。
  • 权限正确率：是否只召回用户有权限看的内容。
  • 证据覆盖率：回答所需关键证据是否被召回。

生成阶段常见指标包括：

  • 答案正确性：是否基于证据回答正确。
  • 忠实性：是否只依据检索证据，不编造。
  • 引用准确率：引用是否真实支持答案。
  • 完整性：是否覆盖问题所需关键点。
  • 拒答正确率：证据不足时是否拒答或说明无法判断。
  • 格式合规率：是否符合结构化输出或业务格式。

面试中可以这样回答：

RAG 是“先找证据，再基于证据生成答案”的两段式系统。最终答案错了，可能是没找到证据，也可能是找到了但没用好。只有把检索和生成分开评测，才能定位问题并选择正确优化方向。

5. Agent 评测为什么比普通问答和 RAG 更复杂？

Agent 评测更复杂，因为 Agent 不只是回答问题，而是在多步骤过程中做计划、调用工具、观察结果、调整策略并可能执行有副作用的动作。

普通问答主要评估最终答案是否正确。RAG 还要评估检索和生成。Agent 则需要评估整个执行轨迹。

Agent 的复杂性体现在：

  • 多步骤决策：Agent 需要决定先做什么、后做什么。
  • 工具选择：要判断是否调用工具、调用哪个工具。
  • 参数生成：工具参数必须正确、安全、符合权限。
  • 环境反馈：工具结果可能失败、延迟、为空或格式异常。
  • 状态管理：多轮任务中要记住目标、约束和中间结果。
  • 非确定性更强：同一个任务可能走不同路径，最终都可能成功。
  • 副作用风险：可能发邮件、下单、退款、修改文件或数据库。
  • 长链路误差累积：前一步小错误可能导致后面全部偏离。
  • 评价标准多元：不仅看最终答案，还看过程是否安全、高效、可解释。

Agent 评测通常要看这些维度：

  • 任务是否完成。
  • 工具调用顺序是否合理。
  • 工具选择是否必要。
  • 参数是否正确。
  • 是否遵守权限和安全策略。
  • 是否正确处理工具失败。
  • 是否避免不必要的高成本调用。
  • 是否产生可接受的副作用。
  • 最终回答是否如实反映执行结果。

常见评测方法包括：

  • 使用模拟环境或沙箱，避免真实副作用。
  • 回放 Trace，评估每一步决策。
  • 对工具调用做断言，例如必须调用或不能调用某工具。
  • 评估最终状态，而不只评估最终文本。
  • 为高风险动作增加人工审批评测。

面试中可以这样总结：

Agent 评测比问答和 RAG 更复杂，因为它要评估计划、工具选择、参数、安全、状态、异常处理、成本和最终结果。Agent 的质量不只体现在最后一句话，还体现在整个执行轨迹是否正确、可靠、可控。

6. 离线评测、Trace 回放、线上灰度分别解决什么问题？

离线评测、Trace 回放和线上灰度分别对应研发流程中的不同阶段：改动前快速判断、用真实链路复现、在真实流量中验证。

离线评测解决的是“改动是否大概率变好”的问题。

特点：

  • 基于 Golden Set 或固定测试集。
  • 适合比较模型、Prompt、参数、RAG 策略。
  • 成本可控、速度快、可重复。
  • 不影响真实用户。
  • 缺点是不能完全代表线上分布。

适用场景：

  • Prompt 改版前。
  • 模型升级前。
  • RAG 切分或重排序策略变更前。
  • 结构化输出 Schema 调整前。

Trace 回放解决的是“真实历史请求在新系统下会怎样”的问题。

特点：

  • 使用线上真实请求链路的记录。
  • 可以重放用户问题、上下文、检索结果、工具调用结果或完整 Trace。
  • 更接近真实分布。
  • 适合发现改动对历史问题的影响。
  • 缺点是需要做好脱敏、版本控制和外部工具 mock。

适用场景：

  • 回归测试线上失败案例。
  • 比较新旧 Prompt 在真实问题上的差异。
  • Agent 工具链升级前验证。
  • RAG 知识库或检索策略变更后回放。

线上灰度解决的是“真实用户环境下是否真的更好”的问题。

特点：

  • 在小比例真实流量中验证。
  • 可以观察真实用户反馈、点击、追问、转人工、投诉、留存等指标。
  • 能发现离线评测覆盖不到的问题。
  • 风险更高，需要监控、回滚和分流策略。

适用场景：

  • 模型升级上线。
  • 新 Agent 能力上线。
  • 新检索策略上线。
  • 新工具调用能力上线。

三者关系可以概括为：

面试中可以这样回答：

离线评测用于研发阶段快速比较方案，Trace 回放用于用真实历史请求做回归验证，线上灰度用于在真实用户环境中验证效果、风险和业务指标。三者是递进关系，不是互相替代。

7. CI 里的 AI 评测如何平衡速度和覆盖度？

CI 里的 AI 评测要分层设计，用少量高价值用例做快速阻断，用更大规模评测放到异步或定时任务中。

AI 评测通常比普通单元测试慢、贵、不稳定。如果把所有评测都放进每次 CI，会导致：

  • 构建时间过长。
  • Token 成本过高。
  • 外部模型抖动导致误报。
  • 开发者不愿意频繁运行。

比较合理的分层策略是：

  • PR 快速评测：只跑少量核心 Golden Set、关键安全样本和结构化输出样本。
  • 模块级评测：改了 RAG 就跑检索评测，改了 Prompt 就跑相关任务集，改了工具就跑工具调用断言。
  • 夜间全量评测：跑更大的 Golden Set、Trace 回放和多模型对比。
  • 发布前评测：跑完整回归、成本评估、延迟评估和安全评测。
  • 线上监控：上线后持续监控真实指标和失败样本。

CI 中适合做强阻断的指标：

  • JSON Schema 合规率。
  • 安全策略命中是否正确。
  • 工具调用参数是否通过校验。
  • 不该调用工具时是否没有调用。
  • 必须拒答的问题是否拒答。
  • 核心高风险样本是否通过。

CI 中不适合过度依赖的指标：

  • 大规模 LLM-as-Judge 平均分。
  • 对开放式文本的细微偏好判断。
  • 对低风险文案质量的主观评分。

实用优化方法：

  • 固定模型版本和参数。
  • 缓存稳定样本结果。
  • 对测试集做分层抽样。
  • 将失败样本优先加入快速集。
  • 设置容忍区间，而不是单次分数微小波动就失败。
  • 对关键结构化任务使用程序化断言，减少 Judge 成本。

面试中可以这样总结：

CI 里的 AI 评测要分层：PR 阶段跑小而关键的快速集，主要阻断结构化、安全和高风险回归；夜间或发布前跑大规模 Golden Set 和 Trace 回放。这样既保证速度，又能维持覆盖度和质量信心。

8. 如果 LLM-as-Judge 和人工评测结果不一致，应该怎么处理？

LLM-as-Judge 和人工评测不一致时，不能简单认为某一方一定错，而要把它当作评测体系需要校准的信号。

处理步骤可以是：

常见原因包括：

  • Rubric 不清晰：人工和 Judge 对“好答案”的理解不同。
  • Judge 没有足够证据：人工知道业务背景，但 Judge 不知道。
  • 人工标注不一致：不同标注员标准不同，甚至人工也可能错。
  • Judge 偏好长答案或漂亮格式：忽略事实错误或引用不足。
  • 样本本身有歧义：问题可能允许多个合理答案。
  • 业务规则变化：人工按新规则评，Judge Prompt 还是旧规则。

处理原则：

  • 高风险和关键业务指标以人工专家评审为最终标准。
  • 对大规模低风险样本，可以用 Judge 做辅助筛选。
  • 建立人工和 Judge 的一致性指标，例如 agreement rate 或 Cohen’s kappa。
  • 定期用人工标注集校准 Judge Prompt 和评分阈值。
  • 对不一致样本分类沉淀，反向改进 Rubric。
  • 不要让 Judge 评价它没有证据判断的事实问题。

如果最终确认是 Judge 错了：

  • 优化 Judge Prompt。
  • 给 Judge 补充证据和评分规则。
  • 改成 pairwise 比较或多 Judge 投票。
  • 降低该类指标的自动化权重。

如果最终确认是人工评测不稳定：

  • 细化标注指南。
  • 增加标注员培训。
  • 引入双人标注和专家仲裁。
  • 把典型样本加入标注规范。

面试中可以这样回答：

LLM-as-Judge 和人工不一致时，要先定位样本和原因，检查 Rubric、证据和标注标准。高风险场景以人工专家为准，同时用不一致样本校准 Judge Prompt、评分规则和人工标注指南。Judge 是规模化辅助评测工具，不是绝对真值。
