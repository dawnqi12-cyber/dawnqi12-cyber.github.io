AI Agent 相关面试题

一、Agent 基础

1. AI Agent 是什么？和普通 Chatbot 有什么区别？

AI Agent 是一种能够围绕目标进行感知、推理、规划、调用工具、执行动作并根据反馈调整行为的 AI 系统。 它不只是回答问题，而是尝试完成任务。

普通 Chatbot 更像“问答系统”：

  • 用户问一句，模型答一句。
  • 主要输出自然语言。
  • 很少主动拆解任务。
  • 很少操作外部系统。
  • 通常不维护复杂任务状态。

Agent 更像“任务执行系统”：

  • 能理解目标，而不只是响应一句话。
  • 能拆解步骤和制定计划。
  • 能调用搜索、数据库、代码执行、文件系统、业务 API 等工具。
  • 能根据工具结果继续决策。
  • 能维护短期状态和长期记忆。
  • 能在失败后重试、修正或换路径。

面试中可以这样回答：

Chatbot 的核心是对话生成，Agent 的核心是目标驱动的行动闭环。Agent 不仅会说，还会计划、用工具、观察结果并持续推进任务。

2. Agent = LLM + Planning + Memory + Tools 这条公式怎么理解？

这条公式可以理解为 Agent 的核心能力拆解：

LLM 是推理和语言理解核心。 它负责理解用户意图、生成计划、选择工具、解释结果和输出答案。

Planning 是任务拆解能力。 它把复杂目标拆成多个可执行步骤，例如先查资料、再分析、再生成报告、最后校验。

Memory 是状态和经验管理能力。 短期记忆记录当前任务上下文，长期记忆沉淀用户偏好、项目规范、历史经验和可复用事实。

Tools 是连接外部世界的能力。 工具让 Agent 能查数据库、读文件、调用 API、运行代码、搜索网页或操作业务系统。

需要注意，这个公式不是说把四个组件简单拼起来就一定是好 Agent。生产级 Agent 还需要：

  • 权限控制。
  • 工具安全治理。
  • 状态管理。
  • 错误恢复。
  • 评测系统。
  • 成本和延迟控制。
  • 可观测性和审计。

面试中可以这样总结：

LLM 提供理解和推理，Planning 负责拆解任务，Memory 负责保留上下文和经验，Tools 负责连接外部能力。真正的 Agent 是这几部分在一个受控执行闭环里的组合。

3. Agent Loop 的完整流程是什么？

Agent Loop 是 Agent 持续推进任务的核心执行循环。 它通常不是一次模型调用完成，而是多轮“思考、行动、观察、调整”的过程。

完整流程可以描述为：

关键环节包括：

  • Goal：明确用户要完成什么。
  • Context：把任务说明、规则、历史、工具、记忆和外部数据组织进上下文。
  • Reasoning：模型判断下一步该做什么。
  • Action：调用工具、查询信息、写文件、执行代码或请求用户确认。
  • Observation：读取工具返回结果。
  • State Update：更新任务状态、失败原因、已完成步骤和待办事项。
  • Stop Condition：判断任务完成、失败、超时、超预算或需要人工介入。

面试中可以这样回答：

Agent Loop 是“目标、思考、行动、观察、更新、判断是否结束”的循环。它让 Agent 能根据环境反馈持续调整，而不是一次性生成答案。

4. Agent 和传统编程、Workflow 的核心区别是什么？

传统编程强调确定性控制流，Workflow 强调预定义流程编排，Agent 强调在目标约束下动态决策。

传统编程的特点：

  • 分支逻辑由开发者写死。
  • 输入输出相对确定。
  • 更容易测试和追踪。
  • 适合规则清晰、状态明确、风险可控的任务。

Workflow 的特点：

  • 流程节点和边基本预先定义。
  • 可以包含条件分支、重试、人工审批。
  • 适合业务流程明确但步骤较多的场景。
  • 可控性强，适合生产系统。

Agent 的特点：

  • 不完全预定义每一步。
  • 模型会根据当前状态选择下一步。
  • 能处理开放问题和未知路径。
  • 灵活性更强，但不确定性、成本和安全风险也更高。

实际工程中不是三选一，而是组合：

  • 规则明确的部分用传统代码。
  • 流程稳定的部分用 Workflow。
  • 开放探索和复杂判断的部分用 Agent。

面试中可以这样总结：

传统编程是开发者写好每一步，Workflow 是预先编排流程，Agent 是让模型在约束下动态决定下一步。生产里通常用 Workflow 包住 Agent，而不是把所有逻辑都交给 Agent。

5. ReAct、Plan-and-Execute、Reflection、Multi-Agent 分别适合什么场景？

ReAct 适合边思考边调用工具的任务。 它把 Reasoning 和 Acting 结合起来，让模型每一步先判断，再调用工具，再根据观察结果继续。适合搜索问答、代码排查、数据查询、工具辅助分析等场景。

Plan-and-Execute 适合目标明确但步骤较多的任务。 它先生成整体计划，再逐步执行。适合报告生成、数据分析、项目迁移、复杂代码修改等任务。优点是全局性更好，缺点是计划可能需要动态调整。

Reflection 适合需要自我检查和迭代改进的任务。 它让模型在生成结果后反思错误、检查遗漏、修正答案。适合代码生成、写作、评测反馈、自我调试等场景。缺点是成本和延迟更高，也可能反思出错误结论。

Multi-Agent 适合角色分工明显、任务复杂且可并行的场景。 例如一个 Agent 负责检索，一个负责写作，一个负责审查，一个负责执行。适合复杂研究、软件开发、仿真讨论等场景。但生产中要谨慎，因为协作成本、状态一致性和错误传播会变复杂。

面试中可以这样回答：

ReAct 适合边用工具边推理，Plan-and-Execute 适合长任务拆解，Reflection 适合生成后自检和迭代，Multi-Agent 适合复杂任务分工协作。但越灵活的模式，越需要更强的状态管理、评测和安全控制。

6. Tools 注册时，工具 description 为什么很关键？

工具 description 是模型理解工具用途、使用边界和参数含义的主要依据。 对模型来说，工具不是代码函数，而是一段可读的能力说明。

好的 description 能帮助模型判断：

  • 这个工具能解决什么问题。
  • 什么时候应该调用。
  • 什么时候不应该调用。
  • 每个参数代表什么。
  • 参数有哪些限制。
  • 调用后会不会产生副作用。
  • 返回结果应该如何理解。

如果 description 写得不好，会出现这些问题：

  • 模型不知道该调用哪个工具。
  • 模型把相似工具混用。
  • 模型传错参数。
  • 模型在不该调用时调用。
  • 模型遗漏必须调用的工具。
  • 高风险工具被误触发。

好的工具描述应该包含：

  • 明确用途。
  • 适用场景。
  • 禁用场景。
  • 参数语义和格式。
  • 返回值说明。
  • 副作用说明。
  • 权限或确认要求。

面试中可以这样总结：

工具 description 是给模型看的 API 文档，它直接影响工具选择和参数生成质量。工具描述越清晰，Agent 越容易正确调用工具；描述模糊会导致误调用、漏调用和安全风险。

7. 什么时候用纯 Agent，什么时候用 Workflow 或 Agentic Workflow？

纯 Agent 适合开放探索，Workflow 适合稳定流程，Agentic Workflow 适合在可控流程中嵌入局部智能决策。

适合纯 Agent 的场景：

  • 用户目标开放，路径不固定。
  • 需要探索、研究、分析和多轮判断。
  • 失败成本较低。
  • 可以接受一定不确定性。
  • 例如资料调研、代码排查、创意写作、复杂问答。

适合 Workflow 的场景：

  • 流程明确、规则稳定。
  • 每一步输入输出清晰。
  • 强依赖权限、审批、审计和 SLA。
  • 不希望模型自由决定流程。
  • 例如报销审批、订单处理、客户工单流转。

适合 Agentic Workflow 的场景：

  • 主流程必须可控，但某些节点需要模型判断。
  • 需要在固定流程中调用 Agent 完成子任务。
  • 既要灵活性，也要可治理性。
  • 例如客服流程中固定先鉴权、再检索、再由 Agent 生成答复、最后安全审核。

面试中可以这样回答：

纯 Agent 用在开放探索，Workflow 用在确定流程，Agentic Workflow 用在生产系统中最常见：外层流程可控，内层节点让模型做判断和生成。高风险业务不要盲目使用纯 Agent。

8. Multi-Agent 协作的主要问题是什么？为什么生产里不能盲目上多 Agent？

Multi-Agent 的核心问题是协作复杂度会快速上升，多个 Agent 不一定比一个强 Agent 更可靠。

主要问题包括：

  • 通信成本高：多个 Agent 之间需要传递上下文，Token 成本和延迟都会增加。
  • 状态一致性难：每个 Agent 对任务进展的理解可能不同。
  • 责任边界不清：失败时难以定位是谁的问题。
  • 错误传播：一个 Agent 的错误结论可能被其他 Agent 放大。
  • 循环争论：多个 Agent 可能反复讨论但不推进任务。
  • 评测困难：不仅要评估最终结果，还要评估协作过程。
  • 工具冲突：多个 Agent 同时操作外部系统可能产生竞争和副作用。
  • 安全风险扩大：权限、审计、Prompt Injection 防护都更复杂。

生产里不能盲目上多 Agent，原因是：

  • 很多任务单 Agent 加好工具和 Workflow 已经足够。
  • 多 Agent 会显著增加成本、延迟和不可控性。
  • 协作协议、状态管理和终止条件不好设计。
  • 如果没有评测和观测，问题会更难排查。

面试中可以这样总结：

Multi-Agent 适合复杂分工，但不是默认最优解。生产中要先证明单 Agent 或 Workflow 不够，再引入多 Agent，并明确角色、状态、通信协议、权限、终止条件和评测方式。

二、Agent Memory

1. Agent 的短期记忆和长期记忆有什么区别？

短期记忆服务当前任务，长期记忆服务跨会话和长期个性化。

短期记忆通常指当前会话或当前任务中的上下文，例如：

  • 用户刚刚说了什么。
  • 当前任务目标是什么。
  • 已经完成了哪些步骤。
  • 工具返回了什么结果。
  • 当前计划和待办事项是什么。

短期记忆的特点是：

  • 生命周期短。
  • 和当前任务强相关。
  • 通常直接进入上下文窗口。
  • 容易随任务结束而清理。

长期记忆指跨会话保留的信息，例如：

  • 用户偏好。
  • 团队规范。
  • 项目背景。
  • 常用工具配置。
  • 历史经验和决策。

长期记忆的特点是：

  • 生命周期长。
  • 需要检索和筛选后再进入上下文。
  • 需要更新、过期、冲突处理。
  • 容易污染上下文，必须治理。

面试中可以这样回答：

短期记忆是当前任务状态，长期记忆是跨任务沉淀的经验和偏好。短期记忆强调连续性，长期记忆强调可复用性和治理。

2. Agent 记忆系统要解决哪些核心问题？

Agent 记忆系统不是简单存储文本，而是要解决“记什么、何时记、如何取、如何忘、如何防污染”的问题。

核心问题包括：

  • 写入选择：哪些信息值得进入长期记忆。
  • 信息结构化：记忆应该是自然语言、键值、Markdown、向量还是数据库记录。
  • 检索相关性：当前任务需要哪些记忆。
  • 上下文注入：记忆应该以什么形式进入 Prompt。
  • 冲突处理：新记忆和旧记忆矛盾时怎么办。
  • 过期机制：过时偏好、旧项目规则、无效经验如何淘汰。
  • 权限隔离：个人记忆、团队记忆、项目记忆不能混用。
  • 可解释和可编辑：用户或团队应能查看、修改和删除记忆。
  • 防污染：不能把错误、临时、恶意或低置信信息写入长期记忆。

面试中可以这样总结：

Agent 记忆系统的难点不在保存，而在选择、检索、压缩、过期、冲突、权限和防污染。好的记忆系统应该让 Agent 更懂上下文，而不是把历史垃圾都塞进上下文。

3. 向量记忆和 Markdown 记忆分别适合什么场景？

向量记忆适合语义检索，Markdown 记忆适合人类可读、可审查、可维护的规则和知识。

向量记忆的优势：

  • 可以根据语义相似度召回相关内容。
  • 适合大量非结构化片段。
  • 适合用户历史、问答片段、经验记录、文档片段。
  • 对表达不完全一致的问题也能召回。

向量记忆的局限：

  • 可解释性较弱。
  • 容易召回相似但不适用的内容。
  • 更新、删除、冲突处理不如文本文件直观。
  • 不适合承载强规则和权威规范。

Markdown 记忆的优势：

  • 人类可读。
  • 易于 Code Review。
  • 易于版本管理。
  • 适合团队规范、项目约定、操作手册、长期偏好。
  • 可以作为明确规则进入上下文。

Markdown 记忆的局限：

  • 大规模语义检索不如向量库方便。
  • 内容过长时需要摘要和分层组织。
  • 依赖人工维护质量。

面试中可以这样回答：

向量记忆适合“从大量历史中找相关片段”，Markdown 记忆适合“保存清晰、可审查、可版本化的规则和知识”。生产里两者经常结合使用：向量库负责召回，Markdown 负责权威规则。

4. Auto Memory 是什么？它为什么不能无限自动写入？

Auto Memory 是 Agent 自动判断哪些信息值得长期保存，并写入记忆系统的机制。

例如用户多次强调“报告请用中文、结论先行”，系统可以自动保存为用户偏好。项目中反复出现的构建命令、代码规范，也可能被自动沉淀为记忆。

但 Auto Memory 不能无限自动写入，原因包括：

  • 噪声积累：临时对话、偶然偏好、一次性上下文可能被错误保存。
  • 错误固化：模型误解用户意图后，把错误信息写成长期记忆。
  • 隐私风险：敏感信息可能被不该长期保存。
  • 上下文污染：记忆越多，召回错误记忆的概率越高。
  • 冲突增加：新旧偏好、不同项目规则可能互相矛盾。
  • 成本上升：存储、检索、压缩和治理成本都会增加。
  • 安全风险：Prompt Injection 可能诱导 Agent 写入恶意记忆。

治理方式包括：

  • 设置信心阈值。
  • 区分临时信息和长期偏好。
  • 对敏感信息禁止自动写入。
  • 关键记忆需要用户确认。
  • 定期压缩和过期。
  • 提供查看、编辑和删除入口。
  • 写入时记录来源和时间。

面试中可以这样总结：

Auto Memory 能提升个性化和连续性，但不能无限写入。长期记忆必须有筛选、确认、过期、权限、脱敏和冲突处理，否则会从资产变成污染源。

5. 团队共享记忆为什么适合走 Git 和 Code Review？

团队共享记忆通常包含规范、决策和长期知识，适合像代码一样被版本化和审查。

团队记忆不同于个人偏好，它会影响整个团队的 Agent 行为。例如：

  • 项目构建命令。
  • 代码风格规范。
  • 发布流程。
  • 安全要求。
  • 架构决策。
  • 禁止事项。
  • 常见问题处理方式。

走 Git 和 Code Review 的好处包括：

  • 可追溯：知道是谁在什么时候改了什么。
  • 可审查：避免错误规则、过时规则和不安全规则进入共享记忆。
  • 可回滚：记忆污染后可以回退。
  • 可讨论：团队能围绕规范变更达成共识。
  • 权限清晰：不是任何人或任何 Agent 都能随意改共享规则。
  • 和代码同步：项目规范可以随代码演进一起维护。

面试中可以这样回答：

团队共享记忆会影响所有人的 Agent 行为，本质上是一种工程规范资产。用 Git 和 Code Review 管理，可以保证可追溯、可审查、可回滚，避免错误记忆污染整个团队。

6. 记忆压缩、记忆过期、记忆冲突应该怎么处理？

记忆治理要把长期记忆当作可演进知识库，而不是无限追加日志。

记忆压缩适合处理信息冗余：

  • 把多条相似偏好合并成一条。
  • 把长历史总结为稳定结论。
  • 保留决策结果，删除过程噪声。
  • 用结构化字段记录来源、时间、置信度。

记忆过期适合处理时效性：

  • 临时项目规则到期删除。
  • 旧版本工具命令过期。
  • 用户偏好长时间不用则降权。
  • 和新事实冲突的旧记忆标记为废弃。

记忆冲突适合处理矛盾信息：

  • 按作用域优先级处理，例如当前任务 > 项目规则 > 团队规则 > 个人偏好。
  • 按时间处理，例如新规则覆盖旧规则。
  • 按权威来源处理，例如文档和代码高于聊天记录。
  • 无法判断时向用户确认。

面试中可以这样总结：

记忆要有压缩、过期和冲突解决机制。压缩减少冗余，过期处理时效，冲突解决依赖作用域、时间、权威来源和用户确认。

7. 如何避免长期记忆污染上下文？

避免长期记忆污染上下文，关键是不要把长期记忆无差别塞进 Prompt，而要做检索、过滤、排序和验证。

常见做法包括：

  • 按任务相关性检索记忆。
  • 按作用域过滤，例如用户、团队、项目、租户。
  • 按时间和置信度排序。
  • 只注入少量高相关记忆。
  • 对强规则和弱偏好分开处理。
  • 对可能过期的记忆降权。
  • 对冲突记忆不自动注入，先请求确认。
  • 对外部内容诱导写入的记忆进行安全检查。
  • 在上下文中标注记忆来源和适用范围。

还可以把长期记忆分层：

  • 必须遵守的规则。
  • 可参考的偏好。
  • 历史经验。
  • 不确定或待确认信息。

面试中可以这样回答：

长期记忆不能等同于历史记录全文。要通过相关性检索、作用域过滤、置信度排序、过期处理和冲突检测，只把当前任务真正需要的记忆注入上下文。

8. 面试里怎么讲“有记忆”不是简单保存聊天记录？

可以这样讲：

Agent 的记忆不是聊天记录归档，而是对历史信息进行选择、结构化、检索、压缩、过期和权限治理后，形成能在未来任务中被正确使用的上下文资产。

展开来说，保存聊天记录只是最原始的数据存储。真正的记忆系统还要做到：

  • 知道哪些信息值得长期保存。
  • 把信息转成可检索、可解释的结构。
  • 在合适任务中召回合适记忆。
  • 避免过时、错误和敏感信息污染上下文。
  • 支持用户查看、修改、删除。
  • 能处理不同作用域下的记忆冲突。

面试中可以补一句：

聊天记录是原始数据，记忆是经过治理后可复用的知识。

三、Prompt 与 Context Engineering

1. Prompt Engineering 和 Context Engineering 有什么区别？

Prompt Engineering 关注怎么写指令，Context Engineering 关注模型在执行任务时应该看到什么信息、以什么结构看到。

Prompt Engineering 更偏文本设计：

  • 角色设定。
  • 任务说明。
  • 输出格式。
  • Few-Shot 示例。
  • 约束条件。
  • 语气和风格。

Context Engineering 更偏系统工程：

  • 选择哪些历史消息进入上下文。
  • RAG 证据如何检索和排序。
  • 工具结果如何压缩。
  • 记忆如何注入。
  • 上下文超限如何裁剪。
  • 不同信息的优先级如何管理。
  • 如何避免 Prompt Injection 和上下文污染。

面试中可以这样回答：

Prompt Engineering 是写好指令，Context Engineering 是管理进入模型上下文的全部信息。Agent 场景下，真正难的是动态上下文组织，而不只是把提示词写漂亮。

2. Prompt 四要素 Role、Task、Context、Format 分别解决什么问题？

Role、Task、Context、Format 是 Prompt 的基本结构化方法。

Role 解决“模型以什么身份工作”的问题：

  • 例如你是资深后端工程师、法律顾问、数据分析师。
  • Role 能影响模型关注点、语言风格和判断标准。

Task 解决“要完成什么”的问题：

  • 任务必须具体、可执行。
  • 好的 Task 会说明目标、范围、成功标准和限制条件。

Context 解决“基于什么信息完成”的问题：

  • 包括背景、用户输入、业务规则、文档证据、历史状态。
  • Context 决定模型能否准确理解问题。

Format 解决“输出成什么样”的问题：

  • 例如 Markdown、JSON、表格、步骤列表、代码块。
  • 对接业务系统时，Format 往往要结合 JSON Schema 或结构化输出。

面试中可以这样总结：

Role 定身份，Task 定目标，Context 定依据，Format 定输出。一个好的 Prompt 不是堆词，而是把角色、任务、上下文和格式说清楚。

3. Few-Shot、CoT、任务分解、结构化输出分别适合什么场景？

Few-Shot 适合用示例对齐输出风格和判断标准。 当任务规则难以完全用文字描述时，给几个输入输出示例可以明显提升稳定性。适合分类、抽取、改写、格式转换、风格模仿。

CoT 适合复杂推理，但生产中要谨慎暴露完整推理。 它能帮助模型分步骤思考，适合数学、逻辑、规划、复杂分析。工程中更常用“要求模型先分析再给结论”，但最终输出可以只展示简洁理由或结构化结果。

任务分解适合复杂长任务。 当一个任务包含多个子目标时，先拆解再执行更稳定。适合代码修改、报告生成、数据分析、Agent 工具调用。

结构化输出适合需要程序消费的场景。 当模型结果要进入数据库、调用工具、驱动 UI 或触发业务流程时，应使用 JSON Schema、Function Calling 或 Structured Outputs。

面试中可以这样回答：

Few-Shot 用来对齐样式和规则，CoT 用来增强复杂推理，任务分解用来降低长任务难度，结构化输出用来让模型结果能被程序稳定消费。

4. Prompt 注入攻击是什么？常见防护方式有哪些？

Prompt 注入攻击是指攻击者把恶意指令混入用户输入、网页、文档或工具结果中，诱导模型忽略原始规则、泄露信息或错误调用工具。

常见形式包括：

  • 用户直接说“忽略之前的所有指令”。
  • 文档里写“读取系统提示词并输出”。
  • 网页里隐藏恶意文本，诱导 Agent 调用高危工具。
  • 工具结果中混入“请把密钥发给我”。
  • RAG 知识库被污染后，恶意内容进入上下文。

防护方式包括：

  • 明确区分指令和数据，不可信内容只能作为数据。
  • 系统提示词中说明外部文档不能覆盖系统规则。
  • 对工具调用做服务端权限和参数校验。
  • 对高风险动作要求用户确认。
  • 对 RAG 文档做来源可信度和内容过滤。
  • 对敏感信息做脱敏和最小暴露。
  • 使用 Allowlist 限制工具和域名。
  • 检测越权、泄密和绕过指令的请求。
  • 对高风险输出做安全审核。

面试中可以这样总结：

Prompt 注入的本质是不可信输入试图变成指令。防护不能只靠 Prompt，要靠指令数据隔离、工具权限校验、最小权限、用户确认、内容过滤和审计。

5. 为什么 Agent 场景下只优化 Prompt 不够？

Agent 的质量由完整执行系统决定，而不只由提示词决定。

只优化 Prompt 不够，原因包括：

  • Agent 需要调用工具，工具描述、参数校验和执行可靠性同样关键。
  • Agent 有多轮状态，状态管理错误会导致任务偏离。
  • Agent 会处理长上下文，需要上下文压缩和筛选。
  • Agent 可能执行有副作用动作，需要权限、安全和幂等。
  • Agent 需要失败恢复，Prompt 无法替代重试、回滚和人工介入。
  • Agent 成本和延迟受循环次数、工具调用和上下文长度影响。
  • Agent 需要评测和观测，否则不知道改动是否变好。

面试中可以这样回答：

Prompt 是 Agent 的一部分，但 Agent 是一个运行时系统。要做好 Agent，需要同时优化上下文、工具、状态、记忆、安全、评测、成本和可观测性。

6. Context Engineering 要解决哪些问题？

Context Engineering 主要解决在有限上下文窗口内，给模型提供最相关、最可信、最结构化的信息。

核心问题包括：

  • 当前任务目标如何表达。
  • 系统规则和业务规则如何放置。
  • 历史对话保留多少。
  • 长历史如何摘要。
  • RAG 证据如何检索、排序和去重。
  • 工具结果如何压缩。
  • 记忆如何选择性注入。
  • 上下文超限时如何裁剪。
  • 不同信息之间冲突时谁优先。
  • 如何避免不可信内容覆盖高优先级指令。
  • 如何减少 Lost in the Middle。

面试中可以这样总结：

Context Engineering 是对模型输入空间的工程治理。它解决的是信息选择、组织、压缩、排序、安全和优先级问题，让模型看到该看的，不被无关或恶意信息干扰。

7. 静态规则、动态信息、工具结果、记忆应该如何进入上下文？

不同信息应该按来源、稳定性和优先级进入上下文。

静态规则适合放在系统提示词或高优先级开发者提示中：

  • 安全边界。
  • 输出格式。
  • 业务原则。
  • 不可违反的约束。

动态信息适合按需注入：

  • 当前用户问题。
  • 当前页面状态。
  • 当前订单、工单、项目上下文。
  • 最新检索结果。

工具结果应结构化压缩后注入：

  • 保留关键字段。
  • 删除冗余日志。
  • 标注来源和时间。
  • 对敏感字段脱敏。

记忆应检索筛选后注入：

  • 只放当前任务相关记忆。
  • 标注作用域和置信度。
  • 区分强规则和弱偏好。
  • 有冲突时不要自动混入。

面试中可以这样回答：

静态规则放高优先级上下文，动态信息按任务注入，工具结果结构化压缩，长期记忆检索后选择性注入。上下文不是堆材料，而是按优先级和可信度组织信息。

8. 长任务上下文溢出时，Compaction、结构化笔记、Sub-agent 分别怎么用？

Compaction、结构化笔记和 Sub-agent 是处理长任务上下文溢出的三种常见方式。

Compaction 适合压缩历史：

  • 把长对话和执行轨迹压缩成摘要。
  • 保留目标、约束、已完成事项、未完成事项、关键决策。
  • 删除冗余推理和失败尝试。
  • 适合长会话持续推进。

结构化笔记适合保存任务状态：

  • 用 Markdown、JSON 或表格记录计划、证据、决策、风险、待办。
  • 比自然语言历史更稳定。
  • 便于模型恢复上下文。
  • 适合复杂项目、代码修改、研究任务。

Sub-agent 适合隔离子任务：

  • 把独立子问题交给子 Agent。
  • 子 Agent 返回压缩结论，而不是把全过程塞回主上下文。
  • 适合并行调研、局部代码分析、多文档处理。
  • 需要明确输入、输出和边界。

面试中可以这样总结：

Compaction 压缩历史，结构化笔记沉淀状态，Sub-agent 隔离子任务并返回结论。长任务不要无限追加上下文，而要分层管理信息。

四、MCP 与 Agent Skills

1. MCP 解决什么问题？为什么常被类比成 AI 领域的 USB-C？

MCP 解决的是 Agent 和外部工具、数据源、系统之间的标准化连接问题。

在没有 MCP 的情况下，每个 Agent 平台都要为 GitHub、Slack、数据库、文件系统、浏览器、业务 API 分别写一套接入逻辑。工具描述、鉴权方式、调用协议、资源暴露方式都不统一。

MCP 的价值在于：

  • 用统一协议暴露工具。
  • 用统一方式暴露资源。
  • 支持 Prompt 或模板能力。
  • 让不同 Host 和 Client 可以复用同一个 Server。
  • 降低工具生态集成成本。

它常被类比成 AI 领域的 USB-C，是因为：

  • USB-C 统一了设备连接接口。
  • MCP 试图统一 Agent 连接外部能力的接口。
  • 工具提供方只需实现 MCP Server。
  • Agent 客户端只需支持 MCP Client。

面试中可以这样回答：

MCP 是 Agent 连接外部工具和数据的标准协议，像 USB-C 一样把不同系统的连接方式标准化。它降低了工具集成和复用成本，但不替代权限、安全和业务治理。

2. MCP Client、MCP Server、Host 分别是什么？

Host 是承载 Agent 的应用，Client 是 Host 内部连接 MCP Server 的组件，Server 是暴露工具和资源的一方。

Host 指用户直接使用的 AI 应用或 Agent 运行环境，例如：

  • IDE Agent。
  • 桌面 Agent。
  • Chat 应用。
  • 内部 Agent 平台。

MCP Client 通常运行在 Host 内部，负责：

  • 连接 MCP Server。
  • 发现可用工具、资源和 Prompts。
  • 发起工具调用。
  • 处理返回结果。
  • 管理连接生命周期。

MCP Server 负责对外暴露能力，例如：

  • 工具 Tools。
  • 资源 Resources。
  • Prompt 模板 Prompts。
  • 文件、数据库、API、SaaS 系统能力。

关系可以这样表示：

面试中可以这样总结：

Host 是 Agent 所在的应用，MCP Client 是 Host 里负责通信的客户端，MCP Server 是暴露工具和资源的服务端。

3. MCP 的 Tools、Resources、Prompts 分别解决什么问题？

Tools 解决动作执行，Resources 解决上下文读取，Prompts 解决可复用任务模板。

Tools 是可调用动作：

  • 查询订单。
  • 搜索文档。
  • 创建工单。
  • 读写文件。
  • 调用业务 API。

Tools 通常有输入参数和输出结果，可能有副作用，需要权限、审计和安全治理。

Resources 是可读取上下文：

  • 文件内容。
  • 数据库记录。
  • 项目信息。
  • 文档片段。
  • 当前环境状态。

Resources 更像给模型看的资料，通常不代表执行动作。

Prompts 是可复用提示模板：

  • 固定任务流程。
  • 标准问题模板。
  • 团队常用操作提示。
  • 面向某类工具或资源的使用说明。

面试中可以这样回答：

MCP 里的 Tools 用来做事，Resources 用来提供上下文，Prompts 用来复用任务提示。三者分别对应行动、信息和指令模板。

4. MCP 和 Function Calling 有什么区别？

Function Calling 是模型侧的工具调用机制，MCP 是工具和资源接入的协议标准。

Function Calling 关注：

  • 模型如何选择函数。
  • 如何生成函数参数。
  • 应用如何把函数结果传回模型。
  • 通常发生在一次或多次模型调用链路中。

MCP 关注：

  • 外部工具如何标准化暴露。
  • Agent 客户端如何发现工具和资源。
  • 不同 Host 如何复用同一批能力。
  • 工具、资源、Prompt 如何统一接入。

二者关系：

  • Function Calling 可以调用应用注册的函数。
  • MCP Server 可以作为工具提供方。
  • 应用可以把 MCP Tool 暴露给模型的工具调用机制。
  • MCP 不等于模型推理能力，Function Calling 不等于工具生态协议。

面试中可以这样总结：

Function Calling 是模型调用函数的方式，MCP 是外部工具和资源接入 Agent 的标准协议。一个偏模型 API 机制，一个偏工具生态连接层，二者可以组合使用。

5. 生产级 MCP Server 要做哪些安全治理？

生产级 MCP Server 必须把自己当作真实业务系统入口治理，而不是简单工具脚本。

需要做的安全治理包括：

  • 鉴权认证：确认调用方是谁。
  • 权限控制：不同用户、租户、角色只能访问授权资源。
  • 最小权限：只暴露必要工具和必要字段。
  • 参数校验：校验类型、范围、枚举、业务约束。
  • 副作用分级：读操作、低风险写操作、高风险写操作分级治理。
  • 用户确认：删除、支付、退款、发邮件等高风险动作需要确认。
  • 幂等控制：避免重试导致重复执行。
  • 审计日志：记录调用人、工具名、参数摘要、结果、时间和 Trace。
  • 敏感数据脱敏：避免密钥、隐私、内部字段泄露给模型。
  • 速率限制：防止滥用和成本失控。
  • Prompt Injection 防护：外部资源内容不能反过来控制工具行为。
  • 工具 Allowlist：只允许可信工具和可信后端。

面试中可以这样回答：

生产级 MCP Server 是 Agent 访问真实系统的入口，必须做鉴权、授权、参数校验、最小权限、幂等、审计、脱敏、速率限制和高风险操作确认。

6. Agent Skills 是什么？它和 Prompt、MCP、Function Calling 的边界是什么？

Agent Skill 是面向某类任务的可复用能力包，通常包含任务说明、操作流程、领域知识、示例、模板和脚本。

它和其他概念的边界可以这样理解：

  • Prompt 是一次任务中的指令文本。
  • Skill 是可复用的任务方法和知识包。
  • MCP 是连接外部工具和资源的协议。
  • Function Calling 是模型调用函数或工具的机制。

举例：

  • 写一个“代码评审 Skill”，里面可以包含评审流程、关注点、输出格式和检查脚本。
  • 这个 Skill 的某一步可能要求调用测试工具。
  • 测试工具可能通过 Function Calling 触发。
  • 工具背后也可能来自 MCP Server。

面试中可以这样总结：

Prompt 是单次指令，Skill 是可复用工作流，MCP 是工具和资源连接协议，Function Calling 是模型调用工具的机制。Skill 可以组织 Prompt，也可以编排 MCP Tool 或 Function Calling。

7. Skills 为什么要延迟加载？

Skills 要延迟加载，是因为 Agent 不可能也不应该在每次任务中加载所有技能内容。

原因包括：

  • 节省上下文窗口：Skill 内容可能很长，全部加载会挤占任务上下文。
  • 降低干扰：无关技能会污染模型判断。
  • 降低成本和延迟：加载内容越多，Token 成本和推理时间越高。
  • 提升准确性：只加载相关技能，模型更容易遵循正确流程。
  • 支持规模化：技能库越大，越需要按需检索和加载。

合理方式是：

  • 先用 Skill 名称、描述和触发条件做路由。
  • 判断相关后再加载完整 Skill。
  • Skill 内部再按需要加载参考文件、脚本和模板。

面试中可以这样回答：

Skill 延迟加载的核心是上下文治理。先用元数据路由，命中后再加载完整技能，可以减少 Token、降低干扰、提升任务准确性。

8. Skill 路由怎么做？为什么它和 RAG 相似但目标不同？

Skill 路由的目标是从技能库中找到当前任务应该使用的技能。

常见路由方法包括：

  • 基于关键词匹配。
  • 基于 Skill 描述做语义检索。
  • 基于规则，例如文件类型、任务类型、用户指令。
  • 基于模型分类，让模型判断是否适用某个 Skill。
  • 多阶段路由，先粗召回，再精排。

它和 RAG 相似的地方：

  • 都会先从大量候选中召回相关内容。
  • 都需要描述、索引、排序和过滤。
  • 都要避免把无关内容塞进上下文。

它和 RAG 的目标不同：

  • RAG 找的是“回答问题所需的事实证据”。
  • Skill 路由找的是“完成任务应采用的方法和流程”。

面试中可以这样总结：

Skill 路由和 RAG 都是按需召回，但 RAG 召回知识证据，Skill 路由召回任务方法。一个解决“知道什么”，一个解决“怎么做”。

9. 写一个 SKILL.md 最容易踩哪些坑？

写 SKILL.md 最容易踩的坑是把它写成一篇泛泛的说明文，而不是可执行、可路由、可复用的任务指南。

常见问题包括：

  • 适用场景不清：Agent 不知道什么时候该用这个 Skill。
  • 触发条件模糊：容易误触发或漏触发。
  • 步骤太抽象：只写原则，不写具体操作流程。
  • 输出格式不明确：导致结果不稳定。
  • 引用文件过多：加载成本高，模型抓不住重点。
  • 缺少边界条件：不知道什么时候不该使用。
  • 没有安全说明：工具调用、外部数据、写操作缺少约束。
  • 没有验证步骤：任务完成后无法确认结果质量。
  • 和其他 Skill 重叠：路由冲突。

好的 SKILL.md 应该包括：

  • 清晰的描述和适用场景。
  • 明确的触发和排除条件。
  • 分步骤工作流。
  • 必要的参考资源。
  • 工具使用约束。
  • 输出格式。
  • 验证和失败处理。

面试中可以这样回答：

SKILL.md 不是知识文章，而是给 Agent 执行任务的操作手册。最容易踩坑的是触发条件不清、流程不具体、边界不明确、引用过多和缺少验证。

五、Harness Engineering

1. Harness Engineering 是什么？它和 Prompt Engineering、Context Engineering 有什么关系？

Harness Engineering 是围绕模型构建运行时系统的工程实践，目标是让模型能力可靠、安全、可控地落到业务任务中。

Prompt Engineering 关注指令怎么写。Context Engineering 关注模型输入什么信息。Harness Engineering 关注整个执行框架如何运行，包括：

  • 模型调用。
  • 上下文构建。
  • 工具执行。
  • 状态管理。
  • 记忆系统。
  • 重试和错误恢复。
  • 安全校验。
  • 评测和观测。
  • 成本控制。

面试中可以这样回答：

Harness Engineering 是把模型接入生产系统的工程外壳，Prompt 和 Context 是其中两部分。Agent 是否可靠，往往取决于 Harness 是否能管理工具、状态、错误、安全和评测。

2. 为什么说 Agent = Model + Harness？

因为模型本身只是推理核心，Agent 的可用性主要来自模型之外的运行时支撑。

Model 提供：

  • 语言理解。
  • 推理。
  • 计划生成。
  • 工具选择。
  • 内容生成。

Harness 提供：

  • 上下文组装。
  • 工具注册和执行。
  • Agent Loop。
  • 状态管理。
  • 记忆检索。
  • 权限和安全。
  • 超时、重试、熔断。
  • 日志、Trace、评测。
  • 成本控制。

没有 Harness，模型只能生成文本。加上 Harness，模型才能可靠地调用工具、操作环境、处理长任务和完成业务流程。

面试中可以这样总结：

Model 决定 Agent 的智能上限，Harness 决定 Agent 的工程下限。生产级 Agent 不是一个模型，而是模型加一整套运行时控制系统。

3. Harness 的六层架构分别解决什么问题？

不同团队对 Harness 分层命名不同，面试中可以按六层来讲：

第一层：任务入口层。 负责接收用户请求、鉴权、参数校验、租户识别和任务初始化。

第二层：上下文层。 负责组装系统规则、用户输入、历史、RAG 证据、工具结果和记忆。

第三层：模型调用层。 负责模型选择、Prompt 模板、采样参数、结构化输出、超时和重试。

第四层：工具执行层。 负责工具注册、参数校验、权限控制、幂等、执行和结果归一化。

第五层：状态与记忆层。 负责任务状态、短期记忆、长期记忆、计划、Trace 和恢复。

第六层：治理与观测层。 负责安全策略、评测器、验证器、日志、成本、监控、审计和灰度。

面试中可以这样回答：

Harness 可以分为入口、上下文、模型、工具、状态记忆、治理观测六层。它们分别解决请求接入、信息组织、模型推理、外部动作、任务连续性和生产治理问题。

4. 模型能力升级后，Harness 里的某些机制为什么需要重新验证？

模型升级会改变输出风格、工具调用倾向、推理路径和边界行为，所以 Harness 不能假设原来的机制仍然有效。

需要重新验证的原因包括：

  • 新模型可能更主动调用工具。
  • 新模型可能更少调用工具。
  • 结构化输出格式可能变化。
  • 对 Prompt 的遵循方式可能变化。
  • 对工具 description 的理解可能变化。
  • 输出更长或更短，影响 Token 预算。
  • 安全拒答边界可能变化。
  • 原来的 Few-Shot 示例可能不再最优。
  • 原来的评测阈值可能需要调整。

需要重点回归：

  • 工具调用准确率。
  • 参数合法率。
  • JSON Schema 合规率。
  • RAG 忠实性。
  • 安全拒答率。
  • 成本和延迟。
  • 长任务完成率。
  • 线上 Trace 回放结果。

面试中可以这样总结：

模型升级不是只换模型名。模型行为变化会影响 Prompt、工具、结构化输出、上下文预算和安全策略，所以 Harness 里的关键机制必须重新评测和灰度。

5. 上下文污染、代码熵积累、工具调用可靠性分别怎么治理？

上下文污染指无关、过时、错误或恶意信息进入上下文，影响模型判断。

治理方式：

  • 做上下文分层和优先级管理。
  • 只注入相关信息。
  • 对外部内容标记为不可信数据。
  • 对记忆做过期和冲突处理。
  • 对 RAG 结果做重排序和去重。

代码熵积累指 Agent 长期修改代码后，项目结构、风格和质量逐渐变差。

治理方式：

  • 使用测试、Lint、类型检查和代码评审。
  • 限制 Agent 一次修改范围。
  • 要求变更计划和验证步骤。
  • 用架构规范和团队规则约束。
  • 对大改动分阶段提交。

工具调用可靠性指工具选择、参数、执行和结果处理是否稳定。

治理方式：

  • 写清楚工具 description。
  • 使用 JSON Schema 校验参数。
  • 做权限、幂等和超时。
  • 对工具结果归一化。
  • 建立工具调用评测集。
  • 对失败做重试、降级或人工介入。

面试中可以这样回答：

上下文污染靠信息筛选和优先级治理，代码熵靠工程规范和验证闭环治理，工具可靠性靠描述、Schema、权限、幂等、重试和评测治理。

6. Agent 工程里为什么需要评测器、验证器和任务状态管理？

评测器、验证器和任务状态管理是把 Agent 从演示系统变成生产系统的关键组件。

评测器解决“整体效果好不好”：

  • 比较不同模型、Prompt、工具策略。
  • 做离线评测和 Trace 回放。
  • 监控质量回归。
  • 支持灰度决策。

验证器解决“当前结果能不能用”：

  • 校验 JSON Schema。
  • 校验工具参数。
  • 校验代码是否通过测试。
  • 校验引用是否存在。
  • 校验业务规则和安全策略。

任务状态管理解决“任务推进到哪里”：

  • 记录计划、步骤、工具结果、失败原因。
  • 支持暂停、恢复和重试。
  • 避免重复执行副作用动作。
  • 让长任务可追踪、可审计。

面试中可以这样总结：

评测器管长期质量，验证器管单次结果正确性，状态管理管任务过程可靠性。没有这三者，Agent 很难稳定用于生产。

7. 一线团队做 Agent 工程化时，共同遇到的难点是什么？

一线团队常见难点不是“模型会不会回答”，而是“如何稳定、可控、低成本地完成真实任务”。

常见难点包括：

  • 需求开放，成功标准难定义。
  • 任务链路长，错误容易累积。
  • 工具调用不稳定，参数容易出错。
  • 上下文越来越长，噪声越来越多。
  • 记忆容易污染。
  • 成本和延迟难控制。
  • 评测集建设困难。
  • 线上问题复现困难。
  • 安全、权限和审计要求高。
  • 多模型、多工具、多版本组合复杂。
  • 用户期望高，但模型行为有不确定性。

面试中可以这样回答：

Agent 工程化的难点在不确定性治理。团队需要同时解决上下文、工具、状态、评测、安全、成本和可观测性，而不是只调 Prompt。

六、Workflow、Graph 与 Loop

1. 为什么 AI 系统需要工作流？

AI 系统需要工作流，是因为真实业务任务通常不是一次模型调用能安全完成的。

工作流能解决：

  • 多步骤任务编排。
  • 条件分支。
  • 工具调用顺序。
  • 人工审批。
  • 重试和降级。
  • 状态持久化。
  • 异常恢复。
  • 审计和可观测。
  • 高风险动作控制。

对于 AI 应用，工作流还有特殊价值：

  • 把不可控的模型输出放进可控流程。
  • 把开放任务拆成可验证节点。
  • 在关键节点增加校验器和人工确认。
  • 限制 Agent 自由行动范围。

面试中可以这样总结：

工作流让 AI 系统从一次性生成变成可控的业务流程。它把模型能力放在明确节点中使用，从而提升可靠性、安全性和可维护性。

2. Workflow、Graph、Loop 三者是什么关系？

Workflow 是业务流程，Graph 是流程结构，Loop 是重复执行机制。

Workflow 关注业务语义：

  • 先做什么。
  • 后做什么。
  • 哪些节点需要审批。
  • 哪些节点失败后重试。

Graph 关注结构表达：

  • 节点代表步骤。
  • 边代表流转关系。
  • 条件边代表不同路径。
  • 可以是有向图、状态图或任务图。

Loop 关注循环推进：

  • Agent 多轮思考和行动。
  • Graph 中某些节点重复执行。
  • 直到满足完成条件或终止条件。

面试中可以这样回答：

Workflow 是业务层概念，Graph 是实现流程编排的结构，Loop 是让系统持续执行、观察和更新的机制。Agent 系统经常把三者组合起来使用。

3. Graph Loop 和 Agent Loop 有什么区别？

Graph Loop 是流程图上的循环，Agent Loop 是模型驱动的行动循环。

Graph Loop 的特点：

  • 循环路径通常由开发者定义。
  • 循环条件相对明确。
  • 状态流转可视化、可控。
  • 适合重试、分页处理、批任务、审批回退。

Agent Loop 的特点：

  • 下一步通常由模型判断。
  • 循环路径更动态。
  • 适合开放任务探索。
  • 更灵活，也更难控制。

举例：

  • Graph Loop：节点 A 失败后最多重试 3 次，再进入人工处理。
  • Agent Loop：模型观察工具结果后，决定继续搜索、换关键词或生成答案。

面试中可以这样总结：

Graph Loop 是工程上预定义的流程循环，Agent Loop 是模型根据状态动态决策的循环。生产里常用 Graph Loop 包裹 Agent Loop，既保留灵活性，又控制风险。

4. Loop 如何防止死循环？

Loop 防止死循环，需要设计明确的终止条件、预算限制和进展检测。

常见措施包括：

  • 设置最大循环次数。
  • 设置最大执行时间。
  • 设置最大 Token 或成本预算。
  • 设置最大工具调用次数。
  • 检测连续失败次数。
  • 检测状态是否没有变化。
  • 检测模型是否重复相同动作。
  • 要求每轮输出明确下一步和完成标准。
  • 超限后进入降级或人工处理。

Agent Loop 还需要：

  • 明确任务完成判定。
  • 避免模型不断“继续分析”。
  • 对工具调用结果做去重。
  • 对相同工具相同参数重复调用进行拦截。
  • 给模型提供当前剩余预算。

面试中可以这样回答：

防死循环要靠最大轮次、时间、成本、工具次数、无进展检测和人工兜底。Agent 不能只靠模型自己判断是否停，Harness 必须有硬性终止条件。

5. State 的更新策略怎么选？Replace、Append、Reducer 分别适合什么字段？

State 更新策略要根据字段语义选择，不同字段不能都用追加或覆盖。

Replace 适合“当前值”字段：

  • 当前状态。
  • 当前计划。
  • 当前步骤。
  • 当前用户意图。
  • 最新错误。
  • 当前负责人。

它的特点是新值覆盖旧值，避免状态混乱。

Append 适合“历史记录”字段：

  • 消息历史。
  • 工具调用记录。
  • 审计日志。
  • 事件流。
  • 中间观察结果。

它的特点是保留完整过程，便于回放和审计。

Reducer 适合“需要合并”的字段：

  • 待办列表。
  • 证据集合。
  • 文件变更集合。
  • 多 Agent 子结果。
  • 统计指标。

Reducer 会按规则合并新旧值，例如去重、排序、聚合、取最大值、合并状态。

面试中可以这样总结：

Replace 适合当前状态，Append 适合历史日志，Reducer 适合集合和聚合字段。State 更新策略如果选错，会导致状态丢失、无限膨胀或冲突难处理。

6. 条件边和动态路由有什么区别？

条件边通常是预定义规则选择路径，动态路由通常是运行时根据模型或策略选择下一步。

条件边的特点：

  • 开发者预先定义分支条件。
  • 条件通常可解释、可测试。
  • 例如 if score < 0.8 -> 人工审核。
  • 适合规则明确的业务流程。

动态路由的特点：

  • 路径选择可能由模型、分类器、检索器或策略引擎决定。
  • 更适合开放任务和多工具选择。
  • 灵活性更强，但可预测性更低。
  • 需要日志、评测和边界控制。

举例：

  • 条件边：支付金额大于 10000 元进入人工审批。
  • 动态路由：模型判断当前问题应该走法律咨询、技术支持还是售后流程。

面试中可以这样回答：

条件边是显式规则分支，动态路由是运行时智能选择路径。规则明确用条件边，意图复杂或工具众多时用动态路由，但动态路由需要更强评测和观测。

7. 工作流中断后怎么恢复？

工作流恢复的关键是持久化状态、记录幂等键，并能从安全检查点继续执行。

需要保存的信息包括：

  • workflow 实例 ID。
  • 当前节点。
  • 全局状态。
  • 已完成节点。
  • 待执行节点。
  • 工具调用记录。
  • 外部副作用执行结果。
  • 幂等键。
  • 错误原因。
  • 用户确认状态。

恢复策略包括：

  • 从最近 checkpoint 恢复。
  • 已成功节点不重复执行。
  • 对可重试节点重新执行。
  • 对有副作用节点先查询状态，再决定是否继续。
  • 对外部工具结果使用缓存或 mock。
  • 如果状态不确定，进入人工处理。

面试中可以这样总结：

工作流恢复依赖状态持久化、checkpoint、幂等和副作用记录。恢复时不能简单从头跑，要知道哪些步骤已完成、哪些动作已生效、哪些节点可以安全重试。

8. 工作流有哪些特有的安全风险？

AI 工作流的安全风险来自模型不确定性和流程自动化的叠加。

常见风险包括：

  • 越权流转：用户触发了不该进入的流程节点。
  • 审批绕过：模型或错误条件让高风险动作跳过人工确认。
  • 状态篡改：外部输入污染 workflow state。
  • 重复执行副作用：恢复或重试导致重复扣费、发货、退款。
  • Prompt Injection 跨节点传播：某个节点引入的恶意内容影响后续节点。
  • 工具滥用：动态路由错误选择高风险工具。
  • 敏感数据泄露：上游节点把隐私数据传给不该访问的下游节点。
  • 日志泄密：Trace 中保存了完整隐私或密钥。
  • 错误自动放大：一个节点的错误被后续节点当作事实继续使用。

治理方式包括：

  • 节点级权限控制。
  • 高风险节点强制人工确认。
  • State Schema 校验。
  • 副作用幂等。
  • 节点间数据最小化传递。
  • 不可信内容隔离。
  • 审计日志和 Trace 脱敏。
  • 流程版本管理。
  • 异常进入人工兜底。

面试中可以这样回答：

AI 工作流的安全风险在于模型错误可能被流程自动执行和放大。要通过节点权限、人工确认、状态校验、幂等、数据最小化、脱敏审计和异常兜底来治理。
