第一部分（上）：数据结构与操作系统

本部分目标是：不仅会背定义，还能回答“为什么、怎么实现、复杂度是多少、什么时候使用、有什么缺点”。

一、面试回答通用结构

回答任何基础题时，按这个顺序：

  1. 先给出一句话定义。
  2. 说明核心工作原理。
  3. 说明时间和空间复杂度。
  4. 对比相近概念。
  5. 结合实际场景说明如何选择。
  6. 补充边界情况和常见问题。

例如回答“为什么哈希表查询快”：

哈希表通过哈希函数把键映射到数组下标，平均情况下查询、插入和删除都是 O(1)。但如果发生哈希冲突，需要通过链地址法或开放寻址法处理；当冲突严重或扩容时，性能会下降，极端情况下可能退化到 O(n)。

二、数据结构

1. 数组和链表

数组

数组的元素存储在连续内存中，可以通过下标直接定位：

  • 随机访问：O(1)
  • 尾部插入：平均 O(1)
  • 中间插入和删除：O(n)
  • 查找无序元素：O(n)
  • 优点：访问快，缓存局部性好
  • 缺点：中间插入删除成本高，扩容可能需要复制数据

链表

链表通过指针连接节点，节点不要求连续存储：

  • 按位置访问：O(n)
  • 已知节点位置时插入删除：O(1)
  • 查找元素：O(n)
  • 优点：插入和删除方便
  • 缺点：随机访问慢，额外消耗指针空间，缓存局部性较差

高频追问

数组和链表如何选择？

如果查询和随机访问多，优先数组；如果插入删除多且位置容易确定，可以考虑链表。但实际工程中动态数组通常比链表更常用，因为连续内存和缓存友好性往往更重要。

2. 栈、队列和双端队列

栈

栈遵循后进先出，常见操作：

  • 入栈：push
  • 出栈：pop
  • 查看栈顶：peek

典型场景：

  • 函数调用栈
  • 括号匹配
  • 深度优先搜索
  • 表达式求值
  • 浏览器页面回退

队列

队列遵循先进先出：

  • 入队：enqueue
  • 出队：dequeue

典型场景：

  • 广度优先搜索
  • 任务队列
  • 消息缓冲
  • 打印任务调度

双端队列

双端队列允许两端插入和删除，适合：

  • 滑动窗口
  • 单调队列
  • 需要同时从两端操作的场景

**注意：**使用数组实现队列时，如果每次从头部删除元素，可能导致 O(n) 的整体搬移；应使用循环队列或双端队列。

3. 哈希表

哈希表通过哈希函数将键映射到存储位置。

平均复杂度：

  • 查询：O(1)
  • 插入：O(1)
  • 删除：O(1)

哈希冲突解决方式

链地址法

每个数组位置保存一个链表或其他容器，发生冲突的元素放在同一个桶中。

优点：

  • 删除方便
  • 扩容逻辑相对简单
  • 对负载因子容忍度较高

开放寻址法

发生冲突后继续寻找其他空位置，例如线性探测、二次探测。

优点：

  • 数据连续存储，缓存友好
  • 不需要额外链表

缺点：

  • 删除复杂
  • 容易形成聚集
  • 对负载因子更敏感

高频追问

为什么哈希表会扩容？

当负载因子过高时，冲突概率上升，查询性能会下降。扩容后需要重新计算元素位置，这个过程本身可能是 O(n)，但摊销后单次插入仍然可以看作 O(1)。

哈希表最坏复杂度是多少？

如果所有键都映射到同一个位置，查询可能退化为 O(n)。优秀的哈希函数、合理扩容和冲突处理可以降低这种风险。

理想情况下查询、插入和删除都是 O(log n)，但如果树退化成链表，复杂度会变成 O(n)。

因此实际工程中通常使用平衡树，例如 AVL 树或红黑树。

堆

堆是一种特殊的完全二叉树：

  • 小根堆：根节点最小
  • 大根堆：根节点最大

常见复杂度：

  • 查看最值：O(1)
  • 插入：O(log n)
  • 删除最值：O(log n)
  • 建堆：O(n)

典型用途：

  • 优先队列
  • Top K 问题
  • 定时任务
  • Dijkstra 最短路径算法

图

图由顶点和边组成，可分为：

  • 有向图和无向图
  • 有权图和无权图
  • 连通图和非连通图

常用遍历：

  • DFS：适合搜索、回溯、连通性判断
  • BFS：适合最短无权路径、层序遍历

5. 排序和查找

需要掌握：

  • 冒泡排序：O(n²)
  • 插入排序：平均 O(n²)，接近有序时较好
  • 归并排序：O(n log n)，稳定，需要额外空间
  • 快速排序：平均 O(n log n)，最坏 O(n²)
  • 堆排序：O(n log n)，额外空间较少
  • 二分查找：O(log n)，要求数据有序

高频追问

快速排序为什么平均是 O(n log n)？

每次划分如果比较均衡，递归深度约为 log n，每层处理 n 个元素，因此平均是 O(n log n)。如果每次都选到极端主元，递归会退化成 O(n²)。

归并排序和快速排序如何选择？

归并排序稳定，适合需要保持相等元素相对顺序的场景；快速排序通常原地执行，平均性能好，但需要关注最坏情况。

三、操作系统

1. 进程、线程和协程

进程

进程是资源分配的基本单位，拥有独立的地址空间和资源。

优点：

  • 隔离性好
  • 一个进程崩溃通常不会直接破坏其他进程

缺点：

  • 创建和切换成本较高
  • 进程间通信复杂

线程

线程是 CPU 调度的基本单位，同一进程中的线程共享：

  • 代码段
  • 数据段
  • 堆
  • 打开的文件等资源

但每个线程拥有独立的：

  • 栈
  • 程序计数器
  • 寄存器状态

优点是切换和通信成本低，缺点是共享数据容易产生竞态条件。

协程

协程通常是用户态调度的轻量执行单元，能够在遇到 I/O 等待时主动让出执行权。

适合：

  • 高并发 I/O
  • 网络服务
  • 异步任务

协程不等同于线程。多个协程可以运行在线程上，是否真正并行取决于线程和 CPU 调度方式。

2. 进程和线程的区别

对比项 进程 线程
资源 独立资源 共享进程资源
地址空间 相互隔离 通常共享
创建成本 较高 较低
通信方式 IPC 共享内存、锁
崩溃影响 隔离性更好 可能影响整个进程
适用场景 强隔离、多任务 并发执行、共享数据

面试中不要只回答“进程资源多、线程资源少”，还要提到隔离性、通信成本和故障影响范围。

3. 上下文切换

上下文切换是 CPU 从一个执行单元切换到另一个执行单元时，保存当前状态并恢复目标状态的过程。

需要保存的信息包括：

  • 程序计数器
  • 寄存器
  • 栈指针
  • 调度状态
  • 地址空间相关信息

上下文切换会消耗 CPU 时间，因此线程数量并不是越多越好。线程过多可能导致：

  • 切换开销增加
  • 锁竞争加剧
  • CPU 缓存失效
  • 内存占用增加

4. 线程安全和同步

多个线程同时访问共享资源时可能出现竞态条件。

常见同步机制：

  • 互斥锁：同一时间只允许一个线程进入临界区
  • 读写锁：允许多个读者并发，但写入时互斥
  • 信号量：控制同时访问资源的数量
  • 条件变量：等待某个条件满足
  • 原子操作：保证某些操作不可被打断

高频追问

为什么有了 GIL 还需要锁？

GIL 只限制特定 Python 实现中同一时刻执行 Python 字节码的线程数量，不能保证业务操作整体的原子性，也不能保护多个步骤组成的共享状态更新。因此线程之间仍然可能发生竞态，需要锁或其他同步机制。

5. 死锁

死锁通常需要同时满足四个条件：

  1. 互斥：资源同一时间只能被一个执行单元占用。
  2. 占有并等待：已经持有资源，同时等待其他资源。
  3. 不可剥夺：资源不能被强制回收。
  4. 循环等待：多个执行单元形成环形等待。

解决方法

  • 统一获取锁的顺序
  • 尽量减少锁的持有时间
  • 使用超时机制
  • 避免嵌套锁
  • 对锁进行检测和回滚
  • 破坏四个必要条件中的任意一个

面试回答时，应区分：

  • 死锁：相互等待，程序无法继续
  • 活锁：不断重试但没有实际进展
  • 饥饿：某个任务长期得不到资源

6. 虚拟内存

虚拟内存让每个进程拥有独立、连续的虚拟地址空间，而实际物理内存由操作系统统一管理。

核心机制：

  • 分页
  • 页表
  • 地址转换
  • 页面置换
  • 缺页中断

当访问的页面不在物理内存中时，会触发缺页异常，操作系统需要从磁盘加载页面。

虚拟内存的优点：

  • 进程之间相互隔离
  • 支持比物理内存更大的地址空间
  • 提高内存利用率
  • 支持共享库和内存映射

如果频繁发生页面置换，系统可能出现抖动，导致性能急剧下降。

7. 阻塞、非阻塞、同步、异步

这四个概念不能混为一谈。

阻塞与非阻塞

描述调用方是否需要等待结果：

  • 阻塞：调用无法继续执行，直到操作完成
  • 非阻塞：调用立即返回，稍后再检查结果

同步与异步

描述结果由谁通知或获取：

  • 同步：调用方主动等待或获取结果
  • 异步：操作完成后由系统、回调或事件通知调用方

因此：

  • 阻塞不一定等于同步
  • 非阻塞不一定等于异步
  • 同步和异步关注结果获取方式
  • 阻塞和非阻塞关注调用是否停住

8. I/O 模型

常见 I/O 模型包括：

  • 阻塞 I/O
  • 非阻塞 I/O
  • I/O 多路复用
  • 信号驱动 I/O
  • 异步 I/O

I/O 多路复用允许一个线程同时监听多个文件描述符，典型机制包括：

  • select
  • poll
  • epoll

它适合大量连接、单个连接大部分时间处于等待状态的网络服务。

六、计算机网络

1. OSI 模型和 TCP/IP 模型

OSI 模型从理论上将网络通信分为七层：

  1. 物理层：传输比特流。
  2. 数据链路层：帧、MAC 地址、交换机。
  3. 网络层：IP 地址、路由、路由器。
  4. 传输层：TCP、UDP、端口和可靠传输。
  5. 会话层：管理会话建立和维持。
  6. 表示层：编码、压缩和加密。
  7. 应用层：HTTP、DNS、FTP 等协议。

实际开发中更常使用 TCP/IP 模型，通常分为网络接口层、网际层、传输层和应用层。面试时重点掌握每一层解决的问题，以及常见协议属于哪一层。

2. TCP 和 UDP

TCP

TCP 是面向连接的、可靠的字节流协议，具备：

  • 三次握手和四次挥手
  • 序列号和确认应答
  • 超时重传
  • 滑动窗口
  • 流量控制
  • 拥塞控制
  • 数据按序交付

TCP 只保证字节流可靠到达，不保留应用层消息边界。因此一次发送的数据，接收端可能分多次读取，也可能一次读取到多条消息，这就是粘包和拆包问题。

UDP

UDP 是无连接的数据报协议：

  • 不保证可靠到达
  • 不保证顺序
  • 不负责重传
  • 开销较小
  • 延迟较低
  • 保留数据报边界

适合实时音视频、在线游戏、DNS、广播和对实时性要求高但允许部分丢包的场景。

3. TCP 三次握手

三次握手用于确认双方的发送和接收能力，并同步初始序列号：

  1. 客户端发送 SYN，表示希望建立连接。
  2. 服务端回复 SYN + ACK，表示收到请求，并允许建立连接。
  3. 客户端回复 ACK，表示确认服务端响应。

三次握手不能简单理解成“确认客户端、确认服务端、确认连接”，更准确地说，是为了让双方确认收发能力，并避免历史连接请求造成错误建立。

4. TCP 四次挥手

TCP 是全双工通信，双方的发送方向可以分别关闭：

  1. 主动关闭方发送 FIN。
  2. 被动关闭方回复 ACK。
  3. 被动关闭方处理完剩余数据后发送 FIN。
  4. 主动关闭方回复 ACK，连接结束。

主动关闭方通常会进入 TIME_WAIT，原因包括：

  • 确保最后的 ACK 能够重传
  • 等待旧连接中的延迟报文消失

TIME_WAIT 不是简单的“资源泄漏”，但短时间大量连接关闭可能造成端口资源压力。

5. TCP 如何保证可靠传输

TCP 主要通过以下机制保证可靠性：

  • 序列号：标识数据顺序。
  • 确认号：表示已经收到的数据范围。
  • 校验和：检测数据是否损坏。
  • 超时重传：长时间未收到确认时重新发送。
  • 快速重传：连续收到重复 ACK 时提前重传。
  • 滑动窗口：允许发送方连续发送多个数据段。
  • 流量控制：避免接收方缓冲区被压垮。
  • 拥塞控制：根据网络状况调整发送速率。

6. 流量控制和拥塞控制

流量控制关注通信双方的处理能力，核心是接收窗口；接收方通过窗口大小告诉发送方自己还能接收多少数据。

拥塞控制关注整个网络的承载能力，常见阶段包括：

  • 慢启动
  • 拥塞避免
  • 快速重传
  • 快速恢复

两者区别是：流量控制防止“接收方处理不过来”，拥塞控制防止“网络整体拥堵”。

7. HTTP

HTTP 是应用层的请求响应协议，一次请求通常包括：

  • 请求方法
  • 请求路径
  • 请求头
  • 请求体

响应通常包括：

  • 状态码
  • 响应头
  • 响应体

常见方法：

  • GET：获取资源
  • POST：创建资源或执行动作
  • PUT：整体替换资源
  • PATCH：部分更新资源
  • DELETE：删除资源

需要注意，HTTP 方法的幂等性是指同一个请求执行一次或多次，对服务器最终状态的影响是否相同。GET、PUT、DELETE 通常被设计为幂等，POST 通常不是，但最终是否幂等还取决于接口实现。

常见状态码：

  • 2xx：请求成功
  • 3xx：重定向或缓存相关
  • 4xx：客户端请求错误
  • 5xx：服务端处理错误
  • 200：成功
  • 201：资源创建成功
  • 204：成功但无响应体
  • 400：请求参数错误
  • 401：未认证
  • 403：已认证但无权限
  • 404：资源不存在
  • 409：状态冲突
  • 429：请求过多
  • 500：服务端内部错误
  • 502：网关收到无效响应
  • 503：服务暂时不可用

8. HTTPS

HTTPS 本质上是 HTTP 运行在 TLS 之上，主要提供：

  • 加密：防止通信内容被窃听。
  • 身份认证：通过证书验证服务端身份。
  • 完整性保护：防止内容被篡改。

HTTPS 并不是“只要加密就绝对安全”。如果证书校验被绕过、私钥泄露或服务端存在漏洞，仍然可能受到攻击。

9. HTTP 和 HTTPS 的面试重点

需要掌握：

  • HTTP 默认明文传输，HTTPS 使用 TLS。
  • HTTPS 需要证书和密钥协商。
  • TLS 握手阶段协商加密套件和会话密钥。
  • 后续业务数据通常使用对称加密传输。
  • 非对称加密主要用于身份认证和密钥协商。

10. DNS 和常见网络排查

DNS 将域名解析为 IP 地址。常见解析过程会涉及：

  • 浏览器缓存
  • 操作系统缓存
  • 本地 DNS 缓存
  • 递归 DNS 服务器
  • 根域名服务器
  • 顶级域名服务器
  • 权威 DNS 服务器

常用排查思路：

  1. 先确认域名是否能解析。
  2. 再确认目标 IP 和端口是否可达。
  3. 检查 TCP 连接是否成功。
  4. 检查 TLS 或 HTTP 响应是否正常。
  5. 最后查看应用日志和服务端状态。

常用命令包括 ping、nslookup、dig、curl、telnet、ss 和 netstat。

七、数据库基础

1. 关系型数据库

关系型数据库通过表、行和列组织结构化数据，通常使用 SQL 操作数据。

核心特点：

  • 数据结构相对明确
  • 支持事务
  • 支持复杂查询和关联
  • 可以通过约束保证数据一致性
  • 适合强一致、结构化业务数据

SQLite 适合嵌入式、本地单机、小规模和低并发场景；MySQL 更适合服务端、多用户并发和长期运行的业务系统。

2. ACID

数据库事务通常需要满足 ACID：

  • Atomicity，原子性：事务中的操作要么全部成功，要么全部回滚。
  • Consistency，一致性：事务执行前后，数据满足约束和业务规则。
  • Isolation，隔离性：并发事务之间尽量互不干扰。
  • Durability，持久性：事务提交后，结果能够持久保存。

一致性不是数据库单独凭空保证的，它还依赖约束、事务逻辑和应用程序实现。

3. 事务隔离问题

并发事务可能产生：

  • 脏读：读到了其他事务尚未提交的数据。
  • 不可重复读：同一事务中两次读取同一行，结果不同。
  • 幻读：同一事务中两次范围查询，返回的记录集合不同。

常见隔离级别：

隔离级别 脏读 不可重复读 幻读
Read Uncommitted 可能 可能 可能
Read Committed 避免 可能 可能
Repeatable Read 避免 避免 具体取决于实现和读方式
Serializable 避免 避免 避免

隔离级别越高，一致性越强，但并发能力通常越低。MySQL InnoDB 默认使用 Repeatable Read，并通过 MVCC 和锁机制处理不同类型的读取。

4. MVCC

MVCC 是多版本并发控制，通过保存数据的多个版本，让读操作尽量不阻塞写操作。

核心思想：

  • 写入数据时保留版本信息。
  • 事务读取时根据自己的可见性规则选择版本。
  • 普通一致性读可以读取快照。
  • 加锁读取会使用当前读，可能参与锁竞争。

MVCC 适合读多写多的并发场景，但并不意味着完全没有锁，也不能解决所有并发问题。

5. 数据库索引

索引是帮助数据库快速定位数据的数据结构，常见实现是 B+Tree。

B+Tree 适合数据库索引的原因：

  • 树的高度较低
  • 非叶子节点主要保存键和指针
  • 叶子节点保存数据位置或数据本身
  • 叶子节点通常有链表连接，适合范围查询
  • 磁盘 I/O 次数相对较少

常见索引类型：

  • 主键索引
  • 唯一索引
  • 普通索引
  • 联合索引
  • 覆盖索引

6. 联合索引和最左匹配

假设存在联合索引：

通常可以有效支持：

  • user_id
  • user_id, status
  • user_id, status, created_at

但只有 status 或只有 created_at，通常不能充分利用该索引的最左前缀。

联合索引的字段顺序应结合：

  • 查询条件
  • 字段区分度
  • 范围查询频率
  • 排序需求
  • 实际执行计划

不能简单地认为“区分度最高的字段永远放第一位”，最终应通过业务查询和 EXPLAIN 验证。

7. 覆盖索引

如果索引已经包含查询所需的全部字段，数据库可以直接从索引中返回结果，不必再回表查询完整数据，这种索引称为覆盖索引。

优点：

  • 减少回表次数
  • 减少随机 I/O
  • 可能降低查询延迟

但覆盖索引也会增加索引大小和写入维护成本，不能无条件添加大量字段。

8. 数据库锁

锁用于控制并发访问，常见分类包括：

  • 共享锁：允许多个事务读取，通常不允许写入。
  • 排他锁：持有锁的事务可以写入，其他事务不能同时读写相关数据。
  • 行锁：锁定较小范围，并发能力较好。
  • 表锁：锁定范围大，实现简单，但并发能力较弱。

InnoDB 还涉及记录锁、间隙锁和临键锁。范围条件下的锁行为与索引、隔离级别和执行计划有关，不能只按“查询一行就是行锁”简单判断。

9. 数据库死锁

数据库死锁通常是多个事务以不同顺序持有和等待锁。

常见解决方法：

  • 保持事务访问表和记录的顺序一致。
  • 缩短事务执行时间。
  • 避免在事务中执行不必要的外部调用。
  • 为事务设置合理的超时时间。
  • 捕获死锁异常并进行有限次数重试。
  • 通过日志分析死锁发生的 SQL 和锁关系。

重试不能代替解决死锁根因，而且重试逻辑必须保证业务操作幂等。

10. SQL 优化

常见优化方法：

  • 使用 EXPLAIN 查看执行计划。
  • 避免 SELECT *。
  • 为高频过滤、连接和排序字段设计索引。
  • 避免对索引字段进行函数计算或隐式类型转换。
  • 避免不必要的深分页。
  • 控制单次查询返回的数据量。
  • 关注联合索引顺序和覆盖索引。
  • 避免在循环中逐条查询造成 N+1 问题。
  • 根据业务需要批量写入和批量更新。
  • 定期关注慢查询日志。

优化时不能只看 SQL 文本，还要关注：

  • 实际数据量
  • 数据分布
  • 索引基数
  • 查询频率
  • 锁等待
  • 磁盘和缓存命中情况

11. 数据库连接池和事务边界

连接池通过复用数据库连接，减少频繁建立连接的开销。

需要关注：

  • 最大连接数
  • 最小空闲连接数
  • 连接超时
  • 空闲回收
  • 连接泄漏
  • 事务是否及时提交或回滚

事务边界应该围绕一个完整的业务操作设置。事务过大，会导致锁持有时间长；事务过小，又可能无法保证业务原子性。

十一、第二部分：Python、FastAPI、Pydantic、SQLAlchemy 与 pytest

这一部分对应简历中的 Python 后端开发能力。面试重点不是只会写语法，而是要能解释 Python 的运行行为、接口请求链路、数据校验、数据库访问和测试边界。

1. Python 对象、变量和可变性

Python 中变量更接近对象的引用，而不是固定类型的内存盒子。变量可以重新绑定到不同类型的对象。

常见不可变对象：

  • int
  • float
  • str
  • tuple
  • frozenset

常见可变对象：

  • list
  • dict
  • set
  • 自定义类实例

不可变对象不能原地修改；对它执行所谓的修改操作时，通常是创建了新对象。可变对象可以在原对象上修改，因此作为函数参数或默认参数时要特别注意共享状态。

== 和 is

  • == 比较两个对象的值是否相等。
  • is 比较两个变量是否指向同一个对象。

业务代码判断值是否相等时使用 ==；判断是否为 None 时通常使用 is None。

2. 浅拷贝和深拷贝

浅拷贝只复制最外层容器，内部嵌套对象仍然共享引用；深拷贝会递归复制嵌套对象。

如果修改 shallow[0] 内部的列表，原始 items 可能也会受到影响；修改 deep 的嵌套对象通常不会影响原对象。但深拷贝可能成本较高，且不适合所有包含文件句柄、连接对象或锁的对象。

3. Python 常用容器

list

有序、可变、允许重复。适合需要按顺序保存数据的场景。

tuple

有序、不可变。适合表示不应被修改的固定结构，也可以作为字典键的一部分，前提是其中元素都可哈希。

dict

保存键值对，平均查询和更新复杂度为 O(1)。键必须是可哈希对象。

set

保存不重复元素，适合去重、集合运算和快速成员判断。

面试时要能说明：字典和集合底层都依赖哈希结构，但集合只保存键，字典还保存键和值。

4. 迭代器和生成器

可迭代对象能够被 for 遍历；迭代器通常实现 __iter__() 和 __next__()，每次返回一个元素。

生成器通过 yield 产生值，具有惰性求值特点：

  • 不会一次性创建全部结果
  • 可以降低内存占用
  • 适合处理大文件、数据流和分页数据
  • 只能按迭代过程逐步消费

生成器不是“自动加速工具”，它主要解决的是延迟计算和内存占用问题。

5. 装饰器和上下文管理器

装饰器

装饰器本质上是接收函数并返回新函数的可调用对象，常用于：

  • 日志记录
  • 权限检查
  • 计时统计
  • 缓存
  • 重试

编写装饰器时应使用 functools.wraps 保留原函数的名称和元信息。

上下文管理器

上下文管理器通过 __enter__ 和 __exit__ 管理资源生命周期，常见于：

  • 文件读写
  • 数据库事务
  • 锁
  • 临时资源

它的核心价值是：即使代码块发生异常，也能执行清理逻辑。

6. 异常处理

异常处理应遵循：

  • 捕获具体异常，而不是无差别捕获 Exception。
  • 不要静默吞掉异常。
  • 保留原始异常上下文。
  • 给调用方返回可理解的错误。
  • 记录必要日志，但不要泄露密钥和敏感数据。

常见错误：

  • 把异常当作正常分支大量使用。
  • 捕获异常后不记录、不返回、不重新抛出。
  • 在底层吞掉异常，导致上层无法判断失败原因。
  • 用异常信息直接向用户暴露堆栈和内部路径。

7. 类型注解

类型注解主要用于：

  • 提高代码可读性
  • 辅助 IDE 和静态检查
  • 帮助接口和数据模型表达契约
  • 降低大型项目维护成本

类型注解默认不会阻止 Python 运行时传入错误类型。需要配合 Pydantic、静态检查工具或运行时校验才能形成实际约束。

8. GIL、线程、进程和异步

在传统 CPython 中，GIL 会限制同一进程内多个线程同时执行 Python 字节码。因此：

  • I/O 密集型任务适合使用线程或异步。
  • CPU 密集型 Python 代码通常更适合使用多进程或原生扩展。
  • GIL 不代表所有操作都线程安全。
  • GIL 也不能代替业务锁。

线程适合共享内存和 I/O 并发；进程适合隔离资源和 CPU 并行；异步适合大量 I/O 等待任务。

异步函数执行过程：

  1. async def 定义协程函数。
  2. 调用协程函数通常只创建协程对象，并不会立即执行函数体。
  3. 事件循环调度协程。
  4. 协程执行到 await 时，如果等待异步 I/O，会主动让出执行权。
  5. I/O 完成后，事件循环恢复协程执行。

异步代码中不能直接调用长时间阻塞的同步 I/O，否则会阻塞整个事件循环。必要时应使用异步驱动、线程池或进程池。

十三、Pydantic

1. Pydantic 解决什么问题

Pydantic 用 Python 类型注解定义数据模型，并进行运行时数据校验和序列化。

它可以处理：

  • 必填字段
  • 默认值
  • 类型转换
  • 字段范围
  • 嵌套对象
  • 枚举值
  • 自定义校验
  • JSON Schema

Pydantic 的作用是建立数据契约，但不能替代数据库约束、权限校验和业务规则。

2. 请求模型和响应模型

请求模型用于限制客户端可以提交什么数据；响应模型用于限制服务端对外返回什么数据。

分离请求模型和响应模型的好处：

  • 避免把内部字段误返回
  • 避免客户端修改只读字段
  • 使输入输出契约更清晰
  • 便于接口版本演进

3. 字段校验和业务校验

字段校验适合：

  • 类型
  • 长度
  • 范围
  • 格式
  • 是否为空

业务校验适合：

  • 用户是否有权限
  • 资源是否存在
  • 状态是否允许转换
  • 多个字段之间是否满足业务关系

不要把所有业务逻辑塞进字段校验器，否则模型会承担过多职责，测试和复用都会变复杂。

4. 序列化和反序列化

  • 反序列化：把字典、JSON 等外部数据转换为模型对象。
  • 序列化：把模型对象转换为字典、JSON 等输出格式。

需要特别处理：

  • datetime
  • Decimal
  • 枚举
  • 嵌套模型
  • ORM 对象
  • 脱敏字段

模型导出时应明确哪些字段需要排除，不能依赖默认行为把内部数据全部暴露出去。

1. 核心组件

Engine

Engine 负责连接数据库的整体入口，包含数据库方言、连接池和连接获取逻辑。

Connection

Connection 表示与数据库的底层连接，适合执行较接近 SQL 层的操作。

Session

Model

  • 面向对象操作
  • 减少重复 SQL
  • 方便建模和关联关系表达
  • 易于复用查询逻辑

原生 SQL 的优点：

  • 表达复杂查询更直接
  • 便于精细控制执行方式
  • 对性能敏感场景更容易优化

实际工程中不应把 ORM 和原生 SQL 对立起来，而应根据查询复杂度、可维护性和性能要求选择。

十五、pytest

1. 测试类型

  • 单元测试：测试单个函数或模块，依赖少、速度快。
  • 集成测试：验证数据库、缓存或外部组件之间的协作。
  • 接口测试：从 HTTP 层验证请求、响应、状态码和错误处理。
  • 端到端测试：验证完整业务链路，成本最高。

测试不是越多越好，而是要覆盖核心规则、异常路径和高风险边界。

2. Fixture

Fixture 用于准备测试依赖和清理测试资源，例如：

  • 测试数据库
  • 测试客户端
  • 临时目录
  • Mock Provider
  • 测试用户

常见作用域：

  • function：每个测试函数执行一次
  • class：每个测试类执行一次
  • module：每个模块执行一次
  • session：整个测试会话执行一次

作用域越大，准备成本可能越低，但测试之间共享状态的风险越高。

3. Mock 和 Patch

Mock 用于替换外部依赖，使测试稳定、快速并且不产生真实副作用。

适合 Mock 的对象：

  • 外部 HTTP 接口
  • 第三方模型服务
  • 当前时间
  • 随机数
  • 邮件、短信和支付服务
  • 不稳定或昂贵的资源

常见错误是 patch 了定义函数的模块，而不是被测试代码实际查找该对象的模块。面试中可以说明：应 patch 使用方命名空间中的引用。

4. 参数化测试

参数化测试适合验证同一规则的多组输入，例如：

  • 合法和非法参数
  • 边界长度
  • 空值和特殊字符
  • 不同状态转换
  • 多种异常类型

它可以减少重复测试代码，同时让边界用例更加清晰。

5. 测试隔离

测试之间不应该依赖执行顺序。数据库测试通常需要：

  • 独立测试数据库或事务回滚
  • 固定的初始化数据
  • 唯一的测试资源
  • 测试后清理
  • 避免连接和文件句柄泄漏

如果测试偶尔失败，不能简单地增加重试次数，应先排查共享状态、时间依赖、网络依赖和并发问题。

6. 后端测试重点

  • 必填字段缺失
  • 参数类型错误
  • 边界值
  • 未认证
  • 无权限
  • 资源不存在
  • 重复操作
  • 数据库异常
  • 外部依赖超时
  • 返回结构和状态码

十九、第三部分：MySQL 进阶、Redis、Kafka 与消息可靠性

这一部分对应简历中的数据库和中间件能力。回答此类问题时，要同时说明数据存储、并发访问、故障恢复和业务一致性，而不能只背组件定义。

1. MySQL 表结构设计

表结构设计首先要明确：

  • 数据实体和实体之间的关系
  • 主键策略
  • 必填字段和默认值
  • 唯一性约束
  • 外键或应用层关联策略
  • 高频查询条件
  • 数据增长速度
  • 删除、归档和历史数据策略

规范化可以减少数据冗余和更新异常；反规范化可以减少关联查询、提高读取效率。实际设计需要在一致性、查询性能和维护成本之间权衡。

2. 主键选择

主键需要满足唯一性、稳定性和可索引性。

常见选择：

  • 自增整数：简单、索引紧凑，但分布式生成和数据迁移需要额外设计。
  • UUID：全局唯一，但随机性可能导致索引页频繁分裂，存储空间也较大。
  • 有序 ID：兼顾分布式唯一性和索引写入效率，但需要维护生成算法。

主键不应包含经常变化的业务属性，否则更新主键会影响关联数据和索引结构。

3. EXPLAIN 重点字段

分析 MySQL 查询时重点关注：

  • type：访问类型，通常应避免全表扫描。
  • possible_keys：可能使用的索引。
  • key：实际使用的索引。
  • key_len：使用了联合索引的多少部分。
  • rows：优化器估计扫描的行数。
  • filtered：过滤比例的估计值。
  • Extra：是否出现回表、临时表或文件排序等信息。

执行计划是估算结果，不等于真实执行过程。排查性能时还要结合实际数据量、慢查询日志和运行时指标。

4. 索引失效的常见原因

索引可能因为以下原因无法充分使用：

  • 对索引字段做函数或表达式计算。
  • 发生隐式类型转换。
  • 对字符串字段使用前置通配符，例如 LIKE '%abc'。
  • 联合索引不符合最左前缀。
  • 查询返回结果占比过高，优化器判断全表扫描更便宜。
  • 对低区分度字段单独建立索引。
  • 使用 OR 导致执行计划复杂。

索引不是越多越好。每个索引都会增加存储空间，并增加插入、更新和删除时的维护成本。

5. 深分页问题

传统 LIMIT offset, size 在 offset 很大时，需要扫描并跳过大量记录，性能会下降。

优化方式：

  • 使用基于唯一递增键的游标分页。
  • 使用上一次查询的最后一条记录作为下一页起点。
  • 保证排序字段稳定且有索引。

游标分页适合连续翻页和大数据量查询；随机跳转到任意页时，仍可能需要传统分页或额外索引设计。

6. MySQL 读写分离

读写分离通常把写请求发送到主库，把读请求发送到从库。

优点：

  • 分担主库读取压力
  • 提高读取吞吐量
  • 便于扩展只读节点

问题：

  • 主从复制存在延迟
  • 刚写入的数据可能暂时读不到
  • 事务中读写路由复杂
  • 从库故障和主从切换需要处理

常见解决方案：

  • 强一致读取路由到主库。
  • 写入后短时间内的关键读取路由到主库。
  • 根据复制位点判断从库是否追上主库。
  • 对业务接受的最终一致性进行明确建模。

7. MySQL 主从复制和故障切换

主从复制的基本过程是：

  1. 主库记录数据变更日志。
  2. 从库拉取主库的日志。
  3. 从库在本地重放变更。

需要关注：

  • 复制延迟
  • 日志堆积
  • 从库执行失败
  • 主库故障时的数据丢失窗口
  • 切换后新的主库是否可写
  • 应用连接是否能够更新

故障切换不是简单地把一个地址改成另一个地址，还涉及选主、数据一致性、连接刷新和业务恢复。

二十、Redis

1. Redis 的特点

Redis 是基于内存的键值存储，常用于：

  • 缓存
  • 计数器
  • 分布式锁
  • 会话存储
  • 排行榜
  • 限流
  • 延迟队列
  • 发布订阅

Redis 速度快的主要原因包括内存访问、数据结构简单、网络协议开销较低，以及单线程事件循环对共享数据操作的简化。现代 Redis 也可能使用后台线程处理部分 I/O 或任务，但命令执行模型仍需避免长时间阻塞操作。

2. Redis 常见数据结构

String

适合缓存字符串、数字、序列化对象和计数值。

Hash

适合保存对象的多个字段，例如用户状态，但不应无限制地把巨大对象塞入一个 Hash。

List

适合简单队列、列表和时间线，但高并发可靠消息场景应结合更合适的机制。

Set

适合去重、集合交并差和标签关系。

Sorted Set

通过 score 排序，适合排行榜、延迟任务和范围查询。

Stream

适合带有消息 ID、消费组和确认机制的日志或消息流场景。

3. Cache Aside 模式

常见缓存旁路模式流程：

读流程

  1. 先读缓存。
  2. 缓存命中则直接返回。
  3. 缓存未命中时读取数据库。
  4. 将数据库结果写入缓存。
  5. 返回结果。

写流程

  1. 先更新数据库。
  2. 再删除缓存。

通常更推荐更新数据库后删除缓存，而不是先更新缓存，因为直接修改缓存容易产生复杂的一致性问题。

4. 缓存一致性

缓存和数据库不可能在所有时间点都绝对一致，需要明确业务允许的短暂不一致范围。

常见问题：

  • 数据库更新成功但缓存删除失败。
  • 并发读请求把旧值重新写回缓存。
  • 删除缓存和更新数据库之间发生故障。
  • 多个服务同时修改同一数据。

常见改进手段：

  • 删除失败重试。
  • 延迟双删。
  • 消息队列异步失效。
  • 设置合理 TTL。
  • 对关键数据直接读主库。
  • 使用版本号或更新时间避免旧数据覆盖新数据。

延迟双删并不能自动保证强一致，仍需要结合并发模型和失败重试设计。

5. 缓存穿透、击穿和雪崩

缓存穿透

查询一个数据库和缓存中都不存在的键，大量请求直接打到数据库。

解决方式：

  • 缓存空值并设置较短 TTL。
  • 使用布隆过滤器过滤明显不存在的键。
  • 对请求参数做合法性校验。

缓存击穿

某个热点键刚好过期，大量并发请求同时查询数据库。

解决方式：

  • 互斥锁或单飞机制。
  • 热点数据永不过期并异步刷新。
  • 提前续期。
  • 设置随机 TTL 避免集中失效。

缓存雪崩

大量缓存同时过期，或 Redis 整体不可用，导致请求集中访问数据库。

解决方式：

  • TTL 增加随机偏移。
  • 多级缓存。
  • 限流和熔断。
  • 缓存预热。
  • Redis 高可用和故障转移。

6. 热点 Key 和大 Key

热点 Key 会造成单个 Redis 节点或单个数据分片压力过高；大 Key 会增加网络传输、内存操作和删除成本。

处理方式：

  • 拆分大对象。
  • 对热点数据做本地缓存或多副本分散读取。
  • 避免一次返回巨量数据。
  • 使用渐进式删除。
  • 监控 Key 访问频率和内存占用。

7. Redis 持久化

RDB

RDB 在某个时间点生成数据快照。

优点：

  • 文件紧凑
  • 恢复速度较快
  • 对运行时读操作影响相对可控

缺点：

  • 两次快照之间发生故障时可能丢失数据
  • 生成快照需要额外资源

AOF

AOF 记录写命令，并在恢复时重放命令。

优点：

  • 数据丢失窗口通常更小
  • 日志可读性相对更好

缺点：

  • 文件可能更大
  • 恢复速度可能较慢
  • 需要重写压缩日志

生产环境通常根据数据重要性、恢复时间目标和可接受丢失窗口组合使用持久化方式。

8. Redis 主从复制、Sentinel 和 Cluster

主从复制

主节点负责写入，从节点同步数据并承担部分读取压力。复制通常存在延迟，因此不能默认从节点读到最新数据。

Sentinel

Sentinel 主要负责：

  • 监控节点
  • 判断主节点是否下线
  • 自动故障转移
  • 通知客户端新的主节点

Sentinel 解决的是高可用和自动切换，不是数据水平分片。

Cluster

Redis Cluster 通过哈希槽把键分布到多个节点，支持数据分片和横向扩展。

需要关注：

  • 多键操作可能要求键位于同一槽位。
  • 节点扩缩容需要迁移槽位。
  • 集群故障可能影响部分数据分片。
  • 客户端必须支持集群拓扑和重定向。

9. Redis 分布式锁

一个基本的分布式锁需要：

  • 唯一锁值
  • 原子加锁
  • 过期时间
  • 只有持有者才能释放锁

释放锁时不能直接执行无条件删除，否则锁过期后被其他请求获得，新请求可能被旧请求误删锁。通常需要通过 Lua 脚本原子判断锁值并删除。

还要考虑：

  • 业务执行时间超过锁 TTL
  • 服务进程崩溃
  • 时钟和网络问题
  • 锁续期
  • 是否真的需要分布式锁

分布式锁不能替代数据库唯一约束和幂等设计。

二十一、Kafka

1. Kafka 核心概念

  • Broker：Kafka 服务节点。
  • Topic：逻辑上的消息分类。
  • Partition：Topic 的分区，消息在分区内追加写入。
  • Replica：分区副本。
  • Leader：处理分区的读写请求。
  • Follower：复制 Leader 数据。
  • Producer：生产消息。
  • Consumer：消费消息。
  • Consumer Group：共同消费一个 Topic 的消费者集合。
  • Offset：消费者在分区中的消费位置。

2. Partition 和消息顺序

Kafka 只能保证单个 Partition 内的有序性，不能天然保证整个 Topic 的全局顺序。

如果要求同一个业务实体的消息有序，应使用稳定的业务键，让相关消息进入同一个 Partition。但这样会造成热点分区，降低整体并行度，因此需要在顺序性和吞吐量之间权衡。

3. Consumer Group

同一个 Consumer Group 中，一个 Partition 在同一时刻通常由一个消费者实例负责消费；不同 Group 可以独立消费同一份消息。

当消费者数量：

  • 少于 Partition 数量：一个消费者可能负责多个 Partition。
  • 等于 Partition 数量：通常可以一一对应。
  • 多于 Partition 数量：多出的消费者可能处于空闲状态。

消费者加入、退出或故障时，会触发 Rebalance。频繁 Rebalance 会造成消费暂停和吞吐下降，需要关注消费者存活时间、处理时长和分区分配策略。

4. Offset 提交

Offset 表示消费进度。常见策略：

  • 自动提交：简单，但可能在业务处理完成前提交，导致消息丢失。
  • 手动提交：业务处理成功后再提交，更容易实现至少一次消费。

手动提交也可能产生重复消费，例如业务处理成功但提交 Offset 失败，消费者重启后会再次读取该消息。

所以“至少一次”通常意味着必须配合业务幂等处理。

5. Producer 可靠性

生产者可靠性相关配置和机制包括：

  • acks：等待多少副本确认。
  • 重试：处理暂时性网络或 Broker 故障。
  • 超时：限制等待时间。
  • 幂等生产：减少重试造成的重复写入。
  • 事务消息：在特定场景下协调消息写入和消费处理。
  • 批量发送：提高吞吐量。
  • 压缩：减少网络和磁盘压力。

可靠性越高，通常会带来更高延迟或更低吞吐，需要根据消息重要性选择配置。

6. 消息投递语义

至多一次

消息最多处理一次，可能丢失，但不会因为重试造成重复。

至少一次

消息不会轻易丢失，但可能重复消费。

恰好一次

在特定边界和配置下尽量实现一次处理语义，但它不是整个业务系统天然具备的能力。跨数据库、外部接口和消息系统时，通常仍需要幂等、事务或状态表配合。

7. 消息重复和幂等

消费者应把重复消费作为正常情况处理。

常见幂等方式：

  • 使用业务唯一 ID。
  • 数据库唯一约束。
  • 消费记录表。
  • 状态机限制重复状态转换。
  • Redis SETNX 配合过期时间。
  • 更新操作使用条件判断。

幂等不是简单地“判断执行过没有”，还要考虑并发、执行中断和状态恢复。

8. 消息丢失排查

需要分段排查：

  1. Producer 是否真正发送成功。
  2. Broker 是否持久化并复制成功。
  3. Consumer 是否成功拉取。
  4. Consumer 是否在业务完成前提交 Offset。
  5. 业务处理是否失败但没有重试。
  6. 重试和死信消息是否被正确记录。

只有记录消息 ID、分区、Offset、处理结果和错误原因，才能定位消息链路问题。

9. 重试和死信队列

不适合无限重试。常见策略：

  • 短暂性错误：延迟后重试。
  • 参数或业务错误：直接进入死信队列。
  • 外部服务不可用：指数退避并限制次数。
  • 超过最大次数：记录告警并等待人工处理。

重试消息应避免和原消息无限相互触发，并且要保留原始消息 ID 和失败原因。

10. Kafka 削峰填谷和异步解耦

Kafka 能够把生产者和消费者的处理速度解耦：

  • 生产者快速写入消息。
  • 消费者按自身能力处理。
  • 分区提供并行消费能力。
  • 积压量反映消费速度跟不上生产速度。

但消息队列不是无限缓冲区。积压过多会导致延迟升高、磁盘压力增加和消息过期，需要通过扩容消费者、优化处理逻辑、限流生产者或降低消息体积解决。

二十五、第四部分：PyTorch 与计算机视觉

这一部分对应简历中的 PyTorch、目标检测、语义分割、图像增强、YOLO、U-Net 和模型训练调优能力。回答模型问题时，应同时说明任务目标、数据处理、模型结构、损失函数、评价指标和部署限制。

1. PyTorch 的基本组成

PyTorch 模型训练通常由以下部分组成：

  • Tensor：保存数据和模型参数。
  • nn.Module：定义模型结构和参数。
  • Dataset：描述如何读取单条样本。
  • DataLoader：负责批量加载、打乱和并行读取数据。
  • Loss：衡量预测结果与真实标签的差异。
  • Optimizer：根据梯度更新模型参数。
  • Scheduler：动态调整学习率。

2. Tensor 和设备管理

Tensor 可以放在 CPU 或 GPU 上。参与同一次计算的 Tensor 和模型参数通常必须位于兼容的设备上。

常见问题：

  • 模型在 GPU，输入数据仍在 CPU。
  • 标签类型不符合损失函数要求。
  • 不必要地频繁进行 CPU/GPU 数据拷贝。
  • 使用不连续 Tensor 时调用依赖内存布局的操作。
  • 没有释放不再使用的中间结果导致显存持续增长。

工程中应统一设备管理，避免在业务代码中到处手写 .cuda()，通常使用明确的 device 变量和 .to(device)。

3. 自动求导和计算图

PyTorch 会根据张量运算构建计算图，并在反向传播时计算梯度。

基本过程：

  1. 输入经过模型前向计算。
  2. 得到损失值。
  3. 调用 loss.backward() 计算参数梯度。
  4. 优化器根据梯度更新参数。
  5. 调用 optimizer.zero_grad() 清理旧梯度。

梯度默认可能会累积，因此每个训练步骤通常需要清空梯度。梯度累积也可以被有意利用，例如显存不足时用多个小批次模拟较大的有效 Batch Size。

4. train()、eval() 和 no_grad()

model.train() 和 model.eval() 用于切换训练和评估行为，尤其影响：

  • Dropout
  • Batch Normalization

torch.no_grad() 用于在推理阶段关闭梯度记录，减少显存占用和计算开销。

二者职责不同：

  • eval() 改变模型层的行为。
  • no_grad() 关闭梯度计算。

验证阶段通常需要同时使用 model.eval() 和 torch.no_grad()。

5. Dataset 和 DataLoader

Dataset 需要明确：

  • 样本数量
  • 单条样本如何读取
  • 输入和标签如何返回
  • 数据异常如何处理

DataLoader 负责：

  • Batch 组装
  • 是否打乱数据
  • 多进程或多线程加载
  • collate_fn 定制批处理方式
  • 预取和持久化 Worker

检测任务中每张图片的目标数量可能不同，默认批处理方式可能无法直接堆叠，因此常需要自定义 collate_fn。

6. 损失函数

损失函数应与任务和标签格式匹配：

  • 分类常用交叉熵或二元交叉熵。
  • 回归常用均方误差、绝对误差或 Smooth L1。
  • 目标检测通常包含分类损失、框回归损失和置信度损失。
  • 分割常用交叉熵、Dice Loss、Focal Loss 或组合损失。

选择损失函数时需要考虑：

  • 标签是类别索引还是概率。
  • 类别是否不平衡。
  • 是否需要对难样本增加权重。
  • 预测目标是离散分类还是连续回归。

7. 优化器和学习率

常见优化器：

  • SGD：泛化性能常较好，但对学习率和动量较敏感。
  • Adam：收敛通常较快，适合快速实验。
  • AdamW：将权重衰减与梯度更新解耦，常用于现代深度学习训练。

学习率过大可能导致损失震荡或发散；过小则可能收敛很慢或停在较差解。

常见学习率策略：

  • Step Decay
  • Cosine Annealing
  • Reduce on Plateau
  • Warmup

学习率调整应结合训练损失、验证指标和训练阶段判断，不能只凭固定经验设置。

8. 模型保存和恢复

至少应保存：

  • 模型参数
  • 优化器状态
  • 学习率调度器状态
  • 当前 Epoch
  • 最佳验证指标
  • 随机种子或实验配置

只保存模型参数可以用于推理，但如果要从中断位置继续训练，还需要保存优化器和调度器状态。

需要区分：

  • 保存最新模型：便于恢复训练。
  • 保存最佳模型：便于最终评估和部署。

9. 混合精度和显存优化

混合精度训练使用不同精度表示不同计算，可以减少显存占用并提升部分 GPU 上的吞吐量。

常见显存优化方式：

  • 降低 Batch Size。
  • 使用梯度累积。
  • 使用混合精度。
  • 减小输入分辨率。
  • 使用梯度检查点。
  • 避免在循环中保存完整计算图。
  • 推理阶段关闭梯度。

降低精度可能带来数值稳定性问题，因此需要观察损失、梯度和最终指标。

二十六、目标检测

1. 目标检测解决什么问题

目标检测同时回答两个问题：

  • 图片中有什么目标。
  • 每个目标位于什么位置。

因此输出通常包含：

  • 类别
  • 边界框
  • 置信度

2. 目标检测和图像分类的区别

图像分类通常为整张图片输出一个或多个类别；目标检测需要定位多个目标；语义分割则进一步为像素分配类别。

如果图片中存在多个同类目标，分类无法提供每个目标的位置，而检测可以输出多个边界框。

3. IoU

IoU 是预测框和真实框交集面积与并集面积的比值：

IoU 越大，表示两个框重合程度越高。它常用于：

  • 判断预测框是否为正样本
  • 计算检测指标
  • 非极大值抑制
  • 评价定位质量

4. NMS

同一个目标可能产生多个重叠预测框，NMS 用于保留最可信的框并抑制重叠框：

  1. 按置信度从高到低排序。
  2. 保留最高分框。
  3. 删除与该框 IoU 超过阈值的其他框。
  4. 重复处理剩余框。

阈值过低可能误删相邻目标；阈值过高可能保留重复框。密集目标场景可能需要 Soft-NMS 或其他改进策略。

5. 一阶段和两阶段检测器

一阶段检测器

直接从特征图预测类别和边界框，例如 YOLO 系列。

优点：

  • 推理速度快
  • 结构相对直接
  • 适合实时场景

缺点：

  • 小目标和密集目标处理可能更困难
  • 速度和精度需要权衡

两阶段检测器

先生成候选区域，再对候选区域进行分类和边界框精修。

优点：

  • 定位和分类精度通常较好
  • 复杂场景适应能力较强

缺点：

  • 推理速度和结构复杂度通常更高

6. YOLO 的基本思想

YOLO 将目标检测视为一次前向传播完成的预测任务，通常包含：

  • Backbone：提取图像特征。
  • Neck：融合不同尺度特征。
  • Head：预测类别、位置和置信度。

多尺度特征对小目标检测很重要，因为小目标在深层特征图中可能已经丢失大量空间信息。

面试中不要只说“YOLO 很快”，还要解释它为什么快，以及速度提升可能带来的精度和小目标检测权衡。

7. Precision、Recall 和 mAP

设：

  • TP：正确检测出的目标
  • FP：错误检测出的目标
  • FN：漏检目标

指标定义：

Precision 高表示误检少；Recall 高表示漏检少。两者通常存在权衡。

AP 是某个类别在 Precision-Recall 曲线下的面积；mAP 是多个类别 AP 的平均值。计算 mAP 时还需要明确 IoU 阈值，例如 mAP@0.5 或多个 IoU 阈值范围下的平均指标。

8. 检测模型常见问题

漏检

可能原因：

  • 目标过小
  • 图像质量差
  • 训练数据不足
  • 正负样本不平衡
  • 置信度阈值过高
  • NMS 参数不合适

误检

可能原因：

  • 背景与目标外观相似
  • 训练标签不准确
  • 类别定义不清
  • 置信度阈值过低
  • 训练集和实际场景分布不同

定位不准

可能原因：

  • 边界框标注质量差
  • 回归损失不合适
  • 输入分辨率过低
  • 目标形状与训练数据差异较大

二十七、语义分割

1. 分割任务类型

语义分割

为每个像素分配类别，同一类别的不同实例不会被区分。

实例分割

不仅识别类别，还区分同一类别的不同目标实例。

全景分割

同时处理可数目标和不可数背景，结合语义分割和实例分割能力。

2. U-Net

U-Net 采用编码器和解码器结构：

  • 编码器逐步下采样，提取高层语义特征。
  • 解码器逐步上采样，恢复空间分辨率。
  • 跳跃连接把浅层的细节信息传递给解码器。

跳跃连接解决了深层网络中空间细节丢失的问题，特别适合医学图像和像素级预测场景。

3. 分割损失函数

交叉熵

适合多分类像素预测，但类别极不平衡时，背景类别可能占据过大权重。

Dice Loss

关注预测区域和真实区域的重叠程度，对小目标和类别不平衡通常更友好。

Focal Loss

降低容易样本的权重，增加困难样本的关注程度。

实际项目中可能组合交叉熵和 Dice Loss，以同时兼顾像素分类稳定性和区域重叠效果。

4. 分割指标

  • Pixel Accuracy：预测正确的像素占比。
  • IoU：预测区域与真实区域的交并比。
  • Dice：预测区域与真实区域的重叠程度。
  • mIoU：各类别 IoU 的平均值。

Pixel Accuracy 在背景占比很高时可能产生误导，因此要结合 IoU、Dice 和各类别指标共同判断。

5. 分割常见问题

  • 边界模糊：需要更高分辨率特征或边界损失。
  • 小目标漏分：需要多尺度特征和合适采样策略。
  • 背景占比过高：需要类别权重或区域损失。
  • 标注边界不一致：模型上限受标签质量限制。
  • 预测结果出现孔洞：可以使用后处理或改进损失。

二十八、图像增强

1. 图像增强的目标

图像增强可以有两种含义：

  • 训练阶段的数据增强：增加样本变化，提高泛化能力。
  • 推理阶段的图像恢复：改善噪声、模糊、分辨率或对比度。

面试时应先确认问题指的是哪一种。

2. 数据增强

常见方式：

  • 随机裁剪
  • 翻转
  • 旋转
  • 缩放
  • 颜色抖动
  • 加噪声
  • 模糊
  • Mixup
  • Mosaic

增强必须符合真实数据分布。对于文字、方向或医学图像，随意翻转和旋转可能改变语义，甚至产生错误标签。

检测和分割任务中，图像变换必须同步变换边界框或像素掩码，否则会造成标签错位。

3. 去噪、去模糊和超分辨率

  • 去噪：减少随机噪声，尽量保留真实边缘。
  • 去模糊：恢复运动模糊或失焦造成的细节损失。
  • 超分辨率：从低分辨率图像恢复高分辨率结果。

这些任务存在不适定性：不同的高质量图像可能生成相似的低质量图像，因此模型恢复出的细节不一定是原始真实细节。

4. PSNR 和 SSIM

PSNR 基于像素误差衡量重建质量，计算简单，但不一定符合人眼感知。

SSIM 从亮度、对比度和结构等方面比较图像，更接近结构相似性，但也不能完全代表主观质量。

图像增强效果不能只看一个指标，还要结合：

  • 视觉质量
  • 任务下游指标
  • 边缘保真度
  • 细节真实性
  • 推理速度

二十九、模型训练与调优

1. 训练集、验证集和测试集

  • 训练集：用于更新模型参数。
  • 验证集：用于选择模型、调参和早停。
  • 测试集：用于最终评估，不能反复用于调参。

数据划分时要避免数据泄漏。例如同一对象、同一视频连续帧或同一病人数据同时出现在训练集和测试集，会让指标虚高。

2. 过拟合和欠拟合

过拟合表现为训练指标很好，但验证或测试指标较差。

解决方式：

  • 增加数据
  • 数据增强
  • 减小模型复杂度
  • 加入权重衰减
  • Dropout
  • 早停
  • 使用迁移学习

欠拟合表现为训练集和验证集效果都不好，可能需要：

  • 提高模型容量
  • 延长训练
  • 调整学习率
  • 改进特征和输入
  • 减弱过强的正则化

3. 调参顺序

推荐顺序：

  1. 先验证数据和标签是否正确。
  2. 使用小数据集过拟合测试，确认训练链路正确。
  3. 确认损失能够下降。
  4. 调整学习率和 Batch Size。
  5. 再处理模型规模和正则化。
  6. 最后进行数据增强和更复杂的结构改造。

如果一个模型连很小的数据集都无法拟合，优先排查标签、损失、输出维度、数据预处理和训练代码，而不是马上换更大的模型。

4. 迁移学习

迁移学习使用已有模型参数作为初始化，适合目标数据较少或任务与已有数据相关的场景。

常见策略：

  • 冻结 Backbone，只训练任务头。
  • 先冻结后逐步解冻。
  • 使用较小学习率微调整个模型。
  • 根据目标域和源域差异决定冻结范围。

如果目标数据与预训练数据差异很大，完全冻结特征提取层可能限制模型效果。

5. 实验可复现性

需要固定或记录：

  • 随机种子
  • 数据划分
  • 模型配置
  • 优化器和学习率
  • Batch Size
  • 数据增强
  • 代码版本
  • 依赖版本
  • 硬件和训练时间

固定随机种子也不能保证所有 GPU 操作绝对确定，但可以显著提高实验可比性。

三十三、第五部分：AI Agent 与 LangGraph

这一部分对应简历中的 AI Agent 基本架构、任务规划、工具调用、工作流编排、状态管理、Human-in-the-loop 和 LangGraph 多节点流程。

1. 什么是 AI Agent

AI Agent 是能够根据目标理解当前状态、进行决策、调用工具并根据结果继续执行的系统。

一个完整 Agent 通常包含：

  • 模型：理解输入并生成决策或动作。
  • 状态：保存当前任务上下文和中间结果。
  • 工具：访问数据库、接口、文件或其他系统。
  • 规划：决定下一步做什么。
  • 执行器：真正执行模型决定的动作。
  • 观察结果：读取工具返回结果并继续判断。
  • 终止条件：判断任务是否完成或需要人工介入。

Agent 不等于“调用一次大模型”。如果流程固定、步骤明确，普通工作流往往比 Agent 更稳定；只有在需要动态决策、工具选择或多步执行时，Agent 的价值才明显。

2. Agent 和普通工作流的区别

普通工作流

流程通常由程序预先确定：

优点：

  • 可预测
  • 易测试
  • 易审计
  • 成本和延迟容易估计

Agent

Agent 可以根据任务和中间结果动态选择下一步：

优点：

  • 对复杂任务更灵活
  • 能根据结果动态调整
  • 可以组合多个工具

缺点：

  • 输出不稳定
  • 成本和延迟难以预测
  • 可能循环或调用错误工具
  • 更难测试和审计

工程上常采用“确定性工作流 + 局部 Agent 决策”的方式，把模型的自由度限制在真正需要动态判断的节点。

3. ReAct 思路

ReAct 将推理和行动结合起来，典型循环是：

工程实现中不应直接暴露模型的内部思维过程，而应保存结构化的决策、工具调用参数、工具结果和最终结论。

4. 任务规划

任务规划是把用户目标转换为可执行步骤。

常见规划方式：

  • 直接执行：任务简单时直接调用工具。
  • 任务分解：把复杂目标拆成多个子任务。
  • 规划后执行：先生成计划，再逐步执行。
  • 动态规划：每执行一步，根据结果重新决定下一步。
  • 规划执行器：规划器负责计划，执行器负责完成具体动作。

5. 什么时候需要规划

适合规划的场景：

  • 任务包含多个依赖步骤。
  • 后一步需要使用前一步的结果。
  • 不同输入可能需要不同工具组合。
  • 任务目标较宽泛，需要先澄清和拆解。

不适合复杂规划的场景：

  • 只有一个明确工具调用。
  • 步骤固定且可以直接编码。
  • 任务要求强确定性和严格审计。
  • 规划成本超过任务本身的收益。

6. 工具调用流程

工具调用通常包含：

  1. 模型识别需要外部能力。
  2. 根据工具 Schema 生成工具名和参数。
  3. 程序校验工具名和参数。
  4. 执行工具。
  5. 将结果以结构化形式返回模型或工作流。
  6. 根据结果继续执行或结束。

工具调用不能只依赖 Prompt 约束，还必须在代码层做：

  • 工具白名单
  • 参数类型校验
  • 权限检查
  • 超时限制
  • 访问范围限制
  • 结果大小限制
  • 审计日志

7. 工具 Schema

一个好的工具定义应明确：

  • 工具名称
  • 工具用途
  • 参数名称和类型
  • 必填参数
  • 枚举范围
  • 默认值
  • 返回结构
  • 可能的错误
  • 是否有副作用

工具描述太模糊会导致模型选择错误；工具描述太多或工具数量过多，会增加选择难度和上下文成本。

8. 工具调用的安全问题

高风险工具包括：

  • 删除数据
  • 修改数据库
  • 发送邮件或消息
  • 执行命令
  • 修改权限
  • 发起支付
  • 访问敏感文件

安全措施：

  • 最小权限。
  • 只允许访问指定资源。
  • 对危险动作增加人工确认。
  • 对参数进行服务端校验。
  • 采用沙箱限制命令和文件访问。
  • 记录调用者、工具、参数、结果和时间。
  • 为重复执行设计幂等机制。

不能把用户输入直接拼接成 SQL、Shell 命令或高权限工具参数。

三十四、LangGraph 的核心概念

1. Graph

LangGraph 使用图来表达多步骤 Agent 或工作流：

  • 节点表示一个处理步骤。
  • 边表示节点之间的流转关系。
  • 条件边根据状态决定下一步。
  • 循环边允许反复执行和修正。
  • 结束节点表示任务完成。

图结构比单个大 Prompt 更容易表达复杂流程，也便于插入校验、重试和人工审批节点。

2. State

State 是图执行过程中共享的结构化状态，例如：

  • 用户目标
  • 当前任务阶段
  • 已生成的计划
  • 工具调用记录
  • 工具返回结果
  • 中间推理结论
  • 错误信息
  • 审批状态
  • 重试次数

状态设计应避免无边界地累积全部历史内容，需要区分：

  • 当前执行所需的短期状态。
  • 可长期保存的业务数据。
  • 仅用于日志和审计的执行记录。

3. Node

节点是一个相对独立的处理单元，可以负责：

  • 解析用户意图
  • 生成计划
  • 调用模型
  • 执行工具
  • 校验结果
  • 请求人工审批
  • 格式化最终响应

一个节点应尽量职责单一，避免一个节点同时负责规划、工具执行、数据库写入和最终响应。

条件判断最好基于结构化状态，而不是从自然语言中模糊匹配。

5. 循环和终止条件

Agent 循环必须明确：

  • 最大循环次数
  • 最大执行时间
  • 最大 Token 或费用预算
  • 工具调用次数上限
  • 成功条件
  • 失败条件
  • 人工接管条件

没有终止条件的 Agent 可能无限调用模型或工具，产生高额成本和不可控副作用。

6. Reducer 和状态更新

多个节点可能同时更新同一类状态。状态更新需要明确：

  • 是覆盖旧值还是追加新值。
  • 多个更新发生冲突时如何合并。
  • 列表是否允许重复。
  • 时间线是否需要保持顺序。
  • 更新失败时是否回滚。

例如工具消息通常适合追加，当前阶段和错误状态通常适合覆盖。状态更新规则必须稳定，否则重试和恢复时可能得到不同结果。

7. Checkpoint 和持久化

Checkpoint 用于保存图执行过程中的状态快照，支持：

  • 中断后恢复
  • 失败重试
  • 人工审批后继续
  • 查看历史执行状态
  • 调试特定节点

持久化时需要考虑：

  • 状态数据是否包含敏感信息。
  • 快照版本如何兼容。
  • 多次恢复是否会重复执行副作用。
  • 状态保存成功但外部动作已经完成时如何处理。

8. Durable Execution

可恢复执行要求系统在异常、重启或暂时不可用后，能够从可靠的状态继续，而不是从头重复所有步骤。

要做到这一点，需要：

  • 节点状态可序列化。
  • 外部动作有执行记录。
  • 副作用操作具备幂等性。
  • 每个步骤有明确状态。
  • 重试次数和错误类型可追踪。

仅保存模型上下文不等于真正可恢复，因为数据库写入、消息发送等外部副作用可能已经发生。

三十五、Human-in-the-loop

1. 为什么需要人工介入

以下场景通常适合人工审批：

  • 高风险数据修改
  • 对外发送重要信息
  • 权限变更
  • 低置信度结果
  • 多次自动修正仍然失败
  • 业务规则无法自动判断

Human-in-the-loop 不是让人参与每一步，而是在风险边界处增加确认和纠偏。

2. 人工审批流程

一个可审计的审批流程应包含：

  1. Agent 生成待审批动作。
  2. 展示动作、参数、影响范围和依据。
  3. 人工批准、拒绝或修改。
  4. 保存审批人和审批时间。
  5. 恢复图执行。
  6. 记录最终结果。

审批界面不能只显示“是否继续”，还应让审批人了解即将发生的副作用。

3. 中断和恢复

中断后需要保存：

  • 当前图节点
  • 当前状态
  • 待审批动作
  • 请求用户或任务 ID
  • 过期时间
  • 恢复权限

恢复时必须再次校验权限和资源状态，不能盲目执行中断前生成的旧参数。

三十六、Agent 的可靠性与可观测性

1. 超时和重试

需要区分错误类型：

  • 网络暂时失败：可以有限重试。
  • 服务限流：按照退避策略重试。
  • 参数错误：修正参数或直接失败。
  • 权限错误：不能盲目重试。
  • 业务冲突：需要重新读取状态。
  • 不可恢复错误：进入人工处理。

重试必须设置：

  • 最大次数
  • 超时时间
  • 退避间隔
  • 抖动时间
  • 幂等策略

2. 日志和追踪

Agent 系统至少应记录：

  • 请求 ID
  • 用户或任务 ID
  • 图运行 ID
  • 当前节点
  • 模型名称和版本
  • 输入输出 Token
  • 工具名称和参数摘要
  • 工具耗时
  • 错误类型
  • 重试次数
  • 最终结果

敏感内容需要脱敏，不能为了调试把完整密钥、个人信息或全部业务数据写入日志。

3. 成本和延迟控制

常见优化：

  • 简单任务使用小模型或固定流程。
  • 限制上下文长度。
  • 缓存稳定结果。
  • 减少无意义的重复规划。
  • 合并可并行执行的工具调用。
  • 为单次任务设置 Token、时间和费用预算。
  • 对工具结果进行摘要而不是无限追加全文。

并行执行时要确认工具之间没有写冲突，也要定义部分失败如何处理。

4. Agent 测试

测试不应只验证最终自然语言答案，还应验证：

  • 是否选择正确工具。
  • 工具参数是否符合 Schema。
  • 条件边是否走了正确分支。
  • 失败后是否重试或转人工。
  • 循环是否能够终止。
  • 状态更新是否正确。
  • 外部副作用是否只执行一次。
  • 不同模型输出变化时流程是否仍然稳定。

可以使用固定模型响应、Mock 工具、模拟超时和故障注入进行测试。

三十七、Agent 设计取舍

1. 单 Agent 和多 Agent

单 Agent：

  • 结构简单
  • 状态容易管理
  • 调试成本较低

多 Agent：

  • 可以按角色拆分能力
  • 适合复杂任务和专业分工
  • 通信和状态协调更复杂
  • 成本、延迟和失败点增加

不能因为“多 Agent”听起来复杂就盲目采用。先判断任务是否真的需要角色隔离、并行处理或独立工具集。

2. 模型决策和代码决策

适合交给模型：

  • 自然语言理解
  • 模糊意图判断
  • 工具选择
  • 结果总结

适合交给代码：

  • 权限判断
  • 金额和数量校验
  • 状态机约束
  • 重试次数
  • 安全规则
  • 数据库事务
  • 最终副作用确认

工程上应把不可接受的风险从模型决策中拿出来，用确定性代码控制。

1. Git 的基本模型

Git 主要包含：

  • 工作区：当前正在修改的文件。
  • 暂存区：下一次提交准备包含的内容。
  • 本地仓库：已经提交的对象和历史。
  • 远程仓库：团队或服务器上的共享历史。

一次提交通常记录一组文件状态和父提交关系。Git 保存的是内容和历史，不只是简单复制整个目录。

2. 分支、合并和变基

分支

分支本质上是指向某个提交的可移动引用。创建分支不会复制整个项目，因此成本较低。

Merge

Merge 将两个历史合并，通常会产生一个合并提交，能够保留分支的真实分叉关系。

Rebase

Rebase 将当前分支的提交重新应用到新的基准提交之上，使历史更线性。

公共分支上的历史不应随意 Rebase 或强制推送，因为这会改变其他人的提交基线。个人未共享分支可以使用 Rebase 整理提交。

3. 常见 Git 操作

  • git status：查看工作区和暂存区状态。
  • git diff：查看未暂存修改。
  • git diff --cached：查看已暂存修改。
  • git add：将修改放入暂存区。
  • git commit：创建本地提交。
  • git fetch：获取远程更新但不自动合并。
  • git pull：获取并合并或变基远程更新。
  • git push：将本地提交推送到远程。
  • git log：查看提交历史。

面试中要能解释：fetch 不会直接修改当前分支，而 pull 通常包含 fetch 加上合并或变基。

4. Reset、Revert 和 Restore

reset

移动当前分支指针，可改变提交历史。软重置保留暂存内容，混合重置保留工作区内容，硬重置可能丢弃本地修改。

revert

创建一个新的反向提交，用来抵消历史提交，适合已经推送到公共分支的情况。

restore

主要用于恢复工作区或暂存区文件，避免把“撤销文件修改”和“重写提交历史”混为一谈。

5. 冲突处理

发生冲突时：

  1. 查看冲突文件。
  2. 理解双方修改意图。
  3. 手动保留正确内容。
  4. 删除冲突标记。
  5. 运行格式检查和测试。
  6. 标记冲突已解决。
  7. 完成合并或变基。

不能只根据“保留当前”或“保留对方”机械解决，因为冲突通常反映了业务逻辑差异。

6. Git 面试注意点

  • 提交应保持单一目的，方便 Review 和回滚。
  • 不要提交密钥、.env、大体积构建产物和临时文件。
  • .gitignore 只能忽略未跟踪文件，已经跟踪的文件需要额外处理。
  • 共享分支避免强制推送。
  • 发生错误时优先保留现场，不要直接删除工作区。
  • 重要操作前先使用 git status 和 git log 确认当前分支。

四十三、Docker

1. Image 和 Container

Image 是可复用的只读模板，通常由多层文件系统组成；Container 是镜像运行后的实例，包含运行时状态和可写层。

镜像应尽量：

  • 小
  • 可复现
  • 少包含无关工具
  • 固定关键依赖版本
  • 不包含密钥

2. Dockerfile

常见指令：

  • FROM：指定基础镜像。
  • WORKDIR：设置工作目录。
  • COPY：复制文件。
  • RUN：构建阶段执行命令。
  • ENV：设置环境变量。
  • EXPOSE：声明端口用途。
  • CMD：默认启动命令。
  • ENTRYPOINT：固定入口。

RUN 发生在构建阶段，CMD 和 ENTRYPOINT 主要影响容器启动阶段。Dockerfile 中的命令顺序会影响缓存命中和最终镜像层。

3. 镜像构建优化

  • 先复制依赖清单并安装依赖，再复制经常变化的业务代码。
  • 使用 .dockerignore 排除 .git、缓存、测试产物和本地环境。
  • 合并不必要的构建步骤。
  • 使用多阶段构建分离编译环境和运行环境。
  • 使用适合运行时的轻量基础镜像。
  • 清理包管理器缓存。

多阶段构建可以避免把编译器、测试工具和源代码带入最终运行镜像。

4. Volume 和 Network

Container 的可写层不适合保存需要长期保留的数据。数据库、上传文件和日志等持久化数据通常使用 Volume 或外部存储。

Docker Network 用于容器之间通信。容器之间通常通过服务名发现，而不是依赖不断变化的容器 IP。

5. 环境变量和配置

镜像应该尽量保持通用，环境差异通过运行参数或外部配置注入。

需要区分：

  • 构建时配置：影响镜像生成。
  • 运行时配置：影响具体容器运行。

密钥、数据库密码和 Token 不应通过 Dockerfile 的 ENV 固化在镜像中，因为镜像层可能被保留和导出。

6. 健康检查和优雅退出

健康检查需要区分：

  • 存活检查：进程是否还活着。
  • 就绪检查：是否已经可以接收流量。

应用关闭时应：

  • 停止接收新请求。
  • 等待正在处理的请求完成。
  • 关闭数据库和外部连接。
  • 刷新必要日志。
  • 在超时后强制退出。

7. Docker 安全

  • 使用非 root 用户运行。
  • 不在镜像中存放密钥。
  • 限制容器权限和资源。
  • 只暴露必要端口。
  • 定期扫描依赖和基础镜像漏洞。
  • 使用固定版本或摘要，避免基础镜像无意漂移。

四十四、pytest 工程实践

1. 测试分层

推荐把测试分成：

  • 快速单元测试：每次提交都运行。
  • 接口测试：验证路由、校验、状态码和响应结构。
  • 集成测试：验证数据库、缓存和消息组件。
  • 慢速端到端测试：在单独阶段运行。

分层可以让开发者快速获得反馈，也避免所有测试都依赖外部环境。

2. 接口测试

接口测试至少要覆盖：

  • 正常请求。
  • 缺少必填字段。
  • 错误类型和边界值。
  • 认证和权限失败。
  • 资源不存在。
  • 重复提交。
  • 内部依赖异常。
  • 返回结构和错误码。

测试不仅验证 HTTP 200，还要验证状态码、响应字段、数据库副作用和异常处理。

3. 测试替身

常见测试替身：

  • Dummy：只用于传递数据。
  • Stub：返回预设结果。
  • Mock：验证调用过程和参数。
  • Fake：功能简化但可运行的实现。

外部模型、HTTP 服务、时间、随机数和消息队列通常可以替换为测试替身。

4. Coverage 和测试质量

代码覆盖率只能说明哪些代码被执行过，不能证明测试一定有效。

更重要的是覆盖：

  • 关键业务分支
  • 异常路径
  • 权限边界
  • 数据边界
  • 重试和超时
  • 状态转换
  • 高风险副作用

测试需要避免只为提高覆盖率而写没有断言价值的测试。

四十五、日志排查

1. 好日志的基本要素

一条可排查日志通常包含：

  • 时间
  • 日志级别
  • 服务名
  • 环境
  • 请求 ID 或 Trace ID
  • 用户或任务 ID
  • 关键业务对象 ID
  • 操作名称
  • 耗时
  • 错误类型
  • 可安全记录的摘要

推荐结构化日志，便于检索和聚合，而不是只输出一段难以解析的长文本。

2. 日志级别

  • DEBUG：调试细节，不应默认长期打开。
  • INFO：正常关键流程。
  • WARNING：异常但系统仍可继续运行。
  • ERROR：当前操作失败，需要排查。
  • CRITICAL：可能影响整个服务或核心能力。

日志级别不能代替告警等级。一个频繁出现但被忽略的 ERROR 可能比偶发 CRITICAL 更值得处理。

3. 排查方法

遇到线上错误时：

  1. 先确认影响范围和开始时间。
  2. 通过请求 ID 找完整链路。
  3. 查看应用日志和异常堆栈。
  4. 检查依赖服务、数据库和消息队列。
  5. 对比最近发布、配置和流量变化。
  6. 确认是否存在资源耗尽或网络异常。
  7. 修复后验证指标和错误是否恢复。

不要只看最后一条报错，很多错误的根因出现在更早的超时、连接失败或配置变化中。

四十六、基础性能问题定位

1. CPU 高

可能原因：

  • 死循环
  • 计算量增加
  • 大量序列化和反序列化
  • 锁竞争
  • 正则表达式或算法退化
  • 日志量过大

排查步骤：

  • 确认是单个进程还是整体 CPU 升高。
  • 查看线程或进程占用。
  • 使用采样 Profiling 定位热点函数。
  • 对比请求量和发布版本。

2. 内存高或持续增长

可能原因：

  • 缓存无上限
  • 对象被长期引用
  • 读取大文件未流式处理
  • 队列积压
  • 连接或资源泄漏
  • 保存了不必要的计算图

排查时关注内存曲线是稳定高位还是持续增长，并结合堆快照和对象引用分析。

3. I/O 或网络慢

可能原因：

  • 磁盘吞吐不足
  • 数据库慢查询
  • 外部接口延迟
  • DNS 慢
  • TCP 重传
  • 响应体过大
  • 同步阻塞调用占用工作线程

需要把总延迟拆分为排队、网络连接、服务处理、数据库、外部依赖和响应传输几个部分。

4. 延迟指标

平均延迟容易被少量极端请求掩盖，通常还应观察：

  • P50：中位数体验。
  • P90：大多数请求上限。
  • P95：较高分位延迟。
  • P99：尾部延迟。

性能优化不能只看平均值，还要关注错误率、吞吐量、资源使用率和尾部延迟。

五十二、每日复习方法

建议每天安排三个环节：

第一环节：理解

阅读文档或课程，回答“它解决什么问题、如何工作、为什么这样设计”。

第二环节：实践

通过代码、SQL、命令、流程图或故障模拟验证概念。

第三环节：表达

脱离资料口述 30 秒和 2 分钟答案，并记录卡顿点。

建议每天至少完成：

  • 3 个基础概念。
  • 2 个高频面试题。
  • 1 个代码或故障排查练习。
  • 1 次不看资料的口述。

复习间隔

  • 当天：第一次理解和口述。
  • 第二天：不看资料复述。
  • 一周后：用追问方式复习。
  • 面试前：只看关键词和易错点。

不要每天只重新阅读长文档。真正的掌握标准是能从关键词恢复出完整解释。
