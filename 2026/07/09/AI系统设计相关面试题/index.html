AI 系统设计相关面试题

说明：问题根据 JavaGuide《AI 系统设计面试题总结》页面中的高频题意整理，答案由本文重新生成，偏生产级 AI 应用工程实践。

一、生产级 AI 应用架构

1. Prompt Demo 到生产级 AI 系统最大的差距是什么？

Prompt Demo 证明的是模型“能答一次”，生产系统要证明的是“长期稳定、可控、可观测、可回滚地回答”。

Demo 阶段通常只关注 Prompt 和模型效果，但生产系统还要解决：

  • 鉴权、租户隔离和权限控制。
  • Prompt、模型、知识库和工具版本管理。
  • RAG、Memory、Tool 的边界治理。
  • 超时、重试、限流、熔断和降级。
  • 结构化输出校验和安全过滤。
  • Trace、日志、成本、质量评测和回放。
  • 灰度发布、回滚和失败样本回流。

面试中可以这样总结：

Demo 是能力验证，生产系统是工程治理。真正的 AI 系统设计不是写一个 Prompt，而是设计一条可观测、可评测、可治理的端到端链路。

2. 如何设计一个生产级 AI 应用的整体架构？

生产级 AI 应用可以按分层架构设计：

各层职责：

  • 入口层：鉴权、租户、限流、参数校验、请求分类。
  • 编排层：判断走普通问答、RAG、Agent、工具调用还是异步任务。
  • Context 层：组装系统规则、历史、检索证据、记忆、工具说明。
  • RAG/Memory/Tool 层：分别管理共享知识、长期偏好和真实业务动作。
  • 模型网关层：模型路由、供应商适配、fallback、Token 预算、成本归因。
  • 输出层：结构化解析、业务校验、安全过滤、引用校验。
  • 评测观测层：Trace、日志、指标、Golden Set、线上反馈和回放。

面试中可以回答：

我会先明确业务目标和约束，再按入口、编排、上下文、知识与工具、模型网关、输出校验、观测评测来拆架构，最后补充稳定性、安全、成本、灰度和回滚。

关键点是每一步都要可观测。出现问题时，要能定位是入口参数、检索、Prompt、模型、工具、输出解析还是安全策略导致。

面试中可以总结：

AI 请求链路不是“后端调模型”，而是从鉴权、编排、上下文、模型网关到输出校验和 Trace 记录的一整套工程链路。

4. 入口层、编排层、Prompt/Context、RAG/Memory/Tool、模型网关、评测观测分别负责什么？

入口层负责把请求安全地接进系统：

  • 鉴权、租户识别、限流、参数校验、请求大小控制。

编排层负责决定任务怎么走：

  • 普通问答、RAG、Agent、工具调用、异步任务、人工介入。

Prompt/Context 层负责准备模型输入：

  • Prompt 模板、版本、变量校验、历史消息、检索证据、工具说明、记忆。

RAG/Memory/Tool 层分别处理三类上下文：

  • RAG 管共享知识。
  • Memory 管用户或项目长期偏好。
  • Tool 管真实业务查询和动作。

模型网关负责统一模型调用：

  • 模型路由、供应商适配、限流、fallback、熔断、Token 预算、成本归因。

评测观测层负责持续改进：

  • Trace、日志、指标、Golden Set、LLM-as-Judge、人工反馈、灰度和回放。

面试中可以回答：

生产级 AI 架构的关键是分层清楚，每层只解决自己的问题，避免把知识、记忆、工具、安全和评测混在一段 Prompt 里。

5. 同步、流式、异步三种模式怎么选？

同步适合短任务，流式适合长输出交互，异步适合耗时长或可离线处理的任务。

同步模式适合：

  • 分类、抽取、短问答。
  • 延迟可控。
  • 用户需要立即拿到完整结果。

流式模式适合：

  • Chat、写作、代码生成、长文总结。
  • 需要降低首字延迟。
  • 用户可能中途停止。

异步模式适合：

  • 长报告生成。
  • 批量文档处理。
  • 大规模 Agent 任务。
  • 多工具、多步骤、高成本任务。

面试中可以总结：

短任务同步，长回答流式，长耗时任务异步。选型核心看用户等待体验、任务耗时、是否可中断、是否需要后台重试和结果通知。

6. 为什么生产系统需要模型网关？

模型网关是业务系统和模型供应商之间的统一治理层。

需要模型网关的原因：

  • 屏蔽不同供应商 API 差异。
  • 统一鉴权、限流、超时、重试、熔断。
  • 支持模型路由和 fallback。
  • 管理 Token 预算和成本归因。
  • 统一日志、Trace、指标和审计。
  • 支持 Prompt 版本和模型版本灰度。
  • 避免业务代码直接耦合供应商接口。

面试中可以回答：

模型网关把大模型调用从“一个外部 API”治理成“可控的基础能力”，是生产 AI 应用稳定性、成本和可观测性的核心。

7. Prompt 为什么要做版本管理？

Prompt 是 AI 应用的核心逻辑之一，变化会直接影响模型行为。

需要版本管理的原因：

  • 方便回放线上问题。
  • 支持灰度和 A/B 测试。
  • 能把质量变化关联到具体 Prompt 版本。
  • 便于回滚。
  • 避免多人修改导致行为不可追踪。
  • 让评测结果和 Prompt 版本绑定。

Prompt 版本管理应记录：

  • 模板内容。
  • 变量列表。
  • 适用场景。
  • 关联模型版本。
  • 发布时间。
  • 评测结果。
  • 变更人和变更原因。

面试中可以总结：

Prompt 在 AI 应用里相当于业务逻辑代码，必须版本化、可评测、可灰度、可回滚。

8. RAG 和 Memory 有什么区别？为什么不能混在一起治理？

RAG 管外部共享知识，Memory 管个体或任务相关的长期记忆。

RAG 的特点：

  • 来源通常是文档、知识库、数据库。
  • 强调权威性、可引用、权限控制。
  • 更新由知识库流程管理。

Memory 的特点：

  • 来源通常是用户行为、对话、项目经验。
  • 强调个性化、连续性、偏好沉淀。
  • 需要防污染、过期、冲突处理。

不能混在一起的原因：

  • 权限边界不同。
  • 生命周期不同。
  • 可信度不同。
  • 更新方式不同。
  • 进入上下文的优先级不同。

面试中可以回答：

RAG 是“查资料”，Memory 是“记经验”。二者都能进入上下文，但治理方式完全不同，混在一起会带来权限、污染和可追溯问题。

9. Tool Calling 的安全边界在哪里？

Tool Calling 的安全边界在应用后端，而不是模型。

模型可以：

  • 判断是否需要工具。
  • 生成工具名和参数。
  • 根据工具结果继续回答。

模型不能：

  • 决定用户是否有权限。
  • 绕过业务校验。
  • 直接执行高风险动作。
  • 自行决定是否跳过确认。

后端必须做：

  • 用户鉴权。
  • 资源归属校验。
  • 参数类型和范围校验。
  • 幂等控制。
  • 高风险动作二次确认。
  • 工具调用审计。
  • 结果脱敏。

面试中可以总结：

模型只负责建议调用工具，真正的权限、参数、安全和副作用控制必须在后端强制执行。

10. AI 应用可观测要看哪些指标？

AI 应用可观测要覆盖质量、成本、延迟、稳定性和安全。

关键指标包括：

  • 请求指标：QPS、成功率、错误率、超时率。
  • 延迟指标：首 Token 时间、总耗时、检索耗时、工具耗时、模型耗时。
  • Token 指标：输入 Token、输出 Token、总 Token、上下文利用率。
  • 成本指标：按租户、用户、功能、模型、Prompt 版本归因。
  • 质量指标：用户反馈、解决率、引用准确率、结构化输出成功率。
  • RAG 指标：Recall@K、Context Precision、Faithfulness。
  • Agent 指标：任务完成率、工具调用成功率、循环次数。
  • 安全指标：拒答率、越权拦截、敏感信息命中、人工确认次数。

面试中可以回答：

AI 应用可观测不能只看接口成功率，还要看模型质量、Token 成本、Trace、检索证据、工具轨迹和安全事件。

11. LLM-as-Judge 能不能替代人工评测？

LLM-as-Judge 不能完全替代人工评测，它更适合做规模化辅助评测。

LLM-as-Judge 的优势：

  • 成本低于大规模人工。
  • 速度快。
  • 适合回归测试和样本初筛。
  • 能覆盖大量开放式回答。

局限：

  • 有位置偏差、长度偏差、表达偏好。
  • 可能无法判断领域事实。
  • 可能偏好流畅但错误的答案。
  • Judge 模型升级会影响评分稳定性。

生产中应该：

  • 用明确 Rubric。
  • 对关键样本人工标注。
  • 定期校准 Judge。
  • 结合规则校验和业务指标。
  • 高风险场景以专家评审为准。

面试中可以总结：

LLM-as-Judge 是评测加速器，不是真理来源。生产中要用人工样本、规则校验和线上反馈对它进行校准。

二、稳定性、成本与安全治理

1. AI 应用如何做超时、重试、限流、熔断和降级？

生产系统要分层治理：

  • 超时：入口、模型、RAG、工具、异步任务分别设置超时。
  • 重试：只对网络抖动、部分 5xx、临时限流做有限重试。
  • 限流：按 QPS、RPM、TPM、并发、租户预算、模型配额限制。
  • 熔断：供应商异常、错误率升高、延迟异常时快速阻断。
  • 降级：切低成本模型、减少上下文、关闭非关键工具、转人工。

关键是降级不能破坏业务安全和输出格式。高风险任务宁可失败或转人工，也不要盲目降级。

面试中可以回答：

AI 稳定性治理要按链路分层做超时、重试、限流、熔断和降级，并区分可恢复错误和不可恢复错误。

2. 为什么大模型调用限流不能只看 QPS？

大模型请求的资源消耗和 Token 数、输出长度、并发时间强相关。同样一个请求，可能消耗几百 Token，也可能消耗几十万 Token。

需要同时看：

  • QPS：入口请求频率。
  • RPM：每分钟请求数。
  • TPM：每分钟 Token 数。
  • 并发数：长生成占用连接和计算资源。
  • 租户预算：防止单个客户成本失控。
  • 模型配额：不同模型供应商限额不同。
  • 工具和 RAG 成本：一次请求可能触发多次调用。

面试中可以总结：

大模型限流的核心不是请求个数，而是资源消耗。QPS 只能控制入口流量，TPM、并发和预算才能控制真实成本和负载。

3. 如何设计模型 fallback 策略？什么时候不能自动降级？

fallback 策略要按任务风险分级。

可以 fallback 的场景：

  • 普通问答。
  • 文案生成。
  • 低风险总结。
  • 对模型能力差异不敏感的任务。

fallback 方式：

  • 同供应商不同模型。
  • 不同供应商备用模型。
  • 缩短上下文。
  • 返回缓存答案。
  • 降级为检索结果列表。

不能自动降级的场景：

  • 结构化输出强依赖特定能力。
  • 高风险法律、医疗、金融建议。
  • 工具调用参数生成。
  • 安全策略和拒答边界不同。
  • 模型降级后可能改变业务结论。

面试中可以回答：

fallback 不是简单换个便宜模型。要评估质量、格式、工具调用、安全边界和合规风险，高风险任务应转人工或失败，而不是自动降级。

4. Token 成本怎么归因到租户、用户、功能和 Prompt 版本？

成本归因要在模型网关或调用中台统一记录。

至少记录：

  • tenant_id。
  • user_id。
  • app_id。
  • feature_name。
  • request_id / trace_id。
  • model_name / model_version。
  • prompt_template_id / prompt_version。
  • input_tokens。
  • output_tokens。
  • cached_tokens。
  • tool_calls。
  • rag_chunks。
  • total_cost。

这样可以回答：

  • 哪个租户最耗钱。
  • 哪个功能成本最高。
  • 哪个 Prompt 版本导致 Token 暴涨。
  • 哪个模型性价比最好。
  • 哪些请求应该缓存或异步化。

面试中可以总结：

Token 成本要按租户、用户、功能、模型、Prompt 版本和请求链路归因，否则 AI 应用上线后很容易变成不可解释的成本黑洞。

5. 高风险工具调用为什么要做二次确认？

高风险工具调用可能产生真实业务副作用，例如：

  • 转账。
  • 退款。
  • 删除数据。
  • 发邮件。
  • 下单。
  • 修改权限。
  • 发布内容。

大模型可能误判意图、生成错误参数或受到 Prompt Injection 影响，所以不能让模型直接执行高风险动作。

二次确认应包括：

  • 展示操作对象。
  • 展示关键参数。
  • 展示影响范围。
  • 要求用户显式确认。
  • 后端再次校验权限和幂等。

面试中可以回答：

高风险工具调用的核心原则是人类确认、后端校验、动作可审计。模型可以建议动作，但不能绕过确认直接执行。

6. PII 脱敏、权限过滤、审计日志应该放在哪些环节？

PII 脱敏应放在多个位置：

  • 用户输入进入模型前。
  • RAG 文档进入上下文前。
  • 工具结果返回模型前。
  • 日志落库前。

权限过滤应放在检索和工具执行前：

  • RAG 检索前按租户和权限过滤。
  • 工具调用前校验用户身份和资源归属。
  • 输出前检查是否泄露无权限内容。

审计日志应覆盖完整链路：

  • 谁发起请求。
  • 使用了哪个模型和 Prompt 版本。
  • 召回了哪些文档。
  • 调用了哪些工具。
  • 参数摘要是什么。
  • 最终结果和安全拦截情况。

面试中可以总结：

脱敏要前置且贯穿链路，权限过滤要在检索和工具执行前强制做，审计日志要覆盖模型、证据、工具和输出。

7. Prompt 注入攻击在系统设计层面怎么防？

Prompt 注入是攻击者把恶意指令混入用户输入、网页、文档或工具结果中，诱导模型越权或泄密。

系统设计层面的防护：

  • 区分系统指令和不可信数据。
  • 外部文档只作为证据，不允许覆盖系统规则。
  • RAG 文档做来源可信度和权限过滤。
  • 工具调用在后端做鉴权和参数校验。
  • 高风险动作二次确认。
  • 最小化暴露敏感上下文。
  • 对工具结果脱敏。
  • 对输出做安全检测。
  • Trace 记录注入来源，便于回放。

面试中可以回答：

Prompt 注入不能只靠“请不要被攻击”这种 Prompt 防。系统必须用权限、隔离、最小暴露、工具校验、确认和审计来防。

8. 出现模型输出事故后，如何通过 Trace 回放定位问题？

Trace 回放要还原事故发生时的完整上下文。

需要记录：

  • 用户输入和会话上下文。
  • Prompt 模板和版本。
  • 模型名称、版本和参数。
  • RAG query、召回 chunk、分数、rerank 结果。
  • Memory 注入内容。
  • 工具调用参数和结果。
  • 输出解析和安全过滤结果。
  • 错误码、延迟、Token 和成本。

定位路径：

  1. 判断输入是否异常。
  2. 看 Prompt 版本是否变化。
  3. 看检索证据是否正确。
  4. 看工具结果是否错误。
  5. 看模型是否误读证据。
  6. 看输出校验是否漏拦。
  7. 用旧版本或候选版本回放对比。

面试中可以总结：

Trace 回放的价值是把一次模型事故从“玄学问题”变成可复现、可比较、可定位的工程问题。

三、评测与持续迭代

1. 为什么没有评测集就很难放心上线？

没有评测集，就无法判断 Prompt、模型、RAG、工具或参数改动到底是变好还是变坏。

AI 应用和传统系统不同：

  • 输出开放。
  • 模型有不确定性。
  • 小改动可能影响大量场景。
  • 线上问题难以完全靠单元测试发现。

评测集的作用：

  • 发布前回归。
  • 比较不同方案。
  • 防止质量退化。
  • 沉淀线上失败样本。
  • 支撑灰度和回滚决策。

面试中可以回答：

没有评测集，AI 应用上线就是靠感觉。生产系统必须用 Golden Set 和 Trace 回放证明改动没有明显退化。

2. Golden Set 如何覆盖正常路径、边缘场景、对抗样本和高权重失败？

Golden Set 应按场景分层构建。

正常路径：

  • 高频用户问题。
  • 核心业务流程。
  • 标准知识问答。

边缘场景：

  • 信息不足。
  • 问题歧义。
  • 超长输入。
  • 多轮上下文依赖。

对抗样本：

  • Prompt 注入。
  • 越权请求。
  • 要求泄露敏感信息。
  • 错误前提问题。

高权重失败：

  • 曾经线上出事故的问题。
  • 高价值客户问题。
  • 法律、金融、医疗、安全等高风险问题。

面试中可以总结：

Golden Set 不只是随机抽样，要覆盖高频、高价值、高风险和历史失败样本，并且带标准答案、证据或评分 Rubric。

3. 离线评测、Trace 回放、线上灰度分别放在发布流程的哪个阶段？

离线评测放在开发和合并前：

  • 用固定 Golden Set 快速判断改动是否退化。
  • 适合 Prompt、模型、检索参数变更。

Trace 回放放在发布前和事故复盘中：

  • 用真实历史请求验证新版本表现。
  • 适合回归线上失败案例。

线上灰度放在正式全量前：

  • 小流量验证真实用户分布。
  • 观察质量、成本、延迟、投诉、转人工率。

面试中可以回答：

发布流程可以是：开发阶段跑离线评测，发布前做 Trace 回放，正式上线前做线上灰度，失败样本再回流评测集。

4. RAG、Agent、结构化输出的评测指标为什么不能混用一套？

三类系统的失败模式不同。

RAG 要看：

  • 检索召回。
  • 排序质量。
  • 上下文相关性。
  • 答案忠实性。
  • 引用准确率。

Agent 要看：

  • 任务完成率。
  • 工具选择是否正确。
  • 参数是否正确。
  • 执行轨迹是否合理。
  • 是否安全处理副作用。

结构化输出要看：

  • JSON 是否可解析。
  • Schema 合规率。
  • 字段类型正确率。
  • 枚举合法率。
  • 业务校验通过率。

面试中可以总结：

RAG 评证据，Agent 评轨迹，结构化输出评格式和业务约束。指标混用会导致看似高分但实际不可用。

5. LLM-as-Judge 有哪些偏差？生产中怎么校准？

LLM-as-Judge 常见偏差：

  • 偏好长答案。
  • 偏好流畅表达。
  • 受答案顺序影响。
  • 对事实缺少证据时仍然打分。
  • 偏好和自身风格相近的回答。
  • 不同 Judge 版本评分漂移。

校准方式：

  • 使用明确 Rubric。
  • 隐藏模型名称。
  • 随机打乱答案顺序。
  • 提供参考答案和证据。
  • 多 Judge 或多次评分。
  • 用人工标注集定期校准。
  • 关键样本专家复核。

面试中可以回答：

LLM-as-Judge 可以规模化评测，但必须用人工样本、规则校验和明确 Rubric 校准，不能把它当绝对真值。

6. CI 自动评测怎么控制成本和耗时？

CI 中 AI 评测要分层：

  • PR 阶段：只跑小而关键的快速集。
  • 模块变更：只跑相关评测，例如改 RAG 跑检索集。
  • 夜间任务：跑大规模 Golden Set 和 Trace 回放。
  • 发布前：跑完整回归、成本和延迟评估。

控制成本的方法：

  • 固定模型和参数。
  • 缓存稳定样本结果。
  • 使用分层抽样。
  • 结构化任务优先用规则校验。
  • LLM-as-Judge 只用于必要场景。
  • 对分数设置容忍区间，避免微小波动阻断。

面试中可以总结：

CI 里的 AI 评测不能全量硬跑，要用快速核心集做阻断，用夜间和发布前任务保证覆盖度。

7. 线上质量下降时，如何判断是模型、Prompt、检索、工具还是数据分布变化导致？

定位要看版本和 Trace。

排查顺序：

  1. 看变更记录：模型、Prompt、检索配置、工具、知识库是否变更。
  2. 看数据分布：用户问题类型是否变化。
  3. 看 RAG Trace：召回证据是否正确，排序是否变化。
  4. 看 Prompt：模板和变量是否正确。
  5. 看模型输出：是否同证据不一致。
  6. 看工具轨迹：工具是否失败、参数是否异常。
  7. 做回放对比：用旧版本和新版本跑同一批样本。

面试中可以回答：

质量下降不能凭感觉判断，要把模型、Prompt、检索、工具、数据和知识库版本都绑定到 Trace 上，通过回放对比定位。

四、实时语音 Agent

1. 如何设计一个实时语音 Agent？

实时语音 Agent 不是 ASR、LLM、TTS 的简单串联，而是实时音频流系统。

核心链路：

架构重点：

  • 低延迟流式处理。
  • 明确状态机。
  • 支持用户打断。
  • 支持工具调用和上下文更新。
  • 记录音频、转写、模型、播放 Trace。
  • 做端云选型和降级策略。

面试中可以总结：

实时语音 Agent 的核心是低延迟、多状态、可打断的流式对话系统，而不是简单拼接语音识别和语音合成接口。

2. ASR、LLM、TTS、VAD 在语音系统中分别负责什么？

VAD 负责判断用户是否在说话：

  • 检测语音起止。
  • 判断静音。
  • 触发 ASR 和打断逻辑。

ASR 负责语音转文字：

  • 将音频流转成文本。
  • 支持中间结果和最终结果。

LLM 负责理解和决策：

  • 理解用户意图。
  • 管理对话上下文。
  • 调用工具。
  • 生成回复内容。

TTS 负责文字转语音：

  • 将模型回复转成音频。
  • 支持流式首包输出。
  • 控制音色、语速、情绪。

面试中可以回答：

VAD 管说话检测，ASR 管听懂，LLM 管理解和决策，TTS 管说出来。实时语音系统的难点是这几部分要以流式方式协同。

3. 实时语音 Agent 的端到端延迟主要来自哪里？

端到端延迟来自多个环节：

  • 音频采集和编码。
  • 网络传输。
  • VAD 判断等待。
  • ASR 首次转写和最终确认。
  • LLM 首 Token 延迟。
  • 工具调用耗时。
  • TTS 首包延迟。
  • 播放缓冲。

优化方向：

  • 使用流式 ASR。
  • 提前触发 LLM。
  • 减少 VAD 静音等待。
  • 使用流式 TTS。
  • 缓存常见回复。
  • 本地化 VAD 或轻量 ASR。
  • 控制工具调用超时。

面试中可以总结：

语音延迟不是单点问题，而是音频、VAD、ASR、LLM、工具、TTS 和播放缓冲叠加的结果，要分段监控和优化。

4. 用户打断时，系统应该如何取消播放、取消生成和更新上下文？

打断处理是语音 Agent 的关键能力。

用户打断时应做：

  • 立即停止当前 TTS 播放。
  • 取消或暂停正在生成的 LLM 请求。
  • 取消后续 TTS 合成。
  • 标记哪些内容已经播放给用户。
  • 未播放内容不要直接写入对话历史。
  • 将用户新语音作为新输入。
  • 更新状态为 interrupted 或 listening。

还要注意：

  • 如果工具调用已经执行，不能简单回滚，要记录状态。
  • 如果模型已生成但未播放，不应默认认为用户听到了。
  • 上下文要区分“已说出口”和“未说出口”。

面试中可以回答：

打断不是只停播放器，还要取消生成、处理未播放文本、更新对话状态，并避免把用户没听到的内容写进上下文。

5. listening、thinking、speaking、interrupted 这些状态如何管理？

可以用状态机管理语音 Agent。

典型状态：

  • listening：正在听用户说话。
  • transcribing：ASR 正在转写。
  • thinking：LLM 正在推理或调用工具。
  • speaking：TTS 正在播放。
  • interrupted：用户打断当前输出。
  • error：出现异常。

状态流转示例：

状态机要记录：

  • 当前轮次 ID。
  • ASR 最终文本。
  • LLM 请求 ID。
  • TTS 播放进度。
  • 是否被打断。
  • 已提交上下文。

面试中可以总结：

语音 Agent 必须用状态机管理听、想、说和打断，否则很容易出现重复回答、上下文错乱和播放状态不一致。

6. 云端 API、本地模型、端云混合怎么选？

云端 API 适合：

  • 快速上线。
  • 模型质量要求高。
  • 团队不想维护推理基础设施。
  • 访问外部大模型能力。

缺点是：

  • 网络延迟。
  • 成本不可控。
  • 数据合规压力。
  • 供应商依赖。

本地模型 适合：

  • 隐私和合规要求高。
  • 低延迟本地处理。
  • 成本可通过规模摊薄。
  • 可控性要求高。

缺点是：

  • 模型效果和维护成本压力。
  • GPU、部署、升级复杂。

端云混合 适合：

  • 本地做 VAD、唤醒、降噪、部分 ASR。
  • 云端做高质量 LLM 或 TTS。
  • 在体验、成本和隐私之间平衡。

面试中可以回答：

云端上线快，本地可控强，端云混合通常更适合生产语音 Agent，因为可以把低延迟和隐私敏感环节放本地，把复杂推理放云端。

7. Speech-to-Speech API 适合什么场景？有哪些取舍？

Speech-to-Speech API 直接处理语音输入并输出语音，减少 ASR、LLM、TTS 分段集成复杂度。

适合：

  • 低延迟自然对话。
  • 语音助手。
  • 陪练、客服、实时问答。
  • 对语气、停顿、情绪连续性要求高的场景。

取舍：

  • 优点是链路更短、体验更自然、端到端优化空间更大。
  • 缺点是中间文本、工具调用、审计和可控性可能更难做。
  • 如果业务需要强结构化、强审计、复杂工具调用，分段式 ASR + LLM + TTS 可能更可控。

面试中可以总结：

Speech-to-Speech 适合追求自然低延迟语音体验的场景，但如果需要强可控、强审计和复杂业务编排，分段式架构更容易治理。

8. 语音 Agent 的可观测指标应该包括哪些？

语音 Agent 要同时观测音频、模型、工具和用户体验。

关键指标：

  • VAD 误触发率和漏检率。
  • ASR 首字延迟、最终转写延迟、字错率。
  • LLM 首 Token 延迟和总生成耗时。
  • 工具调用耗时和失败率。
  • TTS 首包延迟、播放中断率。
  • 端到端首响时间。
  • 用户打断率。
  • 重复回答率。
  • 会话完成率。
  • 用户满意度。
  • 每轮成本。
  • 网络断连率。

面试中可以回答：

语音 Agent 可观测不能只看接口耗时，要按 VAD、ASR、LLM、工具、TTS、播放和打断分段记录，才能定位体验问题。
