## 一、先抓主线：模型输出为什么会变

大模型每次回答都不是“直接想到一句完整的话”，而是：

1. 先把输入拆成 Token。
2. 在上下文窗口里读取这些 Token。
3. 为下一个 Token 计算概率分布。
4. 根据采样参数选出一个 Token。
5. 把新 Token 接回上下文，继续下一轮生成。

所以，输出质量主要受三类因素影响：

- 输入内容本身是否清晰。
- 上下文窗口是否足够、是否被噪声占满。
- 采样参数是否让模型过于保守或过于发散。

## 二、Token 是什么，为什么它直接决定成本

Token 不是“字符数”，也不是“单词数”，而是模型内部处理文本的最小单位。

简单理解：

- 一个英文单词可能对应 1 个或多个 Token。
- 一句中文也会被拆成多个 Token。
- 代码、表格、JSON、URL 往往比普通自然语言更“吃 Token”。

### 关键结论

#### 1. Token 越多，成本通常越高

大模型 API 一般按输入 Token 和输出 Token 分开计费。  
而且很多模型里，**输出 Token 往往比输入 Token 更贵**。

所以真正影响成本的不是“调用了一次”，而是：

- 你塞进去多少内容；
- 模型最后吐出来多少内容；
- 是否重复发送了大量固定上下文。

#### 2. Token 越多，延迟通常越高

输入越长，模型读取和编码越慢；  
输出越长，生成过程也越慢。

这也是为什么“能一句话问清楚，就不要塞十屏背景说明”。

#### 3. 多模态输入也要算 Token

图片、PDF、表格等多模态输入，本质上也会被转换为模型可处理的内部表示，最后仍然体现为 Token 开销。

工程上要有一个意识：

> 多模态不是“额外功能”，而是“额外成本 + 额外上下文占用”。

## 三、上下文窗口到底在限制什么

上下文窗口可以理解成模型一次调用时能“同时看到”的信息上限。

这个上限里要装下：

- system prompt
- 历史对话
- 用户当前输入
- 检索到的 RAG 文档
- 工具调用结果
- 模型自己的输出

### 一个很重要的现实

不是只有你的 prompt 占上下文，**整个调用链都在抢上下文空间**。

所以你以为“我只问了一句话”，实际上模型背后可能已经带上了：

- 系统规则；
- 几轮对话历史；
- 检索片段；
- 工具返回的大段 JSON。

### 上下文窗口的几个核心结论

#### 1. 长上下文不等于更好效果

上下文变长，意味着模型“能看到更多”，但不代表“就能更好地利用这些信息”。

常见问题：

- 重要信息被淹没在大量噪声里；
- 前面内容太长，后面有效指令不够突出；
- 检索内容太杂，模型反而抓不到重点。

#### 2. 真正的瓶颈不是“能不能塞进去”，而是“塞进去后还是否清晰”

很多时候不是窗口不够，而是上下文设计太差：

- 重复内容太多；
- 检索片段太长；
- 工具输出原样塞回，没有做裁剪；
- 历史消息没有摘要。

#### 3. 上下文溢出时，典型表现很明显

常见症状：

- 回答突然不再遵守前文要求；
- 忘记前面已经说过的限制；
- 只抓住最近的内容，忽略更早的重要信息；
- 输出被硬截断；
- RAG 明明检索到了资料，但回答像没看到一样。

## 四、Prompt Caching 为什么能省钱

如果你的应用里有大量重复前缀，比如：

- 固定 system prompt；
- 固定工具说明；
- 固定角色设定；
- 固定输出格式要求；

那么支持 Prompt Caching 的模型/平台，通常可以对这部分重复前缀做缓存。

### 本质

不是“模型变聪明了”，而是：

- 相同前缀不必每次都从头重复算一遍；
- 重复上下文在成本和延迟上会更省。

### 工程意义

如果你在做 Agent、RAG 或复杂工作流系统，Prompt Caching 往往比“再抠几句提示词”更值得优化。

## 五、一次调用怎么做 Token 预算

实战里不要只看模型官方窗口大小，要先做预算。

可以用这个简化思路：

```text
总上下文占用
= system prompt
+ 历史对话
+ 用户输入
+ 检索结果 / 工具结果
+ 预留输出空间
```

而成本可以粗略理解为：

```text
总成本
= 输入 Token 成本
+ 输出 Token 成本
- 可缓存前缀节省部分
```

### 经验建议

#### 1. 一定要给输出预留空间

很多人只算输入，不给输出留余量，最后就会出现：

- 输出被截断；
- JSON 没闭合；
- 列表答到一半停了。

#### 2. 工具返回结果不要原样全塞

例如数据库查询、搜索结果、RAG 文档、网页抓取内容，最好先做：

- 截断；
- 摘要；
- 去重；
- 结构化抽取。

#### 3. 历史对话要分层保留

不是每轮都保留完整历史。可以考虑：

- 最近几轮原文保留；
- 更早内容做摘要；
- 长期偏好单独存储。

## 六、采样参数为什么会改变回答风格

模型在生成每个 Token 时，并不是只有一个“唯一正确答案”，而是会得到一组候选概率。

采样参数的作用，就是决定：

> 到底是更保守地选高概率答案，还是允许模型做更发散的选择。

## 七、Temperature：控制“冒险程度”

`Temperature` 可以理解成模型输出的发散程度调节器。

### 一般规律

- `Temperature` 低：输出更稳定、更保守、更接近高概率答案。
- `Temperature` 高：输出更自由、更有变化，也更容易跑偏。

### 实战理解

#### 适合低温度的场景

- 结构化输出；
- 事实问答；
- 代码生成；
- SQL；
- 提取、分类、改写。

#### 适合略高温度的场景

- 文案草稿；
- 头脑风暴；
- 创意命名；
- 多风格表达。

### 一个常见误区

很多人把“回答不够好”归因到温度，实际上问题常常出在：

- 提示词不清楚；
- 上下文太脏；
- 检索内容不准。

温度只是风格调节器，不是万能修复器。

## 八、Top-p 和 Top-k：控制候选池大小

这两个参数本质上都在控制“模型能从多少候选 Token 里抽签”。

### Top-k

只保留概率最高的前 `k` 个候选。

例如：

- `top-k=1`：几乎就是每次都选最可能的那个。
- `top-k=50`：允许从前 50 个高概率候选里选。

### Top-p

不是固定候选数量，而是保留累计概率达到某个阈值的候选集合。

例如：

- `top-p=0.9`：保留累计概率达到 90% 的那一批候选。

### 实战建议

如果模型平台已经给了比较稳的默认值，通常不要同时大幅乱调 `temperature`、`top-p`、`top-k`。  
参数一起乱动，排查问题会很痛苦。

## 九、停止条件和截断风险

一条回答为什么会突然断掉？通常有三类原因：

- 达到了最大输出 Token 限制；
- 触发了停止符；
- 上下文预算耗尽。

### 工程上最常见的问题

- JSON 输出到一半断了；
- 表格只写了一半；
- Markdown 代码块没闭合；
- 列表中途停止。

### 解决思路

- 增加最大输出 Token；
- 精简输入上下文；
- 对结构化输出增加补全校验；
- 失败后自动重试或续写。

## 十、Penalty：解决重复和啰嗦

Penalty 参数常用于抑制模型反复说同样的话。

常见作用：

- 减少重复句式；
- 减少关键词反复出现；
- 降低“套话”堆积。

但它也不是越大越好。  
惩罚过强，可能让模型为了避免重复而选词奇怪，反而影响可读性。

## 十一、流式输出和首字延迟

流式输出并不会让模型“算得更快”，它主要改善的是用户体验。

### 你会感受到的变化

- 非流式：等全部生成完再看到结果；
- 流式：先看到前几个字，后面逐步出现。

### 工程意义

对聊天产品、Agent 面板、长回答场景，流式输出能显著降低用户的焦虑感。  
尤其在响应较长时，“先看到一点内容”通常比“完全黑屏等 10 秒”体验好得多。

## 十二、Logprobs 的实际价值

`logprobs` 本质上是模型对候选 Token 的概率信息。

它的价值不在日常聊天，而在排查和评估：

- 看模型当时是不是很犹豫；
- 判断某个词是不是高置信度输出；
- 帮助分析为什么结构化输出不稳定；
- 做更细粒度的结果打分。

如果你在做高要求场景，比如抽取、分类、审核、结构化生成，`logprobs` 是个很有用的调试信息。

## 十三、怎么把这些知识点落到工程实践

### 1. 先优化上下文，再纠结参数

优先级通常应该是：

1. 提示词是否清楚；
2. 上下文是否干净；
3. 检索内容是否准确；
4. 工具结果是否裁剪；
5. 最后才是微调采样参数。

### 2. 稳定场景优先低发散

像这些场景优先求稳：

- RAG 问答；
- 工具调用；
- 结构化 JSON；
- 代码和 SQL；
- 生产级流程自动化。

### 3. 创意场景再适度放开

如果是：

- 头脑风暴；
- 文案润色；
- 多版本生成；
- 角色化表达；

再考虑略微提高温度或放宽候选池。

### 4. 长上下文应用必须做预算管理

尤其在 Agent / RAG / Workflow 场景中，要有明确意识：

- 每一段工具输出都在抢上下文；
- 每一轮对话历史都在抬高成本；
- 每一次“多塞一点信息”都可能降低模型聚焦能力。

## 十四、最值得记住的结论

如果只记 6 句话，我会记这 6 条：

1. Token 决定成本，也直接影响时延。
2. 上下文窗口不是越大越好，关键是信息密度和组织方式。
3. 长上下文应用的核心不是“能塞多少”，而是“如何只塞必要信息”。
4. 低温度更适合事实、代码、结构化输出；高温度更适合创意任务。
5. 参数调优只能放大或抑制模型倾向，不能替代正确的上下文设计。
6. 真正稳定的 AI 应用，靠的是上下文管理、预算控制、工具裁剪和输出校验，而不只是“换个模型试试”。

## 总结

理解大模型运行机制，真正有价值的不是背术语，而是建立工程判断：

- 为什么这个调用贵；
- 为什么这个回答慢；
- 为什么这个输出不稳定；
- 为什么这个 RAG 明明检索到了还答不好；
- 为什么明明换了更长上下文模型，效果却没明显提升。

把 `Token`、`上下文窗口`、`采样参数`、`预算控制` 这几件事想清楚，你在做 Prompt、Agent、RAG、面试回答和线上排障时，思路都会清晰很多。
