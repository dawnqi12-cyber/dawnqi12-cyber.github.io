## 2. LLM 应用基础

### 2.1 必须掌握的基本概念

#### Token 与上下文窗口

模型不是按完整汉字或单词处理文本，而是将文本拆成 Token。上下文窗口表示一次请求中模型可处理的输入和输出总长度。

常见问题：

- 输入过长会导致截断或请求失败。
- 历史对话越多，成本和延迟越高。
- RAG 拼接内容过多可能挤占用户问题和输出空间。

解决方式：

- 压缩或摘要历史消息。
- 只保留与当前任务相关的上下文。
- 限制检索结果数量和单条文档长度。
- 对长文档采用分层摘要或父子块检索。

#### Embedding

Embedding 是将文本转换为向量的过程。语义相近的文本在向量空间中的距离通常更近。

需要理解：

- Embedding 模型和生成模型可以不同。
- 向量维度、语言支持和领域适配会影响检索效果。
- 文档和查询必须使用兼容的 Embedding 模型。
- 相似度高不等于答案一定正确，仍然需要生成阶段的约束。

#### 推理参数

| 参数 | 作用 | 常见使用建议 |
| --- | --- | --- |
| Temperature | 控制随机性 | 事实问答、工具调用通常设低；创作任务可适当提高 |
| Top-P | 控制候选词采样范围 | 通常与 Temperature 二选一调整 |
| Max Tokens | 限制输出长度 | 根据任务设上限，避免异常长输出 |
| Stop | 指定停止序列 | 结构化流程或特殊格式中使用 |
| Seed | 尝试提高复现性 | 只是在支持的模型和场景下提高稳定性，不等于绝对确定 |

### 2.2 对话消息与上下文管理

典型消息结构：

```python
messages = [
    {"role": "system", "content": "你是一个严谨的知识库问答助手。"},
    {"role": "user", "content": "请回答：什么是向量检索？"},
]
```

工程上还要处理：

- 会话 ID 与用户 ID 的隔离。
- 历史消息持久化。
- 历史消息摘要。
- 多租户数据隔离。
- 敏感字段脱敏。
- 对话超时和取消。

### 2.3 结构化输出

结构化输出适用于：

- 任务计划。
- 工具参数。
- 分类结果。
- 评测结果。
- 审核结论。

推荐使用 JSON Schema、Pydantic 或框架自带的结构化输出能力。不要只依赖 Prompt 中的“请返回 JSON”，还应在应用侧进行解析和校验。

```python
from pydantic import BaseModel, Field


class TaskPlan(BaseModel):
    goal: str
    steps: list[str] = Field(min_length=1)
    risk_level: str
```

面试要点：

- 解析失败时是否重试？
- 重试是否携带原始错误？
- 是否限制字段长度和枚举值？
- 模型返回的内容是否需要二次安全检查？

### 2.4 Function Calling 基础流程

```text
用户请求
  ↓
模型判断是否需要工具
  ↓
返回工具名和参数
  ↓
应用校验参数并执行工具
  ↓
将工具结果放回消息上下文
  ↓
模型生成最终答案或继续调用工具
```

工具调用的责任边界：

- 模型负责提出调用意图和参数。
- 应用负责权限验证、参数校验和实际执行。
- 任何写操作、支付、删除、发送消息等高风险动作都不应只依赖模型决定。

### 2.5 基础实践任务

完成一个 Python 最小应用：

1. 调用大模型完成普通问答。
2. 增加结构化 JSON 输出。
3. 注册一个计算器工具。
4. 对工具参数进行类型校验。
5. 增加超时、重试和错误日志。
6. 记录请求耗时、Token 和工具调用次数。

验收标准：

- 正常问题可以返回答案。
- 非法参数不会直接执行工具。
- 工具异常时用户能得到可理解的错误信息。
- 日志中可以还原一次完整调用链。

### 2.6 高频问答

**问：RAG 为什么能减少幻觉？**

答：RAG 在生成前检索外部知识，并将检索结果作为上下文提供给模型，使模型有更可靠的事实依据。但 RAG 不能自动保证正确性，仍然可能出现召回错误、上下文冲突、模型误读或无依据扩展，因此需要引用、拒答、评测和事实校验机制。

**问：如何让模型稳定返回 JSON？**

答：使用结构化输出或 JSON Schema 约束，定义字段类型、必填字段和枚举值；应用侧做解析和 Pydantic 校验；解析失败时进行有限次数重试；对字段长度、敏感内容和业务规则做二次校验。

## 3. Agent 核心范式

### 3.1 Agent 的基本组成

一个 Agent 通常由以下部分组成：

```text
目标 Goal
  + 状态 State
  + 推理模型 LLM
  + 工具 Tools
  + 记忆 Memory
  + 规划 Planner
  + 执行器 Executor
  + 约束与安全 Guardrails
  + 观测、日志和评测 Observability
```

Agent 和普通 Chain 的主要区别：

- Chain 的执行路径通常预先确定。
- Agent 可以根据中间结果选择工具、调整步骤或结束任务。
- Agent 的灵活性更高，但可控性、成本、调试难度和安全风险也更高。

### 3.2 ReAct

#### 工作流程

```text
用户目标
  ↓
模型分析当前状态
  ↓
选择工具并生成参数
  ↓
执行工具
  ↓
接收 Observation
  ↓
判断是否继续
  ├─ 是：继续思考和调用
  └─ 否：生成最终答案
```

#### 适用场景

- 需要根据实时结果动态决策。
- 工具调用路径无法提前确定。
- 搜索、计算、数据库查询、网页分析等任务。

#### 优点

- 灵活处理不确定任务。
- 可以利用中间观察结果修正方向。
- 工具扩展比较自然。

#### 缺点

- 调用次数不可预测。
- 容易出现循环调用。
- 受模型决策质量影响较大。
- Token、延迟和成本较高。

#### 必须实现的控制项

- 最大迭代次数。
- 单次工具超时。
- 工具白名单。
- 参数 Schema 校验。
- 重复调用检测。
- Token 和费用预算。
- 任务取消。
- 最终答案兜底。

### 3.3 Plan-and-Solve

#### 工作流程

```text
用户目标
  ↓
Planner 生成结构化计划
  ↓
校验计划：是否完整、是否存在高风险操作
  ↓
Executor 按步骤执行
  ↓
每步记录状态和结果
  ↓
失败时重试或重新规划
  ↓
汇总并生成最终结果
```

#### 适用场景

- 多步骤流程清晰。
- 任务需要稳定、可审计和可恢复。
- 研究报告、代码开发、数据分析、流程自动化等任务。

#### 与 ReAct 的对比

| 维度 | ReAct | Plan-and-Solve |
| --- | --- | --- |
| 决策方式 | 边执行边决策 | 先规划后执行 |
| 灵活性 | 高 | 中等 |
| 可预测性 | 较低 | 较高 |
| 调试难度 | 较高 | 相对较低 |
| 适合任务 | 动态探索 | 稳定多步骤流程 |
| 主要风险 | 循环和过度调用 | 计划错误导致后续偏差 |

实际系统可以组合使用：先用 Planner 生成总体计划，再在每一个复杂步骤内部使用 ReAct。

### 3.4 多智能体协作

#### 常见模式

| 模式 | 说明 | 典型用途 |
| --- | --- | --- |
| Supervisor | 一个主管 Agent 分配任务 | 复杂流程编排 |
| Sequential | Agent 按顺序执行 | 分析、写作、审核 |
| Parallel | 多个 Agent 并行执行 | 多来源检索、多角度分析 |
| Router | 根据问题路由到专门 Agent | 客服、领域专家系统 |
| Critic | 审核或批评主 Agent 结果 | 事实核验、代码审查 |
| Debate | 多个 Agent 讨论后汇总 | 复杂决策和方案比较 |

#### 设计原则

- 每个 Agent 只承担清晰、可验证的职责。
- Agent 之间传递结构化结果，不传递无边界的长文本。
- 共享状态要定义字段、所有权和修改规则。
- 设置最大轮次、超时和异常转移。
- 最终汇总需要解决结果冲突。
- 高风险动作交给独立审核节点。

#### 多智能体的代价

- 调用次数和成本增加。
- 调试链路更复杂。
- 状态同步可能出错。
- 角色边界不清时会互相推诿或重复工作。

### 3.5 Agent 状态设计

建议至少包含：

```python
state = {
    "user_request": "",
    "plan": [],
    "current_step": 0,
    "tool_results": [],
    "draft_answer": "",
    "review_result": None,
    "errors": [],
    "risk_level": "low",
    "trace_id": "",
}
```

面试中要说明：状态不是越多越好，应区分：

- 用户输入。
- 过程状态。
- 工具结果。
- 最终输出。
- 审计信息。
- 不应暴露给用户的内部信息。

### 3.6 实践任务

实现两个版本：

**版本 A：ReAct Agent**

- 工具：搜索、计算、知识库查询。
- 增加最大 5 轮循环。
- 工具调用失败后最多重试 2 次。
- 发现重复参数时停止调用。

**版本 B：Plan-and-Solve Agent**

- Planner 输出结构化步骤。
- Executor 执行步骤并保存结果。
- Reviewer 审核结果。
- 审核失败时返回 Planner 重新规划。

## 4. Agent 开发框架

### 4.1 LangChain

重点对象：

- `PromptTemplate`：管理 Prompt 模板。
- `Runnable`：组合模型、解析器和工具。
- `Tool`：封装可调用能力。
- `Retriever`：封装检索逻辑。
- `Memory`：管理历史消息或状态。
- `OutputParser`：解析模型输出。
- Callback：记录过程、Token、耗时和错误。

面试表达：LangChain 适合快速组合模型、工具、检索器和解析器，生态完整；但复杂循环和长期状态管理需要额外设计，不能把框架默认行为当作生产级可靠性保证。

### 4.2 LangGraph

LangGraph 适合有状态的 Agent 工作流，核心概念如下：

| 概念 | 作用 |
| --- | --- |
| State | 工作流共享状态 |
| Node | 一个处理步骤或 Agent |
| Edge | 节点之间的流转 |
| Conditional Edge | 根据状态动态路由 |
| Checkpoint | 保存执行进度，支持恢复 |
| Interrupt | 暂停等待人工确认 |

典型流程：

```text
START → Planner → Executor → Reviewer
                    ↑           ↓
                    └──失败─────┘
                                ↓
                              END
```

需要练习：

- 线性节点。
- 条件路由。
- 循环执行。
- 失败重试。
- 状态持久化。
- 人工审批。

### 4.3 LlamaIndex

重点理解它在数据接入和知识库场景中的优势：

- 文档加载和解析。
- Node 切分。
- Index 构建。
- Retriever 和 Query Engine。
- 知识库与 Agent 结合。

适合用于快速构建数据密集型 LLM 应用。面试时应说明：框架选择取决于团队已有技术栈、数据接入复杂度、状态工作流需求和运维能力，而不是简单比较“哪个框架更好”。

### 4.4 AutoGen

重点了解：

- 多 Agent 对话。
- 角色定义。
- 自动协作。
- 人工介入。
- 多轮任务终止条件。

面试中要特别关注多轮对话的终止、成本和权限控制。

### 4.5 框架选型回答模板

```text
如果任务是简单问答或固定流程，我会优先使用轻量 Chain，降低复杂度。
如果任务包含循环、条件分支、人工审批、持久化状态和失败恢复，我会使用 LangGraph。
如果核心难点是多种文档接入和知识库检索，我会重点评估 LlamaIndex。
如果需要快速验证多 Agent 对话协作，可以使用 AutoGen，但上线前仍需要补充状态、权限、观测和评测能力。
```

## 5. RAG 与向量数据库

### 5.1 RAG 完整链路

```text
数据接入
  → 解析和清洗
  → 结构化切分
  → 生成 Embedding
  → 写入向量数据库
  → 用户问题改写
  → 召回候选内容
  → Metadata 过滤
  → Rerank
  → 拼接上下文
  → LLM 生成
  → 引用和答案校验
```

### 5.2 文档处理

处理重点：

- 去除重复页眉、页脚和无意义空白。
- 保留标题层级和章节信息。
- 表格不要简单压平成无序字符串。
- 代码、公式、列表应保持结构。
- 记录来源文件、页码、标题、权限和更新时间。
- 对扫描 PDF 使用 OCR，并检查 OCR 错误。

### 5.3 Chunk 切分策略

常见方法：

- 固定长度切分：简单，但容易切断语义。
- 按段落切分：适合结构化文本。
- 按标题层级切分：保留文档语义结构。
- 递归切分：在多个分隔符之间逐层调整。
- 父子块切分：小块负责召回，大块负责提供上下文。

参数不能机械照搬，应通过评测集调优：

- Chunk 太小：语义不完整，召回片段缺少背景。
- Chunk 太大：主题混杂，噪声多，Token 成本高。
- Overlap 太小：跨块信息容易断裂。
- Overlap 太大：重复内容增加索引量和上下文噪声。

### 5.4 检索策略

#### 向量检索

适合语义相似但关键词不同的问题。

#### 关键词检索

适合专有名词、编号、产品型号和精确匹配。

#### 混合检索

同时使用向量检索和关键词检索，再进行融合排序，通常比单一检索更稳健。

#### Query Rewrite

把口语问题改写成更适合检索的查询，尤其适合多轮对话中的指代和省略。

#### Multi-Query

让模型生成多个检索角度，再合并候选结果，适合问题表达存在歧义的场景。

#### Rerank

先用向量数据库快速召回较多候选，再用更精确的模型重排序，平衡召回率和精确率。

### 5.5 向量数据库设计

需要考虑：

- 向量维度和相似度函数。
- 索引类型和查询延迟。
- 文档版本和增量更新。
- Metadata Filter。
- 权限过滤和租户隔离。
- 删除、重建和数据一致性。
- 备份、恢复和容量扩展。

典型数据结构：

```json
{
  "id": "doc_001_chunk_003",
  "text": "文档片段内容",
  "embedding": [0.12, -0.03],
  "metadata": {
    "document_id": "doc_001",
    "title": "员工报销制度",
    "page": 3,
    "tenant_id": "tenant_a",
    "access_level": "internal",
    "updated_at": "2026-07-22"
  }
}
```

### 5.6 RAG 排障顺序

遇到答案错误时，按以下顺序定位：

1. 原始文档是否包含正确答案？
2. 文档解析是否丢失内容？
3. Chunk 是否切分合理？
4. 查询是否被正确改写？
5. Top-K 是否召回了正确片段？
6. Metadata Filter 是否误过滤？
7. Rerank 是否把正确片段排到后面？
8. Prompt 是否明确要求基于上下文回答？
9. 模型是否忽略或误读了上下文？
10. 答案校验和引用是否正常？

### 5.7 RAG 实践任务

构建一个本地知识库问答项目：

- 支持 Markdown 或 PDF。
- 保存文档来源和页码。
- 支持向量检索。
- 增加关键词或混合检索。
- 让答案携带引用。
- 对无答案问题拒答。
- 准备 30 条测试问题，其中包含 5 条无答案问题。

验收指标建议：

- Recall@K：正确片段是否进入前 K 条。
- Context Precision：召回内容中相关内容的比例。
- Answer Relevance：答案是否回应了问题。
- Faithfulness：答案是否有上下文依据。

## 6. Prompt Engineering 与 Function Calling

### 6.1 Prompt 模板

推荐模板：

```text
# 角色
你是一个严谨的企业知识库问答助手。

# 任务
只根据提供的参考资料回答用户问题。

# 参考资料
{context}

# 规则
1. 资料没有明确答案时，回答“当前资料无法确认”。
2. 不得编造政策、时间、金额和人员信息。
3. 结论后附上来源编号。

# 输出格式
{
  "answer": "...",
  "citations": ["source_1"],
  "confidence": "high|medium|low"
}
```

### 6.2 Prompt 设计检查点

- 任务是否单一明确？
- 输入、上下文和指令是否分隔？
- 输出格式是否可验证？
- 是否定义不确定时的行为？
- 是否限制工具使用范围？
- 是否考虑恶意输入覆盖系统指令？
- 是否准备了边界样例和反例？

### 6.3 Prompt Injection

攻击示例：

- 文档中写入“忽略之前的所有指令”。
- 用户要求模型泄露系统 Prompt。
- 用户诱导 Agent 调用不相关的高权限工具。
- 检索内容伪装成系统消息。

防护原则：

- 把外部文档视为不可信数据，而不是指令。
- 在 Prompt 中明确区分指令和参考资料。
- 工具权限由应用层决定，不由模型自行授予。
- 工具输出进行长度、格式和敏感信息检查。
- 对高风险动作要求人工确认。

### 6.4 Function Calling 设计

工具定义应包含：

- 清晰的工具名称。
- 准确的功能描述。
- 严格的参数 Schema。
- 参数取值范围。
- 权限要求。
- 错误返回格式。
- 是否有副作用。

工具分类：

| 类型 | 示例 | 是否通常需要人工确认 |
| --- | --- | --- |
| 只读查询 | 搜索、查库存、查订单 | 通常不需要 |
| 低风险计算 | 汇率计算、格式转换 | 通常不需要 |
| 数据修改 | 修改地址、更新状态 | 建议确认 |
| 外部发送 | 发邮件、发消息 | 通常需要确认 |
| 高风险操作 | 删除、支付、权限变更 | 必须确认或禁止自动执行 |

### 6.5 工具调用实践任务

实现以下工具：

1. `search_documents(query, filters)`
2. `calculate(expression)`
3. `get_order(order_id)`
4. `update_order(order_id, status)`

要求：

- 查询工具允许自动执行。
- 修改工具需要二次确认。
- 参数缺失时不能猜测关键字段。
- 工具异常需要返回可识别的错误码。
- 记录调用者、参数摘要、耗时和执行结果。

## 7. 幻觉抑制与安全边界

### 7.1 幻觉分类

| 类型 | 表现 | 排查方向 |
| --- | --- | --- |
| 事实幻觉 | 生成不存在的信息 | 上下文约束、引用、拒答 |
| 检索幻觉 | 召回内容不相关 | Chunk、Embedding、Top-K、Rerank |
| 工具幻觉 | 虚构工具结果 | 强制真实工具返回，不允许模型伪造 |
| 计划幻觉 | 计划不可执行 | 计划校验、依赖检查、执行反馈 |
| 引用幻觉 | 引用与答案不对应 | 引用片段绑定和自动校验 |
| 状态幻觉 | 误记历史或任务状态 | 显式状态、持久化和权限隔离 |

### 7.2 抑制方案

按成本从低到高可以逐步加入：

1. 降低随机性。
2. 明确回答范围。
3. 提供高质量上下文。
4. 要求引用来源。
5. 无依据时拒答。
6. 使用结构化输出。
7. 加入答案自检。
8. 使用独立 Critic 或事实核验模型。
9. 对关键事实调用外部系统核验。
10. 对高风险业务采用人工审批。

### 7.3 安全边界

必须覆盖：

- 输入安全：恶意 Prompt、越权指令、敏感信息。
- 数据安全：租户隔离、权限过滤、脱敏。
- 工具安全：白名单、参数校验、最小权限。
- 运行安全：超时、重试、循环上限、费用上限。
- 输出安全：敏感内容、违法内容、内部信息泄露。
- 审计安全：Trace ID、用户、工具、结果和审批记录。

### 7.4 高风险动作处理模板

```text
模型提出动作
  ↓
应用校验用户身份和权限
  ↓
校验参数、资源范围和幂等性
  ↓
判断风险等级
  ├─ 低风险：自动执行
  └─ 高风险：展示摘要并等待人工确认
  ↓
执行并记录审计日志
```

## 8. Agent 测试、评估与监控

### 8.1 测试分层

#### 单元测试

测试内容：

- 文档切分。
- Metadata 生成。
- 查询改写。
- 参数校验。
- 工具函数。
- 输出解析。
- 重试和超时逻辑。

#### 集成测试

测试内容：

- Agent 是否选择正确工具。
- 工具结果是否正确回传。
- 状态是否正确流转。
- 失败是否进入预期分支。
- 计划、执行和审核是否闭环。

#### 回归测试

模型、Prompt、Embedding、切分策略或检索参数发生变化后，重新运行固定测试集，比较指标变化。

#### 对抗测试

包括：

- Prompt Injection。
- 越权查询。
- 恶意文件。
- 超长输入。
- 工具参数注入。
- 重复调用。
- 无答案问题。
- 相互矛盾的文档。

### 8.2 评测数据集设计

每条测试数据至少包含：

```json
{
  "id": "case_001",
  "question": "员工出差可以报销哪些费用？",
  "expected_answer": "...",
  "reference_sources": ["travel_policy.md#section-2"],
  "expected_tools": ["search_documents"],
  "risk_level": "low",
  "must_refuse": false
}
```

数据集应覆盖：

- 常见问题。
- 多轮追问。
- 模糊问题。
- 无答案问题。
- 需要工具的问题。
- 不应调用工具的问题。
- 恶意输入。
- 高风险操作。

### 8.3 核心指标

| 指标 | 含义 |
| --- | --- |
| Task Success Rate | 任务是否完成 |
| Tool Selection Accuracy | 是否选择正确工具 |
| Tool Argument Accuracy | 工具参数是否正确 |
| Recall@K | 正确文档是否召回 |
| Precision@K | 召回内容是否相关 |
| Faithfulness | 答案是否有上下文依据 |
| Answer Relevance | 答案是否回应问题 |
| Citation Accuracy | 引用是否支持答案 |
| Latency | 端到端和各节点耗时 |
| Token / Cost | 单次和总体成本 |
| Error Rate | 解析、工具、模型错误率 |

### 8.4 LLM-as-a-Judge 的注意事项

可以使用模型辅助评分，但要注意：

- 评分标准必须明确。
- 评分模型和被评测模型最好不要完全相同。
- 关键场景保留人工抽检。
- 不能只看平均分，还要看失败案例。
- 记录评分 Prompt 和模型版本。

### 8.5 线上观测

一次完整 Trace 至少记录：

- `trace_id`。
- 用户请求摘要。
- 模型名称和版本。
- Prompt 版本。
- 检索查询和召回文档 ID。
- 工具名称和参数摘要。
- 每个节点耗时。
- Token 数和费用。
- 最终结果。
- 错误码和重试次数。

### 8.6 问题定位方法

使用“现象 → 定位节点 → 最小复现 → 修复 → 回归”的流程：

```text
答案错误
  ├─ 检索错误？查看召回结果
  ├─ 工具错误？查看参数和真实返回
  ├─ 规划错误？查看计划和状态转移
  ├─ Prompt 错误？检查约束和上下文拼接
  └─ 生成错误？增加校验、引用或模型能力
```

## 9. 系统设计与工程化

### 9.1 典型 Agent 架构

```text
客户端
  ↓
API 网关 / 鉴权 / 限流
  ↓
会话管理与任务编排

Agent Runtime
  ├─ Planner

  ↓
日志、Trace、评测、告警和成本监控
```

### 9.2 可靠性设计

- 所有外部调用设置超时。
- 只对可重试错误重试。
- 使用指数退避，并限制最大次数。
- 工具写操作设计幂等键。
- 关键状态持久化。
- 支持任务暂停和恢复。
- 失败时提供降级答案或人工接管。
- 对循环流程设置上限。

### 9.3 成本与延迟优化

- 先用小模型做路由、分类和查询改写。
- 只在复杂节点使用大模型。
- 减少无效历史上下文。
- 限制检索数量和输出长度。
- 缓存 Embedding、检索结果和稳定问答。
- 并行执行相互独立的检索任务。
- 避免无意义的多 Agent 讨论。
- 监控每个节点的 Token 和耗时。

### 9.4 生产化前检查

- 是否有鉴权？
- 是否有租户和数据权限隔离？
- 是否有 Prompt 和模型版本管理？
- 是否有测试集和回归门禁？
- 是否有超时、重试和限流？
- 是否有工具调用审计？
- 是否能人工接管？
- 是否能复现线上问题？
- 是否有成本预算和异常告警？

## 10. 项目表达与高频面试题

### 10.1 项目介绍模板

用 2～3 分钟完成第一轮项目介绍：

```text
我负责的是一个 ______ 系统，目标是解决 ______ 问题。

系统主要由 ______、______ 和 ______ 组成。
在 Agent 部分，我采用 ______ 范式，因为这个任务具有 ______ 特点。
知识库部分使用 ______ 检索，主要解决 ______ 问题。
工具调用通过 ______ 实现，并在应用层增加了 ______ 安全控制。

项目中最棘手的问题是 ______，我通过 ______ 定位到原因，最终采用 ______ 解决。
上线后重点关注 ______、______ 和 ______ 指标。
```

### 10.2 高频理论题

#### 什么是 Agent？

Agent 是一个能够围绕目标，利用模型进行决策，并通过工具、状态和环境反馈完成任务的系统。它不只是一次模型调用，核心在于决策、执行、观察和循环控制。

#### ReAct 和 Chain 有什么区别？

Chain 的步骤和路径通常预先确定；ReAct 会根据当前观察结果动态决定下一步操作。ReAct 灵活性更高，但成本、延迟和不可控性也更高。

#### 什么时候不应该使用 Agent？

当流程完全固定、结果要求高度确定、工具调用路径明确，或任务只需要一次模型生成时，不应为了“智能体”而引入复杂循环。固定流程使用普通 Chain 或代码编排往往更容易测试和维护。

#### 如何避免 Agent 无限循环？

设置最大迭代次数、超时、费用预算和重复调用检测；对工具结果进行状态更新；为异常设计终止分支；必要时由 Supervisor 或人工节点接管。

#### 为什么多智能体不一定更好？

多智能体可以分工和并行，但会增加模型调用、状态同步、冲突解决和调试成本。只有当任务确实需要专业角色分工、并行探索或独立审核时才值得使用。

### 10.3 高频 RAG 题

#### RAG 效果不好如何排查？

先检查数据是否存在，再依次检查解析、切分、Embedding、召回、过滤、Rerank、上下文拼接和生成约束。必须查看真实召回片段，不能只凭最终答案猜原因。

#### 如何提升召回率？

优化文档清洗和切分；调整 Chunk 参数；使用 Query Rewrite、Multi-Query、混合检索、Metadata Filter 和 Rerank；同时建立 Recall@K 测试集验证改动是否有效。

#### 如何处理知识库没有答案的问题？

让系统识别低相关度或低置信度情况，明确要求只能基于参考资料回答；当资料不足时拒答或转人工，不允许模型用常识补全关键事实。

### 10.4 高频工程题

#### 如何处理工具调用失败？

区分参数错误、权限错误、业务错误、网络错误和服务不可用。参数错误需要修正或终止；临时网络错误可以有限重试；权限和业务错误应直接反馈；超过重试上限后进入降级或人工处理。

#### 如何控制 Agent 成本？

统计每个节点的 Token、调用次数和耗时；使用模型分层；限制循环次数和输出长度；缓存稳定结果；减少重复检索和无意义的多 Agent 对话；对高成本任务设置预算和告警。

#### 如何保证可观测性？

为每次请求生成 Trace ID，记录 Prompt 版本、模型版本、状态变化、检索结果、工具调用、耗时、Token、错误和最终答案。日志中应脱敏，且能通过 Trace 重放或定位失败链路。

### 10.5 系统设计题：企业知识库 Agent

回答顺序：

1. 明确用户、数据类型、实时性、权限和成功标准。
2. 设计文档入库、解析、切分、Embedding 和索引更新。
3. 设计查询改写、混合召回、过滤和重排序。
4. 设计 Agent 是否需要工具以及工具权限。
5. 设计无答案拒答、引用和人工转接。
6. 设计评测集、线上日志、成本和延迟监控。
7. 说明扩展性、容灾、租户隔离和数据安全。

### 10.6 项目深挖必须准备的失败案例

至少准备以下三类真实案例：

| 失败类型 | 需要讲清楚的内容 |
| --- | --- |
| 检索失败 | 现象、召回样本、根因、参数或架构调整、指标变化 |
| 工具调用失败 | 错误类型、参数校验、重试策略、降级方案 |
| 模型幻觉 | 触发条件、影响范围、拒答或校验方案、回归结果 |

回答时使用：

```text
背景 → 现象 → 影响 → 定位过程 → 方案 → 取舍 → 结果 → 后续改进
```

- 画出 ReAct 时序图。

### 第 6 天：LangChain

验收：能够解释核心组件的职责和组合方式。

- 使用 State、Node、Edge 和条件路由。

- 接入 Markdown 或 PDF。

### 第 12 天：测试与评估

- 建立功能、回归和对抗测试集。
- 统计工具选择、检索和答案质量指标。
- 记录延迟、Token 和成本。

验收：能用数据说明一次优化是否真正有效。

### 第 13 天：系统设计与项目整理

- 画出完整系统架构。
- 准备 2 分钟项目介绍。
- 准备 3 个失败案例。
- 整理技术选型和工程取舍。

验收：不看稿完成项目介绍，并能接受连续追问。

### 第 14 天：模拟面试

- 进行一轮基础知识面试。
- 进行一轮 Agent 系统设计。
- 进行一轮项目深挖。
- 复盘表达不清和技术薄弱点。

验收：能够在 30～45 分钟内完整回答基础、设计和项目问题。

- [ ] 能对比 ReAct、Plan-and-Solve 和多智能体。
- [ ] 能说明 Agent 与 Chain 的区别。

### 编码

- [ ] 能实现结构化输出。
- [ ] 能实现 Function Calling。

- [ ] 能实现 Plan-and-Solve 工作流。
- [ ] 能使用 LangChain 或 LangGraph 完成小项目。

## 结语

这类面试的核心不是背诵框架名词，而是证明自己能够把模型、检索、工具、工作流、安全和评测组合成一个可运行、可观测、可控制的系统。

复习结束时，至少应具备一个可以现场演示的 Agent 项目，并且能够回答三件事：它为什么这样设计、它出问题时如何定位、它上线后如何证明有效。
