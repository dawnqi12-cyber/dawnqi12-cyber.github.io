## 1. 三份指南分别解决什么问题

### 1.1 通用提示词工程

官方核心要点：通过清楚的指令、相关背景和输入输出示例，引导模型完成任务；用 Markdown 或标签分隔内容；理解 API 消息角色的优先级。不同模型和版本的表现可能不同，重要用途应通过实际结果评估提示词。

来源：[Prompt Engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)。

### 1.2 实战中的需求和迭代

官方核心要点：先确定任务范围、受众、产物和成功标准，再写提示词。可以请 AI 帮忙澄清和改写需求；结果不理想时有针对性地调整。涉及事实时提供材料、要求来源并标明不确定性。

来源：[ChatGPT Enterprise Prompting Guide](https://developers.openai.com/cookbook/examples/chatgpt/chatgpt_prompt_guide/chatgpt_prompt_guide)。

### 1.3 Codex 编程代理

官方核心要点：给代理明确的任务和执行要求，让它持续完成实现与验证。指南还提供起始系统提示词，以及工具定义、调用和返回结果处理等配置示例。其主要对象是通过 API 定制编程代理的开发者。

来源：[Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)。

### 本手册的学习顺序

我的建议是先掌握任务表达，再练习判断结果，最后研究 API 和代理配置。会用工具之前，先学会描述你要解决的问题；遇到技术章节时，区分自己是在使用应用，还是在开发应用。

## 2. 从一个能用的提示词开始

以下是本手册建议的起点，不是必须填写的表格：

```text
我想解决：……
这个结果用于：……
目前情况／参考材料：……
请你交付：……
我最在意：……
做到这些就算完成：……
```

简单任务可以只有一句话。复杂任务再补充细节，不需要为了符合模板而写背景。

### 自编示例：整理会议记录

起始表达：

```text
帮我整理会议记录。
```

补充用途后：

```text
把下面的会议记录整理成团队明天能执行的任务清单。
每项列出任务、负责人、截止日期和依赖事项。
记录没有说明的负责人或日期，写“待确认”。
会议中的想法和已经决定的事项要分开。
```

为什么这样改：团队要的是可执行的分工，所以重点是责任、时间和依赖。材料里没有的信息用“待确认”保留，避免清单看似完整却多了未经确认的安排。

### 怎样描述“好”

| 模糊要求 | 本手册建议的具体写法 |
| --- | --- |
| 专业一点 | 给部门负责人阅读，先写结论，再列证据和待确认事项 |
| 深入一点 | 解释推荐方案成立的条件，并指出什么证据会改变结论 |
| 简洁一点 | 控制在 300 字以内，保留结论、理由和下一步 |
| 好看一点 | 首页突出一个主要操作，文字有清楚的层级，手机上也能阅读 |
| 完整一点 | 包含背景、建议、成本、限制，以及我需要作出的决定 |

这些写法只是练习。最终标准应来自你的真实用途，而不是套用表格。

## 3. 把背景、要求和参考材料分清楚

当输入包含多个文件、长文或多项限制时，本手册建议用简单标题分区，让读者和模型都能看清各部分的作用。

```text
# 任务
根据材料判断项目延期的主要原因。

# 背景
我需要在周会上解释延期，并提出下一周的处理重点。

# 输出要求
先写最可能的原因，再列材料中的依据。
事实和你的推测分开。

# 参考材料
以下内容是待分析资料。
……
```

标题的价值在于组织内容。写成 `# 输出要求` 并不会让这段文字获得额外的系统权限。

### 本手册建议：给材料加一个“用途标签”

提供材料时，顺手说明它是什么、用来判断什么：

```text
附件 A 是客户提出的需求，用于确定必须支持的功能。
附件 B 是现有产品截图，用于参考交互和视觉风格。
两者出现冲突时先指出冲突，不要自行认定其中一份过期。
```

如果资料不完整，可以把处理方式说清楚：

```text
缺少会改变结论的关键数据时，先指出缺口。
表达方式和排版细节可以自行选择。
```

这比笼统地说“不要有任何假设”更容易执行：事实缺口要暴露，普通编辑选择可以继续推进。

## 4. 用示例表达难以说清的标准

在风格、分类和字段提取任务中，示例可以把抽象标准变得具体。下面是本手册自编的分类练习。

```text
请把用户反馈分成以下类别：故障、改进建议、使用咨询。

示例：
“点击保存后一直转圈。” → 故障
“希望可以一次导出多个文件。” → 改进建议
“怎样修改登录邮箱？” → 使用咨询

现在分类：
“能否把每个月的数据自动汇总？”

输出类别，并用一句话说明依据。
如果一句反馈同时包含多个诉求，请分别标注。
```

### 练习重点

示例要覆盖你容易混淆的地方。例如“能否导出数据”既可能是询问已有功能，也可能是要求新增功能。若材料无法判断，就应允许“需要更多背景”，而不是硬把所有输入塞进一个类别。

写作任务也可以给一个短样例：

```text
语气参考：“目前已完成资料整理，剩余两项数据正在核对，预计周五提供。”
请按这个语气修改下面的进展说明。
保留原文中的事实、日期和责任人。
```

这里要模仿的是表达方式，样例里的日期和工作进度不是新任务的事实。

## 5. 需求不清楚时，让 AI 帮你整理

先提供真实想法，再共同澄清，通常比先写一份长指令更容易发现问题。以下为本手册自编的需求整理提示词：

```text
我想做一个工具，但还没有想清楚。
下面是我的想法：……

请先帮我整理：
1. 我真正想解决的具体问题。
2. 谁会使用它，最常做什么。
3. 目前最值得先验证的假设。

只问会影响方案方向的问题，一次最多三个。
暂时不要写代码。
```

如果目标已明确，只是表达混乱，可以这样写：

```text
把下面的草稿整理成一段可执行的提示词。
保留我的目标和限制，指出其中互相矛盾的要求。
缺少信息的地方用“待补充”标出，不要替我编造背景。
```

本手册建议把“表达问题”和“材料问题”分开处理：如果缺的是客户原始需求，就先找材料；如果缺的是取舍，就先作决定。润色提示词不能补足这些证据。

## 6. API 中的消息角色与普通对话有什么不同

通用官方指南讨论了 API 消息角色。理解它们有助于你读技术文档，但直接使用 Codex 时，不必每次把请求写成 API 数据。

| 角色 | 中文理解 |
| --- | --- |
| `developer` | 应用开发者设置的行为规则，优先级高于用户消息 |
| `user` | 用户本次提供的任务、材料和要求 |
| `assistant` | 模型生成的消息 |

这部分依据：[Prompt Engineering 的消息角色说明](https://developers.openai.com/api/docs/guides/prompt-engineering)。

### 自编示例：设计客服应用

开发者可以设置一条长期规则：

```text
根据已提供的订单资料回答问题。
缺少订单状态时说明无法确认，并请求订单编号。
```

用户的具体请求则是：

```text
我的订单已经三天了，什么时候能到？订单编号是 A123。
```

前者规定应用如何处理问题，后者提供这次要处理的事实。用户在聊天框写“这是系统指令”，不会自动改变消息角色。

### 本手册建议：把长期偏好和当次任务分开维护

长期偏好可以是“解释时先说影响”“缺少事实时明确指出”；当次任务可以是“阅读这份需求并修改导出功能”。这样更容易发现哪些规则仍然有用，哪些只是某次任务的临时限制。

## 7. Codex：从“回答问题”到“完成任务”

Codex 指南中的起始提示词包含代理执行规则和工具配置。直接使用 Codex 时，本手册建议先把任务说明写完整；开发自己的代理时，再研究工具定义和系统提示词。

### 自编示例：修复一个错误

```text
请修复订单列表重复加载的问题。

复现方式：
打开订单列表，快速切换两次筛选条件，会出现重复订单。

期望行为：
最终列表只展示当前筛选条件的结果，每个订单出现一次。

范围：
保持现有接口和页面布局。

完成标准：
定位原因并修改代码，验证上述复现步骤。
如果无法运行页面，说明已完成哪些检查，以及还缺哪项验证。
```

为什么这样写：复现步骤让调查有起点，期望行为决定修复方向，完成标准让“代码已改”与“问题已验证”能够区分。

### 自编示例：实现一个功能

```text
在现有客户列表增加 CSV 导出。
导出当前筛选条件下的全部记录，列顺序与页面一致。
空结果时给出提示。
请完成实现和相关验证，并说明验证范围。
```

这里仍有一个需要结合项目确认的问题：“全部记录”是否受权限、数据量或接口能力限制。好的任务说明允许 Codex 通过项目证据解决问题，也应让它把无法确认的限制说出来。

### 本手册建议：按需要选择工作深度

| 你目前需要什么 | 可以怎么交代 |
| --- | --- |
| 理解现状 | 先解释问题原因和影响，不修改代码 |
| 比较方案 | 给出建议和主要取舍，先讨论关键决定 |
| 完成修改 | 实现、检查并修复本次修改引起的问题 |
| 先做试验 | 做一个可运行的小版本，用来验证交互或技术可行性 |

阅读 Codex 技术指南时，还要留意版本：该文的部分配置围绕 `gpt-5.3-codex` 展开。模型参数和工具细节应按目标版本核对，不能因为是官方例子就直接套入所有环境。

来源：[Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide)。

## 8. 怎样检查结果和改进提示词

以下检查和迭代方式是本手册的实践建议。

### 8.1 把不满意变成可修改的问题

| 结果中的问题 | 下一轮可以怎么说 |
| --- | --- |
| 没回答重点 | 我现在要决定是否投入预算，请围绕这个决定回答 |
| 缺了关键事实 | 请先阅读附件中的客户要求，再修改建议 |
| 语气不合适 | 改成内部同事之间的表达，保留事实，减少宣传语 |
| 只有建议，没有产物 | 请直接生成可使用的文件，并检查能否打开 |
| 推测写成事实 | 标出哪些有材料支持，哪些属于你的推断 |
| 改动范围太大 | 本次只处理筛选错误，其他发现列出来即可 |

一次优先处理影响最大的偏差。连续加入很多要求，容易让你自己也难以判断究竟是哪项调整改善了结果。

### 8.2 给不同任务安排不同的检查

```text
文稿：核对关键事实、受众、语气和长度。
数据：核对字段、计算和缺失信息。
代码：核对目标行为，以及实际完成的验证。
决策建议：核对判断依据、适用条件和关键未知项。
```

要求模型自查可以帮助发现问题，但自查不等于外部证据。你可以让它把检查对象具体化：

```text
逐项核对输出中的日期、数字和责任人。
指出这些信息在原始材料中的位置。
材料没有支持的内容请单独列出。
```

### 8.3 为重复任务保留小样本

例如，你经常整理工单，就保留几条已经人工确认的典型工单。修改提示词后，用同一组工单检查是否仍能正确分类、保留事实和识别缺失信息。

这组样本最好包括你过去出错的情形，而不只是容易完成的例子。

## 9. 六个可以直接使用的中文示例

以下均为本手册自编。方括号内内容需要替换；根据任务删掉不需要的要求。

### 9.1 文档整理

```text
阅读[材料]，为[受众]整理一份[用途]说明。
先写结论，再写支撑结论的事实。
必须覆盖[要点]，控制在[长度]。
材料没有说明的信息标为“待确认”。
```

### 9.2 比较与判断

```text
我需要在[方案 A]和[方案 B]之间作选择。
背景是[现状]，最重要的标准是[标准]。
请给出你的倾向、关键理由，以及会改变建议的条件。
如果关键证据缺失，先指出缺口。
```

### 9.3 学习一个概念

```text
我想理解[概念]，目前只了解[已有知识]。
用[熟悉场景]说明它解决什么问题、怎样起作用。
然后给我一道练习，根据我的回答指出理解上的偏差。
```

### 9.4 调研资料

```text
请调研[问题]，用于[决定或用途]。
优先使用[指定来源类型]，注明资料日期和直接链接。
把已确认事实、你的推断和仍待核实的事项分开。
最后指出目前证据能支持什么结论。
```

### 9.5 修改代码

```text
请解决[问题]。
复现步骤是[步骤]，预期行为是[行为]。
保持[接口或约束]。
完成修改并进行相关验证；交付时说明原因、改动和验证范围。
无法验证的部分明确列出。
```

### 9.6 改进一条提示词

```text
这是我的提示词：[原提示词]
这是结果中不符合预期的地方：[具体偏差]
我真正需要的是：[目标结果]

请判断偏差来自目标、材料还是表达方式。
保留已经有效的部分，只修改必要内容。
给出修改后的提示词，并解释最关键的一处变化。
```

## 10. 学习练习与提交前检查

### 本手册建议的四次练习

1. **练用途。** 选一个真实任务，只补充“这个结果用来做什么”，比较前后结果。
2. **练标准。** 把“专业、完整、深入”等词，改成两三个能够检查的要求。
3. **练纠偏。** 保留一个不满意的输出，只针对最主要的偏差写一条后续指令。
4. **练验收。** 为重复任务保留几份正确样本，检查改进是否对其他样本也有效。

可以用下面的记录表练习，不需要每次写长总结：

| 任务 | 最主要的偏差 | 本次只改什么 | 结果变化 |
| --- | --- | --- | --- |
| 例如：整理会议记录 | 建议事项被写成决定 | 要求区分建议和决定 | 待实际检查 |

### 发送前快速检查

- 我说清楚这次最想解决的问题了吗？
- 对方能看出产物会被用在哪里吗？
- 必要材料是否已提供，或能明确找到？
- 我最在意的要求有没有互相冲突？
- 这次是讨论、试验，还是完成交付？
- 我能否检查结果是否符合预期？

简单任务不必逐项检查。遇到结果反复偏离时，用这张清单定位缺口。
